# Design: test-metadata-selection

## Context

See proposal.md for the motivation and specs/ for the behaviour. Verified facts that shape the approach:

- **RF 7.5 model.** `TestCase.metadata` (running and result model) is Robot's `Metadata` mapping: names are case, space and underscore insensitive, the first spelling is kept, the last value wins. The cells of one `[Metadata]` row are joined with the separator of the source (two or four spaces stay as they are, a tab becomes one space); continuation lines (`...`) become `\n`; `[Metadata]    Owner` gives `Owner: ''`; `[Metadata]` alone gives `'': ''`, which RobotCode already drops (`named_metadata` in `runner/cli/_search.py`). Variables in names and values are replaced only when the test runs (`SuiteRunner.visit_test`): pre-run modifiers and `discover` see `${BUILD}`, `output.xml` holds the value.
- **RF selection.** `Filter._filter_tests` applies `--test`, `--include` and `--exclude` one after another; nothing looks at metadata. In `robot` and in `discover`'s `handle_options`, pre-run modifiers run before `suite.configure`, so every selection narrows the others. `ModelModifier` logs a `DataError` raised by a modifier's constructor and goes on without the modifier; an exception while visiting is logged too, and a suite left without tests then fails with "contains no tests after model modifiers" (exit 252) unless `--runemptysuite` is given — checked on RF 7.5.
- **RF tag patterns.** `TagPattern.from_string` (RF 7.5) splits at `NOT` first, then `OR`, then `AND`, wherever the text contains them: `Issue:CORE-123` becomes `Issue:C OR E-123`, with a `UserWarning` that RF 8.0 will require spaces around operators (RF #5656); `&` is a deprecated alias for `AND` (RF #5662). A single term is matched with `Matcher(normalize(pattern, ignore="_"), caseless=False, spaceless=False)` against normalised tags. `robot.utils.Matcher` and `robot.utils.normalize` have the same signatures on RF 5.0 and RF 7.5.
- **RobotCode selection.** `-bl/--by-longname` and `-ebl/--exclude-by-longname` are declared in `ROBOT_OPTIONS` (`runner/cli/robot.py`) and reach `robot`, `robot-debug` (REPL package; `_invoke_runner` forwards them to `robot`) and every `discover` command; `RobotFrameworkEx.parse_arguments` appends `robotcode.modifiers.ByLongName`/`ExcludedByLongName` instances to `prerunmodifier`. `results` declares its own `-bl/-ebl` in `RESULT_FILTER_OPTIONS`, applies the same classes in `_apply_tree_filters` after `suite.filter` (one `ModelModifier` pass, `DataError` → `invalid filter pattern` error) and lists them via `_filters_dict`. `robotcode-modifiers` depends only on `robotframework>=5.0` and has no tests yet. The `pre-run-modifiers` setting of `robot.toml` joins arguments with `;` as soon as one contains `:` (`robot/config/model.py`), which Robot's `split_args_from_name_or_path` accepts.
- **Discover.** `discover tags` builds its index in the `Collector`, renders it with `render_tags` and emits `TagsResult`; every discover command takes `ROBOT_OPTIONS` and `DISCOVER_SEARCH_OPTIONS`. Test items carry `metadata` (name → value, author's spelling) on RF ≥ 7.5; suite items carry none (the `test-metadata` spec keeps them unchanged), but `Collector.visit_suite` sees `suite.metadata` on every version, and it already includes `--metadata` given to Robot, because `handle_options` runs `suite.configure` before the collector. `SUPPORTS_TEST_METADATA` hides `--show-metadata` on RF < 7.5. The order of the shared options is fixed by `cli-reference-generation` and `tests/robotcode/runner/cli/test_option_order.py`.

## Goals / Non-Goals

**Goals:**
- One matching rule for the filter and the index, the same on every supported Robot Framework version and independent of the quirks of RF's tag-pattern parser.
- The same options with the same meaning in `robot`, `robot-debug`, `discover` and `results`, and stand-alone modifiers for plain `robot` and `robot.toml` profiles.
- An invalid pattern never widens a selection.

**Non-Goals:**
- Selection by suite metadata (`--by-suite-metadata`); the index shows suite metadata, but only test metadata is selectable. RF #5769 plans `Test Metadata` for metadata shared by the tests of a suite and puts it into each test's own metadata; this selection then covers it without change.
- Statistics by metadata (`results stats --by metadata`), a display in the editor clients, a `robot.toml` key, regular expressions, the `&` operator.
- Metadata selection in Robot Framework itself; the maintainer proposes it separately.

## Decisions

### D1: Entries are the lines of a value

A test's entries are `Name:Line` for every non-empty line of every named value, `Name:` for a value without such a line. Cells of one row are not split: Robot keeps the separator of the source, and a tab becomes a single space, so cells cannot be told from spaces inside a value (`Hans Müller`). Continuation lines are the way to write several values, and they are documented as such. The whole multi-line value is deliberately not an extra entry, although the conversation first proposed it: normalisation removes the line break, so it would only add odd matches such as `Issue:44095769`, and the index could not show it as a value. Every value the index lists is then exactly one entry.

### D2: Own operator parsing, Robot's term matching

The pattern is split into words at whitespace; a word that is exactly `AND`, `OR` or `NOT` is an operator, and the words between operators, joined again, form a term. Terms are grouped with RF's precedence (split at `NOT`, then `OR`, then `AND`; an empty part before a leading `NOT` means "every test"), and each term is matched like a single tag pattern — `Matcher(normalize(term, ignore="_"), caseless=False, spaceless=False).match_any(entries)` with the entries normalised the same way. Rejected: `TagPatterns` over the entries — it splits operators inside words (`CORE-123`, `ANDROID-5`, `NORBERT`), treats `&` as `AND`, warns about RF 8.0, and will change its parsing in RF 8.0; issue keys and names in upper case are typical metadata values. Also rejected: pre-processing the text (lower-casing the terms) before handing it to `TagPatterns` — it still inherits `&` and future parsing changes. `Matcher` and `normalize` are the pieces RF's tag matching itself uses, with an unchanged API since RF 5.0. A term without `:`, an empty pattern or an operator without a term on both sides (apart from a leading `NOT`) raises `DataError` naming the pattern. A prototype of these rules reproduced every pattern scenario of the spec on RF 7.5.

### D3: The logic lives in `robotcode-modifiers`

A new module `packages/modifiers/src/robotcode/modifiers/metadata_modifiers.py` holds `metadata_entries(metadata) -> List[Tuple[str, str]]` (name and line, author's spelling), `MetadataPattern` (parses in its constructor, `match(entries)`), and the `SuiteVisitor`s `ByTestMetadata(*patterns)` and `ExcludedByTestMetadata(*patterns)`, exported from the package like `ByLongName`. `ByTestMetadata` keeps a test if one pattern matches, `ExcludedByTestMetadata` drops it if one matches; both remove suites left without tests in `end_suite`, like `_BaseSuiteVisitor`. The runner imports the entries helper and `MetadataPattern` from there, so the index and the filter cannot drift apart. The package must stay importable with plain Robot Framework, so it does not import RobotCode's `RF_VERSION`: reading `test.metadata` is bound once at import from `robot.version.VERSION` (RF ≥ 7.5 reads the attribute, older versions give no entries), following the repo's rule to resolve version differences at import. Rejected: the helpers in `runner/cli/_search.py` next to `get_test_metadata` — not importable by the stand-alone modifiers.

### D4: Invalid patterns fail early, stand-alone modifiers fail closed

The CLI paths parse every pattern before any work and let the `DataError` take the error path that already exists there: in `RobotFrameworkEx.parse_arguments` Robot reports it and exits with 252 (`robot`, `robot-debug`), `handle_options` turns it into the `DATA_ERROR` exit (`discover`), `_apply_tree_filters` into `invalid filter pattern: …` (`results`). A modifier created by Robot from a string (`--prerunmodifier`, `pre-run-modifiers`) cannot raise in its constructor without Robot skipping it and running every test. So `ByTestMetadata` and `ExcludedByTestMetadata` keep a parse error, and on the first suite they clear its tests and child suites and raise the `DataError`: Robot logs `Executing model modifier '…' failed: Invalid metadata pattern …`, and the suite without tests stops the run (verified with a stand-in modifier on RF 7.5; with `--runemptysuite` it runs nothing). For the exclusion this is deliberate as well: silently excluding nothing would run the tests the user wanted to leave out.

### D5: Options and their order

`-btm/--by-test-metadata PATTERN` and `-ebtm/--exclude-by-test-metadata PATTERN` (`multiple=True`, metavar `PATTERN`) follow `-ebl` in `ROBOT_OPTIONS` and in `RESULT_FILTER_OPTIONS`, declared as needing Robot Framework 7.5 (D8). `RobotFrameworkEx` takes `by_test_metadata` and `exclude_by_test_metadata` (defaulting to empty, so the REPL's other use keeps working) and appends one `ByTestMetadata` and one `ExcludedByTestMetadata` after the longname modifiers; `handle_options` and all discover commands, the `robot` command, `robot-debug` and `_invoke_runner` (forwarding `--by-test-metadata`/`--exclude-by-test-metadata`), and the five results commands with `_apply_tree_filters` thread them through. The names say `test` (maintainer decision): only a test's own metadata is matched, and the names keep `--by-suite-metadata` and `BySuiteMetadata` free for a later selection by suite metadata. The short names are the initials, as `-bl/-ebl` are; `-btm` and `-ebtm` are free in every affected command. `_filters_dict` lists them under `by-test-metadata` and `exclude-by-test-metadata` exactly as given — unlike tag patterns, metadata patterns are not canonicalised, so the echo shows what the user typed — and the checks that decide whether any filter is active include them.

### D6: `discover metadata` is built from the collected items, in two sections

The command takes the options of `discover tags` minus `--normalized` (Robot defines how names compare): `--values/--no-values`, `--tests/--no-tests`, `--tasks/--no-tasks`, `--suites/--no-suites` (all off), `--full-paths`, `ROBOT_OPTIONS` and the search options. It is declared as needing Robot Framework 7.5 like the options (D8; maintainer decision: the feature is only offered with RF ≥ 7.5, although suite metadata exists on every version); called anyway on an older version, it lists the suite metadata and an empty test section. The test section is built from `collector.test_and_tasks` — the items left after every filter — using `metadata_entries` on each item's `metadata`; the suite section from the suites the collector visits, whose named metadata (`named_metadata(suite.metadata)`) the `Collector` records next to each suite item in `visit_suite`. Suite items themselves stay without a `metadata` field, so `discover all` and `discover suites` do not change. The maintainer asked for the suite section once the options were named `--by-test-metadata`: with the level in the option name, an index that shows both levels separately no longer suggests that suite metadata can be selected. In both sections names are keyed by `normalize(name, ignore="_")` and values by `normalize(line, ignore="_")` (the comparison the patterns use), the first spelling is kept, names and values are sorted by their keys, and items keep discovery order (an item is listed once per value). JSON is a new `MetadataResult(metadata, suite_metadata, filters_applied)`, both maps `Dict[str, Dict[str, List[TestItem]]]` (emitted as `metadata` and `suiteMetadata`); their keys are user data and are not camel-cased, as with `TagsResult`. The text renderer follows `render_tags`: under `# Metadata` a `## Tests and Tasks` and a `## Suites` section (a section without entries is left out), `- **Name**`, values as sub-items with `--values`, items below them with `--tests`, `--tasks` or `--suites` (or below the name without `--values`, each item once), and `_(no metadata matched)_` when both sections are empty, inside the usual statistics and diagnostics block.

### D7: Documentation and skill

The documentation shows the feature although `--help` hides it on older versions: every place that describes the options, the command or the modifiers marks them "(Robot Framework 7.5+)", as the existing test-metadata documentation does, and one note says what happens on older versions (not listed in `--help`, still accepted, `--by-test-metadata` selects nothing, `discover metadata` shows only suite metadata). The regenerated `cli.md` — built on RF 7.5, where they are listed — marks them through D8; `--help` carries no note. `discovering-tests.md` gets the command table row, a `metadata` section, a "Selecting by metadata" section (pattern rules and examples, lines versus cells, operator words, unresolved variables, invalid patterns, stand-alone and `robot.toml` use) and the `metadata` JSON shape; `analyzing-results.md` gets the two filter rows, the note that `results` sees values after variable replacement, and a link to the pattern rules; `cli.md` is regenerated. In `robotframework-agent-plugins`, marked "RF 7.5+" as well, `SKILL.md` lists the options next to `-bl/-ebl` and `discover metadata` in the discovery table, `references/authoring.md` names `discover metadata` for the metadata names already in use, `references/results.md` the filter; `scripts/sync_chat_plugin.py` then updates the vendored copy.

### D8: The Robot Framework version is declared once, on the option or command

`runner/cli/_robot_version.py` holds `RobotVersionOption(click.Option)` and `RobotVersionCommand(click.Command)`, used as `click.option(..., cls=RobotVersionOption, since=(7, 5))` and `@discover.command(cls=RobotVersionCommand, since=(7, 5))`. Each hides itself when the installed Robot Framework is older than `since` and keeps `since`; `scripts/create_cmdline_doc.py` recognises them with `isinstance`, as it already does for `AliasedCommand`/`AliasedGroup`, and adds `*(Robot Framework 7.5+)*` to an option's description (before click's `[default: …]`), to a command's entry in the command list and under its section heading. The two metadata options in `ROBOT_OPTIONS` and `RESULT_FILTER_OPTIONS`, `--show-metadata` in `discover` and `results show`, and `discover metadata` use them, replacing their `hidden=not SUPPORTS_TEST_METADATA`. The classes live in the runner because they need RobotCode's `RF_VERSION`; `robotcode-plugin`, home of the other click helpers, does not depend on Robot Framework. Rejected: the note in the help text — it was implemented first and dropped by the maintainer, since `--help` only shows these items where the version is right, so the note is noise there and helps only the web reference; running the generator under several Robot Framework versions and marking what only appears in newer ones — no declaration needed, but the reference generation would need every environment.

## Risks / Trade-offs

- [Robot Framework adds its own metadata selection with other rules] → The options are removed again then (maintainer decision); that removal is a separate, breaking change decided at that time.
- [An operator word, `*`, `?` or `[` inside a value] → Same as for tags: write the word in lower case or without spaces (`Title:rock and roll`, `Title:RockANDRoll`), `[[]` for a literal `[`; documented.
- [Values differ between `robot`/`discover` and `results` when they contain variables] → Documented; tags behave the same way.
- [On RF < 7.5 the hidden `--by-test-metadata` selects nothing] → That is the meaning of the pattern when no test has metadata; `robot` then reports an empty selection like any other filter that matches nothing.
- [A stand-alone modifier with a typo stops the run instead of being ignored] → Intended (D4); the error names the pattern.
- [Pre-parsing in the CLI plus parsing in the modifier] → Parsing is a string split per pattern; negligible.

## Migration Plan

Additive options, command and modifier classes; no migration. `robotcode-modifiers`, `robotcode-runner` and `robotcode-repl` are released together, as always. Rollback is a revert.

## Open Questions

- Whether Robot Framework takes up metadata selection after the maintainer's feature request. It only decides when these options are removed again, not how they work now.
