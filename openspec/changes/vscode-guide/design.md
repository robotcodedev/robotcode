# Design

## Context

The site is Starlight 0.42.5 (see `docs/astro.config.mjs`).

**Sidebar and overview pages**
- The Guides group is autogenerated from `docs/src/content/docs/guides/`. Pages sort by their `sidebar.order`:
  - The overview has order 0.
  - `discovering-tests` comes next at 10.
  - The highlighting tip has order 230.
- Starlight groups a subdirectory into a nested group of its own. The group takes the lowest order of its pages, and its label is the directory name. In `dist/utils/navigation.js`, `groupFromDir` uses `dirName` as label, and nothing lets a page or a config entry override it.
- `src/components/AreaOverview.astro` lists every page whose id starts with `<area>/`, sorted by order. It flattens subdirectories.
- `docs/scripts/llms-index.mjs` and `docs/scripts/check-page-links.mjs` already read the content directory recursively.

**Theme and Markdown**
- Starlight sets `data-theme` on `<html>`. The server renders `dark`, and an inline script replaces it before first paint and whenever the reader switches the theme.
- Its utility CSS has `light:sl-hidden` and `dark:sl-hidden`, which hide an element in the light or the dark theme.
- The Markdown processor (`@astrojs/markdown-satteri` with `headingAttributes`) keeps explicit heading IDs that contain dots. `### \`robotcode.analysis.cache.saveLocation\` {#robotcode.analysis.cache.saveLocation}` renders as `<h3 id="robotcode.analysis.cache.saveLocation">`, checked with `markdownToHtml`.

**The extension and the existing VS Code material**
- The extension's settings are 13 categories in `package.json` `contributes.configuration`, each with `title` and `properties`. The properties use these fields:
  - `type`
  - `default`
  - `description` or `markdownDescription`
  - `enum` with `enumDescriptions` or `markdownEnumDescriptions`
  - `items`
  - `minimum` and `maximum`
  - `scope`
  - `markdownDeprecationMessage`, set only on `robotcode.python`
- `launch.json` offers these configuration snippets:
  - Run Current and Run All
  - Test, Test Profile and Default, which are hidden and carry a `purpose`
  - Remote-Attach
- The language status items are RobotCode, Robot Framework, Python, Robocop and profiles (`languageToolsManager.ts`).
- The output channels are "RobotCode", "RobotCode REPL" and the log channels of the language servers.
- The Test Explorer (`vscode-client/extension/testcontrollermanager.ts`, controller "Robot Framework Tests/Tasks"):
  - **Discovery:** it fills the tree with `robotcode discover … all` per workspace folder, passing unsaved documents on stdin, and with `robotcode discover … tests` per document. `discover` honours `robot.toml` and `.robotignore`.
  - **Updates:** it searches again when a file is created or deleted, when a document is saved or changed (debounced), and when the configuration changes.
  - **Run profiles (`updateRunProfiles`):**
    - Run and Debug per workspace folder, suffixed with `[folder]` in a multi-root workspace; their configure handler opens "Select Configuration Profiles".
    - A Run and a Debug profile per profile of `robot.toml`.
    - A Run and a Debug profile per `launch.json` configuration of type `robotcode` with `purpose: "test-profile"`.
  - **Tags:** Robot Framework tags become test tags.
  - **Results:** a failure carries a `TestMessage` with the location of the failing line, and run output is appended to the test run.
  - **Errors:** a suite's error is set on its item. Discovery errors go to the diagnostics collection "robotCode discovery".
  - **Switching it off:** `robotcode.testExplorer.enabled`.
- The VS Code screenshots and recordings of the home page come from scripts in the git-ignored `playground/robotcode-demo/vscode/`: an isolated harness with its own profile and extensions dir, the demo shop project and a fake HOME. That includes the parked 24-second Documentation Viewer recording (`scene4.js`), which so far exists only in the dark theme.

## Goals / Non-Goals

**Goals:**
- Pages a VS Code user can read in order, each built around what the reader wants to do, with screenshots that match the site's theme.
- A settings reference that cannot drift from `package.json`.

**Non-Goals:**
- A walkthrough inside VS Code (`contributes.walkthroughs`).
- Pages for PyCharm and other editors.
- Notebooks.
- The deprecated language model tools.
- Changes to the extension.
- A CI check that the generated page is current. The CLI and `robot.toml` references have none either.

## Decisions

### D1 Pages under `guides/vscode/`, first in Guides

The group's pages are `.mdx` files, because they use the components of D4.

| File | Address | Sidebar label | Order |
|---|---|---|---|
| `index.mdx` | `/guides/vscode/` | Overview | 0.5 |
| `writing-code.mdx` | `/guides/vscode/writing-code/` | Writing code | 1 |
| `finding-information.mdx` | `/guides/vscode/finding-information/` | Finding information | 2 |
| `documentation-viewer.mdx` | `/guides/vscode/documentation-viewer/` | Documentation Viewer | 3 |
| `test-explorer.mdx` | `/guides/vscode/test-explorer/` | Test Explorer | 4 |
| `running-and-debugging.mdx` | `/guides/vscode/running-and-debugging/` | Running and debugging | 5 |
| `configuration.mdx` | `/guides/vscode/configuration/` | Configuration | 6 |
| `diagnostics-and-linting.mdx` | `/guides/vscode/diagnostics-and-linting/` | Diagnostics and linting | 7 |
| `repl.mdx` | `/guides/vscode/repl/` | REPL | 8 |
| `troubleshooting.mdx` | `/guides/vscode/troubleshooting/` | Troubleshooting | 9 |

The orders lie between the Guides overview (0) and the first other guide (10), so the group sorts right after the Guides overview. Ten pages do not fit into the whole numbers 1–9, so the group's overview takes 0.5. A later page of the group takes a fractional order as well.

Alternatives considered:
- **A sixth top-level area "VS Code":** this changes the area structure of the documentation-site spec, which sorts areas by reader intent, not by editor.
- **The group at the end of Guides:** most readers use VS Code, and the group would sit below the tips.

### D2 The group's label comes from a route middleware

`docs/src/routeData.ts` exports a `defineRouteMiddleware` handler. `astro.config.mjs` registers it as Starlight's `routeMiddleware`. It walks `context.locals.starlightRoute.sidebar` and gives the group labelled `vscode` the label "VS Code".

Alternatives considered:
- **A directory named `VS Code`:** right label, but the path in the repository and in every script contains a space.
- **A hand-written Guides sidebar:** every new guide would need a config entry, and the area would no longer sort by the pages' own orders.

### D3 Area overviews list direct pages only

`AreaOverview` keeps only pages exactly one path segment below the area. The group's `index.mdx` (id `guides/vscode`) is such a page, so `/guides/` shows one card for the group. The group's overview renders `<AreaOverview area="guides/vscode" />` for its nine other pages, which matches the modified "Area overview pages" requirement.

`llms-index.mjs` stays unchanged. It sorts each area flat by order, and because the group's orders sit below the other guides, the flat order equals the sidebar order. To be verified.

### D4 Theme pairs as two components

- **`src/components/ThemeImage.astro`** takes:
  - `light` and `dark` (imported image metadata)
  - `alt`
  - optional `markers` (D5)
  - optional `full`, which wraps each variant in a link to its original file for the full-size view

  It renders both variants with `astro:assets` `<Image>`. The light variant carries `dark:sl-hidden` and the dark variant `light:sl-hidden`. `<Image>` loads lazily, so the hidden variant should not be fetched. To be verified in the browser's network log for both themes.
- **`src/components/ThemeVideo.astro`** renders two `<video autoplay muted loop playsinline>` with width, height, an `aria-label` and the same classes. If a browser downloads or plays the hidden variant, the component adds a small script that sets the source and plays only the visible variant, and follows `data-theme` with a `MutationObserver`.
- **Without JavaScript,** the server-rendered `data-theme="dark"` stays, so the dark variants show.
- **Recordings** follow the maintainer's decision for screenshots: every recording of the group exists in both themes.

Alternatives considered:
- **`<picture>` with `prefers-color-scheme`:** follows the operating system, not the site's theme switch.
- **One theme:** the maintainer chose both.

### D5 Markers as an overlay

`markers` is a list of positions in percent of the image (`{ x, y }`). The component draws numbered badges at these positions over both variants, `aria-hidden="true"`. The numbered list under the picture carries the meaning, and the `alt` text describes the window. Both themes share the layout and thus the positions. When the overview is captured again, its marker positions in `index.mdx` are checked.

Alternative considered: numbers drawn into the PNG. Every new capture would need image editing, twice.

### D6 Window shots only where the window matters

- **Window size:** the harness window is 1036×591 at device scale 2, giving 2072×1182 like the home page.
- **Full window:** the overview, and the pages where the arrangement is the point: the Test Explorer beside the editor, and a debug session on the running page. These pass `full`.
- **Detail shots:** clipped to the relevant region with `page.screenshot({ clip })`. They are at most about 720 CSS pixels wide, so the content column shows them close to their real size.

### D7 Capture by script in the playground

Each page gets a capture script `playground/robotcode-demo/vscode/guide-<page>.js`, run by the existing harness and `setup.js`.

- **Themes:** each script takes every shot twice, once with `workbench.colorTheme` set to "Default Light Modern" and once with "Default Dark Modern". After a theme switch, frames of webviews such as the Documentation Viewer are looked up again.
- **Recordings:** they use screencast mode (keys only), `x11grab` and the encoding of the home page recordings (libx264 CRF 24, yuv420p, faststart). The viewer recording is re-recorded from `scene4.js` in both themes.
- **Files:** `docs/src/assets/screenshots/vscode/<page>-<subject>-light.png` and `…-dark.png` (or `.mp4`).
- **Documentation:** the demo README lists the scripts. They stay outside the repository like the home page's.

### D8 The viewer section moves as a page

`browsing-documentation.md` from `## VS Code` to its end becomes the body of `documentation-viewer.mdx`, with each `###` turned into `##` and the text kept apart from links. The page adds screenshots and the recording. `browsing-documentation.md` keeps a short paragraph that points to the page.

The feature tour's link `/guides/browsing-documentation/#vs-code` changes to the new address. The build's link check finds any other link into the moved section.

### D9 Settings reference generator

`scripts/create_vscode_settings_doc.py`, hatch script `create-vscode-settings-docs`, works like `create_config_doc.py`.

**Input and output**
- It reads `package.json`.
- It keeps the frontmatter of `docs/src/content/docs/reference/vscode-settings.md`: title "VS Code settings", description, sidebar order 4.
- It writes the body.

**Body**
- One `## <category title>` per category, in declared order.
- One `### \`<key>\` {#<key>}` per setting, in declared order, containing:
  - The description: `markdownDescription`, else `description`.
  - For `robotcode.python`, a caution with the deprecation message.
  - A short list:
    - **Type:** with item types for arrays, and alternatives joined with "or".
    - **Default:** as JSON in code.
    - **Allowed values:** each with its (markdown) enum description.
    - **Minimum and maximum.**
    - **Where it can be set:** derived from `scope`, with VS Code's default `window` where none is given. The wording of each scope is checked against VS Code's documentation during implementation.

The output depends only on `package.json`, so regenerating without changes keeps the file byte-identical. `AGENTS.md` and `CONTRIBUTING.md` (the list of generator commands) name the script.

Alternative considered: a Node script. The other generators are Python scripts run through hatch, and contributors already know those commands.

### D10 Writing rules for the pages

- **Checked statements:** every statement about behavior is checked in `package.json`, the extension or language server code, or in the harness. Nothing is assumed.
- **Commands:** named by their Command Palette titles. Keyboard shortcuts are given for Windows/Linux and macOS, as on `getting-started/vscode.mdx`.
- **Settings:** a page that names a setting links to its entry in the settings reference.
- **CLI side:** where a feature also exists on the command line, the page links to that guide (`results`, `doc`, `repl`, `robot-debug`).
- **AI:** the chat plugin commands appear in the overview's command list with a link to the AI agents guide.

### D11 Test Explorer and Running and debugging split by place

- **Test Explorer page:** everything the Test Explorer view does:
  - where its entries come from and when they update
  - the tree of workspace folders and suites
  - filtering by text and tags
  - the run profiles
  - results, failure messages and test output
  - errors of suites and of the discovery
  - the setting that switches it off
- **Running and debugging page:** running and debugging started from the editor (the icons beside the tests, Run/Debug Current File), `launch.json`, breakpoints, the Debug Console, inline values, the log after a run and the profile selection.
- **Run profiles** belong to the Test Explorer page, because VS Code offers them in the Test Explorer's Run and Debug menus and under "Configure Test Profiles".
- The two pages link to each other.

The tag filter syntax and the names VS Code shows for the profiles are taken from the harness, not assumed.

Alternative considered: one page for both. It would mix the explorer view with debugging, and it would be the longest page of the group.

## Risks / Trade-offs

- [VS Code changes its UI every week, so screenshots age.] → All captures are scripted and are run again when the UI around a shot has visibly changed. The text describes what a reader does, not pixel details.
- [Two themes double capture time and image weight.] → Detail shots are crops. Images load lazily, and the hidden variant is not fetched (verified per D4).
- [The command list on the overview is written by hand and can miss a new command.] → It is checked against `package.json` when written. The settings, which change most often, are generated.
- [Marker positions drift when the overview is captured again.] → The positions sit next to the image in `index.mdx` and are part of the re-capture check (D5).
- [External links to `/guides/browsing-documentation/#vs-code` lose the section.] → They still reach the guide, which points to the new page.
