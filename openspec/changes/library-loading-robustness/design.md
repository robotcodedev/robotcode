# Design: library-loading-robustness

## Context

See proposal.md. Verified facts that shape the design:

- **Worker and timeout.** `ImportsManager._run_in_subprocess` (`imports_manager.py`) starts a fresh `ProcessPoolExecutor(max_workers=1, mp_context=spawn)` per library or variable-file load, waits with `.result(self.load_library_timeout)`, turns `TimeoutError` into a `RuntimeError` ("… timed out after N seconds …") and then runs `executor.shutdown(wait=True)` in `finally`, which waits for the worker to finish. Reproduced during planning: a library sleeping 4 s with a 1 s timeout raised at 1.0 s and returned at 4.1 s. `ProcessPoolExecutor.terminate_workers()`/`kill_workers()` exist only from Python 3.14; RobotCode supports 3.10+. A planning prototype with a spawned `multiprocessing.Process`, a one-way `Pipe`, `poll(timeout)` and `terminate()`/`kill()` returned at 1.0 s, the library's code after its blocking call never ran, and `Collections` loaded normally through the same helper.
- **Failure lifetime.** The timeout error propagates out of `_LibrariesEntry._update` / `_VariablesEntry._update`, so `_lib_doc` stays `None` and the next `get_libdoc_with_meta` loads again; two suites importing one hanging library loaded it twice in one `analyze code` run. A load that fails with an error returns a `LibraryDoc` with `errors`, which the entry keeps: two suites importing a refused `Remote` connected only for the first. An entry lives while a namespace references it (`__remove_library_entry` via `weakref.finalize`) and is invalidated by `check_file_changed` (library source, package directory or Python path, depending on what the `LibraryDoc` carries). Library results with errors are written to disk with `meta.has_errors` and not served from it; variable-file results never set `has_errors`. `build_namespace_meta` refuses to persist a namespace when a dependency meta is `None`. `_import_default_libraries` reports only exceptions ("Can't import default library …"), not `LibraryDoc.errors`. The language server is restarted by the VS Code client when `robot.toml`/`pyproject.toml` change and by Clear Cache and Restart (`languageclientsmanger.ts`); `robot/cache/clear` alone clears only the disk cache.
- **Call order.** `get_library_doc_from_library(create_keywords=True)` reads `lib.doc`, builds the init keyword, then creates the keywords. Planning probe with a dynamic library on RF 5.0.1, 6.1.1, 7.0.1 and 7.5: calls `__init__`, `get_keyword_documentation('__intro__')`, `get_keyword_documentation('__init__')`, `get_keyword_names`; on RF < 7 a successful load also creates a second instance. For `Remote` the two documentation requests cost 3 connection attempts before `get_keyword_names` (RobotCode 4, `robot` 2, on RF 5.0.1–7.5). RF 7.5's Libdoc (`LibraryDocBuilder.build`) calls `TestLibrary.from_name`, which creates the keywords, before it reads the documentation. RF < 7 `create_handlers()` resets the instance of non-global libraries (`reset_instance()`); restoring it with `reset_instance(instance)` kept one instance and gave the order `__init__`, `get_keyword_names`, keyword docs, `__intro__`, `__init__` doc on all four versions. Failing keyword names raise `DataError("Getting keyword names from library '…' failed: …")` on every version. When a dynamic library returns no documentation, RF uses the class/module docstring for the introduction (`DynamicLibrary.doc` → `super().doc`) and the `__init__` docstring for the importing documentation (RF 7.5 `LibraryInit.doc`, RF < 7 `_PythonInitHandler.doc`).
- **Fallback without arguments.** `get_library_doc` records the error of `_get_test_library(..., args)` / instantiation and, `if args:`, builds the library again with `()` and documents that instance. Observed with `analyze code` on RF 7.5: `Library StrictLib.py bogus`, `… a b c AS Two` and `… ${NOT_KNOWN} AS Three` report `ImportContainsErrors` / `DataError` / `VariableError`, and all three provide `Strict Keyword` (reported as `MultipleKeywords`); nothing says where the keywords come from. `ignore-arguments-for-library` passes `()` to `get_library_doc`. `LibraryDoc.__setstate__` sets missing slots to `None`; the disk cache is keyed by `app_version`.
- **Duplicate imports.** `ImportResolver._import_library` registers an entry under `alias or name or import_name`; `already_imported` compares source, member, alias and raw `imp.args`; `LibraryAlreadyImported` (INFORMATION) is reported only for that case and only `top_level`; an import whose name is taken otherwise is dropped silently. RF 7.4+ `Namespace._import_library` imports the library first and then calls `_duplicate_library_import_warning`: WARN for a different `real_name` ("another library with name …") or different `init.positional`/`init.named` ("… with different arguments"), INFO for the same arguments; RF ≤ 7.3 logs INFO only (checked on 7.3.2 and 7.4.2). Observed on RF 7.5: `a` then `x=a` warns, `a` then `${VAL}` (= `a`) does not, `n=1` then `n=01` for an `int` argument does not (converted values are compared), aliases are compared by alias. The same `ImportResolver` serves the legacy and the semantic-model analyzer. `get_libdoc_for_library_import_with_meta` keys entries by `resolve_args(args, root_folder, base_dir, command-line variables, scope variables)`, which leaves unresolvable variables literal and fills runtime-only built-ins (`${OUTPUT DIR}`, `${SUITE NAME}`, …) with `""`: the names `_get_default_variables` (`library_doc.py` ≈2157-2198) fills with placeholders; `&{TEST METADATA}` of RF 7.5 has none and already stays as written. `resolve_args` is used only for the two entry keys. Library entries pass the raw arguments to the worker, where `get_library_doc` resolves them through `resolve_robot_variables` with the same placeholders; variable-file entries pass the resolved arguments (`_VariablesEntry(name, resolved_args, …)`), and `get_variables_doc` hands them to `get_variables` as given (verified on RF 7.5: an unresolved `${OUTPUT DIR}/x` arrives literally). The analyzers know all of these built-ins through `BUILTIN_VARIABLES` (`utils/variables.py`). Verified on RF 5.0.1 and 7.5: resolving against the built-ins without the runtime-only ones leaves `${OUTPUT DIR}`, `${output_dir}/a` and a file variable `${LOG}` with the value `${OUTPUT DIR}/x` as written, gives `a/${OUTPUT DIR}` for `${VAL}/${OUTPUT DIR}` with `${VAL}` = `a`, and still resolves `${TEMPDIR}`, `${EMPTY}`, `${CURDIR}/c` and a command-line variable named `OUTPUT DIR`. RF 7.5 warns for `a` followed by `${OUTPUT DIR}`, by `${EMPTY}` or by such a `${LOG}`.

## Goals / Non-Goals

**Goals:**
- A load never blocks longer than `load-library-timeout` (plus process termination), and a timed-out load is not repeated for every namespace build.
- A library whose keyword names cannot be retrieved is asked no more than Robot Framework's import asks it.
- The fallback without arguments, and a library import of the analysed file that Robot Framework 7.4+ ignores with a warning, are visible on the import.

**Non-Goals:**
- Remembering other failures than timeouts beyond today's behaviour (errors are already kept in the entry; exceptions such as an unresolvable library name stay fast and are not cached).
- Reporting ignored imports inside imported resource files, and imports that Robot Framework would reject before its duplicate check.
- Changing how a library or variable file is loaded when an argument refers to a runtime-only built-in: the placeholders stay, and so do the entry keys. `library-keyword-set-declaration` later skips such a load for libraries that declare their keyword set (its D4) and adds the result of the D5 method to the library entry key (its D2).

Not decided by this design, see Open Questions: ending processes that a library started itself, the import-name completion executor, the consumer reloads with `()`, the disk caching of failed variable-file loads, and a user-triggered retry.

## Decisions

### D1: Hard timeout with a plain spawned process

`_run_in_subprocess` keeps its contract (one fresh process per load, `spawn` context, same callers) but uses a `multiprocessing` `Process` whose module-level target sends `(ok, value)` over a one-way `Pipe`. The parent waits with `poll(load_library_timeout)`; on expiry it raises a dedicated timeout exception (a `RuntimeError` subclass with today's message, so callers can tell a timeout apart). A `finally` block ends a worker that is still alive in every case (timeout, `KeyboardInterrupt`, errors): `terminate()`, `join` for one second, `kill()` if needed, `join()`. An exception raised in the worker is re-raised in the parent with its type; if it cannot be pickled, a `RuntimeError` with its text is sent instead. A worker that ends without sending a result raises a `RuntimeError` naming its exit code (today `BrokenProcessPool`); the parent closes its copy of the sending end after `start()`, so `poll` returns at the worker's exit instead of at the timeout.

Rejected: `terminate_workers()`/`kill_workers()` (Python 3.14 only); killing the pool's processes through `ProcessPoolExecutor._processes` (private attribute); a thread with a timeout (cannot stop the worker); a version split between 3.14 and older.

### D2: A timeout becomes a kept error result

`_get_library_libdoc` and `_get_variables_libdoc` catch the timeout exception and return an error document instead of raising: a `LibraryDoc`/`VariablesDoc` with the import name, `source` set to the file RobotCode already resolved without importing (`LibraryMetaData.origin`, or the found path of an import by path; without a meta, as for `ignored-libraries`, a library imported by module name has no `source` and is watched through `python_path`, like a library that cannot be found), `python_path`, and one `Error` without a source, with today's message and type name (`RuntimeError`, so `_report_entry_errors` reports the same text and code on the import as today). The existing entry code then keeps it (`_lib_doc` is set), attaches its file watchers from `source`/`python_path`, and `check_file_changed` invalidates it when a file changes. The error document is not written to the disk cache, and the methods return `None` as meta, so namespaces that depend on it are not persisted. `ImportResolver` records dependency metas per import name (`lib:{imp.name}`, `var:{imp.name}`), and a later import of the same name overwrites the entry; `_import_library` and `_import_variables` therefore keep an existing `None` for the key instead of replacing it, so that a later import of the same name that loads (for example with other arguments and an alias) does not make the namespace persistable. `library-keyword-set-declaration` relies on the same rule for its run-time fallback and does not add it again. `_import_default_libraries` reports the errors of a returned default-library document with its existing "Can't import default library '…': …" message, so a timed-out `BuiltIn` stays visible. The command-line variable files already report `VariablesDoc.errors`.

Alternatives: caching the exception object in the entry (a second failure path next to `LibraryDoc.errors`, and no file watchers); remembering timeouts on disk (would survive a restart, which the proposal names as the retry point).

### D3: Keyword names before documentation

In `get_library_doc_from_library` with `create_keywords=True`, the keywords are created first (with the capturing logger, as today); on RF < 7 the instance is restored with `lib.reset_instance(instance)` after `create_handlers()` so that the documentation requests use the same instance. If keyword creation succeeds, the introduction, the init keyword, the keyword documentation and the types are built as today. If it raises, the error is recorded and no further call is made to the library: the introduction is the Python docstring of the library class or module, and the init keyword is built from the class `__init__` (its argument specification and docstring) through a `KeywordWrapper` subclass whose `doc` returns that docstring instead of asking the dynamic API; no keywords and types. The per-version access to the static docstrings follows the existing `RF_VERSION < (7, 0)` branches of the function. `create_keywords=False` (REPL, running libraries) is unchanged. Robot Framework's Libdoc also gets the keyword names first (`TestLibrary.from_name` creates the keywords before the documentation is read). The documentation of working libraries does not change: the same requests are made to the same instance, only in another order.

Alternative: dropping the init keyword after a failure — a refused `Remote` shows its arguments `uri`/`timeout` today, and hover of the import would lose them.

### D4: The fallback without arguments carries a marker

`get_library_doc` keeps the retry with `()` (maintainer decision) and sets a new `LibraryDoc` field `loaded_without_arguments: bool = False` when the documented instance comes from that retry. Old pickles get `None` (falsy) through `__setstate__`. `ImportResolver._report_entry_errors` (imports of the analysed file only) appends, after the import's errors, an INFORMATION diagnostic `LibraryLoadedWithoutArguments` (new `Error` constant): "Keywords of library '<name>' come from loading it without arguments, because loading it with the import's arguments failed." INFORMATION, because the original error is already reported as ERROR on the same import and this message only explains the keywords. The marker is data on the `LibraryDoc`, so other surfaces can show the same fact: the canonical documentation of `doc-cli` shows it as a note in its `Importing` section (`doc-cli` D6), and `vscode-doc-browser` shows that documentation. `doc-cli` does not depend on this change, so whichever of the two is implemented later adds the note to the canonical renderer (task 4.3 here, task 4.5 of `doc-cli`). `library-keyword-set-declaration` marks its own load without arguments (arguments known only at run time) with a separate field. It does not attempt a load with the import's arguments for such imports, so `loaded_without_arguments` stays unset and `LibraryLoadedWithoutArguments` is not reported for them (spec: "does not load the library with the import's arguments at all").

Alternatives: appending the note to the error's related information (not suppressible on its own, and invisible to other surfaces); a WARNING (a second warning-or-worse diagnostic on an import that already has an ERROR).

### D5: Warning for library imports that Robot Framework ignores

In `ImportResolver._import_library`, in the branch where the import's name is taken and `already_imported` is `None`, a new warning `LibraryImportIgnored` (new `Error` constant) is reported for `top_level` imports when a module-level flag `RF_VERSION >= (7, 4)` is set:
- no warning if the new or the existing `LibraryDoc` has `errors` (Robot Framework imports the library before its duplicate check, so an import that cannot be loaded gets its error instead; the existing import would not have taken the name);
- "Another library with name '<name>' has already been imported. This import is ignored." if the library names (`LibraryDoc.name`, Robot Framework's `real_name`) differ;
- otherwise the statically resolved arguments of both imports are compared; if either still contains a variable (`contains_variable`: an unknown variable or a runtime-only built-in, see below), no warning; if they differ, "Library '<name>' has already been imported with different arguments. This import is ignored.".

`<name>` is the taken name (alias or library name), related information is `_related_info_from_entry(existing)`. The resolver stores the resolved arguments per registered library name (default libraries with `()`) at the time of each import, since the scope grows while imports are processed. `LibraryEntry` and the namespace cache format are unchanged. `LibraryAlreadyImported` stays as it is. The message leaves out Robot Framework's "Suite '…'" because the analysed file can be a resource file.

The resolved arguments come from a small `ImportsManager` method with the inputs of the entry key of `get_libdoc_for_library_import_with_meta` (root folder, base directory, command-line variables, scope variables). In it, Robot Framework's runtime-only built-ins are known but have no value (maintainer decision): `${TEST NAME}`, `@{TEST TAGS}`, `${TEST DOCUMENTATION}`, `${TEST STATUS}`, `${TEST MESSAGE}`, `${PREV TEST NAME}`, `${PREV TEST STATUS}`, `${PREV TEST MESSAGE}`, `${SUITE NAME}`, `${SUITE SOURCE}`, `${SUITE DOCUMENTATION}`, `&{SUITE METADATA}`, `${SUITE STATUS}`, `${SUITE MESSAGE}`, `${KEYWORD STATUS}`, `${KEYWORD MESSAGE}`, `${LOG LEVEL}`, `${OUTPUT FILE}`, `${LOG FILE}`, `${REPORT FILE}`, `${DEBUG FILE}`, `${OUTPUT DIR}` and `${OPTIONS}`. `_get_default_variables` takes these entries from one module-level dict. A new function in `library_doc.py`, next to `resolve_args`, builds its store from the default variables without that dict and adds `${CURDIR}`, `${EXECDIR}`, the command-line variables and the file's variables as `resolve_robot_variables` does, through a private helper both call; `resolve_args` and `resolve_robot_variables` keep their behaviour and their parameters. Robot Framework's own variable matching then leaves a reference to a runtime-only built-in as written, also when it is written differently (`${output_dir}`) or reached through a variable of the file (`${LOG}    ${OUTPUT DIR}/x`), and the check above treats the argument like one with an unknown variable. The other built-ins (`${TEMPDIR}`, `${/}`, `${EMPTY}`, `${CURDIR}`, …) keep their values, and so does a command-line or robot.toml variable named like a runtime-only built-in. The analyzers keep knowing all built-ins through `BUILTIN_VARIABLES`, which this change does not touch. The entry keys keep `resolve_args` with the placeholders, and library entries still pass the raw arguments to the worker, so loading does not change, including which imports share an entry. The method and `resolve_args` differ only for arguments that refer to a runtime-only built-in, so for all other arguments the method's result is the entry key's tuple. `library-keyword-set-declaration` uses the method for its run-time fallback and its disk entries, adds its result to the library entry key so that imports differing only in a runtime-only built-in get separate entries (its D2), and uses the same function in the worker.

Alternatives:
- comparing raw argument strings (warns for `a` vs `${VAL}` = `a`, which Robot Framework does not);
- comparing converted values like Robot Framework (needs the library's converters, which live in the worker);
- filling the runtime-only built-ins with their placeholders, as the entry key does (`a` then `${OUTPUT DIR}` would be compared as `a` vs `""`, and `${OUTPUT DIR}` then `${EMPTY}` as equal);
- resolving this way in `resolve_args` itself, and so in the entry keys: variable-file entries pass their resolved arguments on, so a variable file would receive `${OUTPUT DIR}/x` instead of `/x`; and a file variable that refers to a runtime-only built-in and is defined differently in two files, such as `${LOG}`, would give both imports one library entry, loaded with the first file's value;
- detecting the runtime-only built-ins by name in the raw arguments (misses a reference through a variable of the file and needs its own name matching).

### D6: Tests

New `tests/robotcode/robot/diagnostics/test_library_loading.py` with libraries written to `tmp_path` (paths embedded with `repr()` for Windows) and a real `ImportsManager` (`DocumentsManager`, mocked `DocumentsCacheHelper`, `tmp_path` as root and cache base): a library that sleeps and then writes a marker file (timeout 1 s: returns long before the sleep ends, marker never written), a load log to count loads, a variable-file counterpart, a crashing worker (`os._exit`) and a normal library. `get_library_doc` tests for the call order with a recording dynamic library and for `Remote` against a local accept-and-close TCP server whose connection count is compared with `Remote(uri).get_keyword_names()` (relative, not a fixed number, so `xmlrpc`'s retry behaviour does not matter). The resolution of D5 is tested on the real `ImportsManager` (runtime-only built-ins as written, directly, written differently and through a file variable; other built-ins resolved; entry keys and loads unchanged). `ImportResolver` tests in the style of `test_import_resolver_dependency_metas.py` for the kept `None` dependency meta and the two diagnostics, with the real resolution of D5 behind the mocked argument resolution, gated by RF version with inverse gates. Time limits in tests are generous (process start on Windows): a library that should load gets the default timeout, a hanging one a short timeout and a sleep well beyond it, and the tests assert "well below the library's sleep", never exact durations.

## Risks / Trade-offs

- [Processes started by the library survive the worker (Java of SikuliLibrary's default mode, node of Browser with `jsextension=`)] → unchanged from today (the executor never ended them either); Open Questions.
- [A library installs a `SIGTERM` handler] → `kill()` after one second.
- [A library that is slow only once stays failed until a file change or restart] → the timeout message says how to raise the limit; a user-triggered retry is an Open Question.
- [A timed-out library inside a resource file no longer marks the suite's `Resource` import with "Import definition contains errors."] → it now behaves like every other load error of a nested import, which is reported in the resource file itself; accepted.
- [After a keyword-name failure, the importing documentation is the Python docstring, which can differ from what the server documents] → only while the library fails; the same text Robot Framework uses when a dynamic library returns no documentation.
- [Duplicate warning compares strings, Robot Framework converted values: `n=1` then `n=01` for an `int` argument warns in RobotCode only] → rare; suppressible.
- [Runtime-only built-ins have no value in the comparison, so `a` followed by `${OUTPUT DIR}` gets no warning, although Robot Framework warns at run time] → maintainer decision; missed warnings rather than false ones, as for unknown variables.
- [No duplicate warning when a library has non-fatal errors (for example one keyword that cannot be created)] → missed warnings rather than false ones.
- [More diagnostics on imports with failing arguments] → information severity; suppressible.
- [Cached analysis results show the new diagnostics only after the release bump] → expected (`app_version` keyed cache).

## Migration Plan

Additive; no user migration. The two new diagnostic codes can be suppressed with the existing modifiers. Timeout diagnostics keep their text and code.

## Open Questions

They come from the proposal's Open list; each has a recommended default that needs no change to the specs above:

- **Duplicate loads without arguments** (signature help, inlay hints, semantic analyzer reload with `()` when an import's `LibraryDoc` has errors). Recommended: for libraries, show the inits of the import's own `LibraryDoc` (after D3 a keyword-name failure keeps them, after the fallback they are those of the load without arguments) and never load the library again with `()`, also when it has no inits (when the import's arguments could not be used, the loader has already tried `()`; for an import without arguments, `()` is the same entry); keep the reload for variable files, where it is the only attempt without arguments.
- **Processes the library started itself.** Recommended: out of scope; end only the worker. Ending a process tree portably needs platform-specific code or a dependency such as `psutil`, which RobotCode does not have.
- **Failed variable-file loads on disk.** Recommended: align with libraries — set `has_errors` for variable-file results with errors and do not serve them from the disk cache.
- **Import-name completion** (shared `self.executor`, `.result(5)` without ending the worker). Recommended: not part of this change; it lists module and file names on the Python path instead of loading a library.
- **User-triggered retry.** Recommended: none in this change; a file change or a language server restart retries; the proposed "Reload library" action of `library-keyword-set-declaration` covers it if confirmed there.
