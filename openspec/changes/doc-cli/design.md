# Design: doc-cli

## Context

See proposal.md. Verified facts that shape the design (RF 5.0.1, 6.1.1, 7.0.1, 7.3.2, 7.4.2 and 7.5 in the hatch environments):

- **Libdoc's own model and output.** `robot.libdocpkg.model.LibraryDoc._process_keywords` returns `sorted(kws)`; `KeywordDoc._sort_key` and `TypeDoc._sort_key` are `name.lower()` on every version checked. The HTML writer calls `to_json(include_private=False)` (6.1, 7.5), so private keywords are not in Libdoc's HTML. `LibraryDocBuilder._get_initializers` documents the initializer only when it takes arguments (`lib.init.args` on 7.5, `maxargs` on 5.0). RF 7.5's `LibdocMarkdownWriter` (`libdocpkg/markdownformatter.py`) writes `# <Name>`, `* Version:`/`* Scope:`, `## Introduction` with the documentation as written, `## Importing`, `## Keywords`, `### <Keyword>` with `#### Arguments`/`Returns`/`Raises`/`Tags`/`Documentation`, no data types; its docstring says the result is proper Markdown only for Markdown-documented libraries, and `Collections`' output keeps `%TOC%` and has its introduction sections as `#` headings. On RF ≤ 7.4 `libdoc X show` prints raw Robot markup wrapped at 78 characters (`consoleviewer._wrap`). Libdoc's table of contents for Robot-format documentation lists the `= X =` sections plus `Importing`/`Keywords` on RF 6.1 (`LibraryDoc._create_toc`) and the `=` sections with their `==` subsections on RF 7.5 (`DocToHtml._get_toc`, which skips a `==` heading before the first `=` section — the standard libraries on RF ≤ 7.4 start with `== Table of contents ==`); for Markdown documentation RF 7.5 uses Python-Markdown's TOC extension with two levels. Libdoc's HTML resolves backtick names (Robot, text, HTML, reST formats) and `[Name]` references (Markdown) against keywords, types (`#type-<Name>`), introduction headings and the fixed targets `introduction`, `library introduction`, `importing`, `library importing`, `keywords`; keyword element ids are the raw names. Libdoc's `DocumentationBuilder` treats a `.robot` file as a suite file (documented with its keywords since RF 6.0; RF 5.0 rejects it). RF 5.0/6.1 cannot read a JSON or XML spec written by RF 7.5 (`KeyError: 'types'`, "Invalid spec file version '7'").
- **RobotCode's documentation model and rendering.** `LibraryDoc.to_markdown(only_doc=False)` (`library_doc.py`) is called only by the REPL's `.doc` (`console_interpreter.py`) and the unreachable `type=md` branch of `http_server.py`; hover, completion, signature help and the tree view use the `only_doc=True` default or `KeywordDoc.to_markdown`. Its output for `Collections` has the heading defects listed in proposal.md, and its keyword order follows `LibraryDoc.keywords`, which differs between two runs with different `PYTHONHASHSEED` (RF 6.1 and 7.5); `LibraryDoc.types` comes from a set as well. `_get_toc_sections` has a `TODO` for data types. `MarkDownFormatter` (`utils/markdownformatter.py`) escapes every `#` to `\#` before converting links (`LineFormatter._quote_hash`), so `[http://x/y.html#frag|docs]` becomes `[docs](http://x/y.html\#frag)`, and `TableFormatter` splits Robot cells on ` | ` only, so `| x | (Foo|Bar) |` keeps an unescaped `|` (BuiltIn `Should Match Regexp`, String `Replace String Using Regexp` on RF 6.1). `get_library_doc_from_library` stores `str(lib.scope)`, which is `GLOBAL` on RF 5.0–6.1 and `Scope.GLOBAL` on RF ≥ 7.0 (the library hover shows the latter; Libdoc's own builder uses `str(lib.scope)` on 6.1 and `lib.scope.name` on 7.5). The Markdown-documented standard libraries of RF 7.5 define links to each other as reference definitions in their introductions (`Collections`: `[BuiltIn]: https://robotframework.org/robotframework/latest/libraries/BuiltIn.html`), which `get_reference_targets` returns as link targets. `markdown_docs.slugify` only lower-cases and replaces spaces; `render_toc`, `anchor_link_resolver` and the REPL viewer's anchor map use it, `LibraryDoc._link_inline_links`/`_create_toc` inline the same rule (`_link_inline_links` writes its targets as `(\#slug)`: 319 of the 328 escaped link targets of BuiltIn's full rendering on RF 6.1, the other 9 come from `MarkDownFormatter`). `test_markdown_docs.py` and `test_doc_viewer.py` assert the current rule on `Library *BuiltIn*` (`library-*builtin*`). Section titles with punctuation or code occur in standard libraries: DateTime's `` `TODAY` and `NOW` ``, `` `date` object`` and `` `datetime` object`` on RF 7.5, and OperatingSystem's `pathlib.Path` support section (written as code) on RF 6.1 and 7.5. `KeywordDoc._get_argument_list`/`_format_description` already render the Libdoc-style argument list with descriptions (`rf75-argument-docs` D3); `ArgumentInfo.type_docs` maps used type names to `TypeDoc` names on RF ≥ 6.1; `TypeDoc` has `usages`, `members`, `items`, `accepts`.
- **Resolution.** An `ImportsManager` needs a `DocumentsCacheHelper` (`robot/diagnostics/document_cache_helper.py`) with a `Workspace` whose documents manager can read Robot files. The helper's constructor takes the workspace, its `DocumentsManager`, a file watcher manager, the combined profile and a `WorkspaceAnalysisConfig`; `get_imports_manager_for_workspace_folder(folder)` creates one `ImportsManager` per folder (`create_imports_manager`: variables, variable files and environment of the profile, `ignored-libraries`, `ignored-variables`, `ignore-arguments-for-library`, the global library search order, `load-library-timeout`, the folder's cache directory). `analyze code` builds all of this through `CodeAnalyzer` (a `Workspace` with one `WorkspaceFolder` for the root, `code_analyzer.py:47`) → `RobotFrameworkLanguageProvider`, which puts the profile's `python-path` on `sys.path` (`_update_python_path`: relative entries joined to the workspace root, glob-expanded, directories not yet on `sys.path` inserted at the front), registers a reader for Robot files on the documents manager's `on_read_document_text` (`robot.utils.FileReader`; without a reader `DocumentsManager.read_document_text` raises `FileNotFoundError`) and creates the `DocumentsCacheHelper` with a `FileWatcherManagerDummy`, from `robot.toml` loaded with `extra_tools={"robotcode-analyze": AnalyzeConfig}` and `AnalyzeConfig.to_workspace_analysis_config()`. Apart from `CodeAnalyzer`, the language provider and `AnalyzeConfig`, every piece of this setup lives in `robotcode-robot` or `robotcode-core`. `analyze code` and `analyze dump-model` merge `-v/-V/-P` into the combined profile with the same code in their function bodies (`code()` in `analyze/code/cli.py`, `dump_model()` in `analyze/dump_model.py`). `analyze-config-in-robot` moves the analysis part of the model — the base class `AnalyzeConfig` with `to_workspace_analysis_config()`, without the `code` table of `analyze code` — to `robotcode.robot.config.analyze_config`, lets `load_robot_config_from_path` read `[tool.robotcode-analyze]` with it as a built-in section (`BUILTIN_TOOL_CONFIG_CLASSES` in `loader.py`), adds `get_analyze_config(robot_config)`, which returns the section or its defaults, and replaces the duplicated merging with `merge_variable_and_path_options(profile, *, variable, variablefile, pythonpath)` in `robotcode.robot.config.utils`. Prototypes outside the repo built this setup for a project with `python-path = ["lib"]`, `[variables] MODE = "b"` and `load-library-timeout = 7` — once with a hand-built `Workspace` + `DocumentsCacheHelper`, once through a `CodeAnalyzer` for the root folder and its `RobotFrameworkLanguageProvider.document_cache.get_imports_manager_for_workspace_folder(...)`: the `ImportsManager` had timeout 7, `get_libdoc_for_library_import("ArgLib", ("${MODE}",), root)` returned the dynamic keyword `Kw B` (the library returns `Kw b`) on RF 5.0 and 7.5 and `Kw C` with `MODE = "c"` in the profile and an empty cache, and `get_resource_doc_for_resource_import` documented a `.resource` and a `.robot` suite file (with a test case) with their keywords on RF 5.0 and 7.5. A further prototype of D7 read the section with a copy of the planned base class, standing in for the built-in section, and merged `-v` like `merge_variable_and_path_options`; on RF 5.0.1 and 7.5, with a `robot.toml` that also has a `[tool.robotcode-analyze.code]` table: timeout 7, `Kw B`, `Kw A` (the default of the library's `mode` argument) with `[tool.robotcode-analyze.cache] ignore-arguments-for-library = ["ArgLib"]`, `Kw C` with `-v MODE:c` and an empty cache, and no `robotcode.analyze` module in `sys.modules`. Loading runs in a spawned process, so a script that drives it needs a `__main__` guard (the `robotcode` entry point has one). The library disk cache is read by `LibraryMetaData.cache_key` (module name or path) regardless of the import arguments; the library meta has no configuration fingerprint. `robotcode-runner` depends on `robotcode-robot` and `robotcode-plugin`; `robotcode-repl` depends on `robotcode-runner` and `prompt_toolkit` and already imports `robotcode.runner.cli.*`; neither depends on `robotcode-analyze`.
- **CLI conventions.** Commands that print human-readable text call `app.echo_as_markdown` (rich on a coloured TTY, raw Markdown otherwise, pager per `--pager/--no-pager`); structured output goes through `app.print_data` for the global `--format json|json-indent|toml`. AI-agent sessions (`is_running_in_ai_agent`) default to no colour and no pager, while explicit `--color`/`--pager` options keep their precedence (`src/robotcode/cli/__init__.py`); the REPL additionally falls back to its plain backend there and when stdin is no TTY, unless `--backend`/`--plain` is given explicitly (`repl/cli.py` `_resolve_backend`). The global `--format` is ignored by `robotcode libdoc` and `robotcode repl`. `discover`'s and `results`' Markdown renderers write entity names bold (`- **<name>**`). `results`/`discover` share `--search`/`--search-regex` via `runner/cli/_search.py` (`make_search_matcher`: case-insensitive substring or regex, tags normalised with `normalize(..., ignore="_")`, mutual exclusion). `analyze dump-model` uses `-o/--output FILE`; `analyze code` has `-v/--variable`, `-V/--variablefile`, `-P/--pythonpath`. `docs/03_reference/cli.md` has a hand-written package overview and a generated command reference between `<!-- START -->`/`<!-- END -->` (`hatch run create-cmd-line-docs`).
- **REPL viewer.** `DocViewer` (`repl/_pt/doc_viewer.py`) is one full-screen prompt_toolkit `Application` (frame, body window, search bar, footer) with application-level key bindings; it renders Markdown with rich, follows `#anchor` links through an anchor map built from `iter_headings` + `slugify`, opens `http(s)` links in the browser, hands other targets to a `link_resolver`, and keeps a back/forward stack. Tests in `tests/robotcode/repl/test_doc_viewer.py` exercise its helpers and its application without a terminal.

## Goals / Non-Goals

**Goals:**
- One Markdown form of a library's documentation that is valid Markdown, reproducible, navigable by stable anchors and built by the same rules on RF 5.0–7.5, produced by one renderer that the CLI, its browser and the later VS Code browser share.
- A command that shows exactly what the analysis sees for an explicitly named library or resource, for people (browser), pipes and agents (Markdown), and website generators (files).

**Non-Goals:**
- Finding libraries or resources that were not named (`library-index`), variable files as targets, the VS Code browser and its LSP request (`vscode-doc-browser`).
- Changing `robotcode libdoc`, `LibraryDoc.to_markdown`, `KeywordDoc.to_markdown` or the hover (apart from the converter corrections, the scope value of D6 and, with Q1 (a), the anchors of punctuated section titles of D5).
- Converting reStructuredText or HTML documentation to real Markdown (they stay HTML blocks, as in the editors).
- Keyword sets that depend on import arguments across the disk cache (`library-keyword-set-declaration`), timeouts that do not hold and visible fallbacks (`library-loading-robustness`).

## Decisions

### D1: A separate renderer next to the documentation model

New module `packages/robot/src/robotcode/robot/diagnostics/documentation_markdown.py` with `render_documentation(doc: LibraryDoc, *, keywords: Optional[Sequence[KeywordDoc]] = None, import_args: Sequence[str] = (), project_root: Optional[Path] = None, document_links: Optional[Mapping[str, str]] = None) -> DocumentationMarkdown`, where `DocumentationMarkdown` holds `markdown: str` and `outline: List[OutlineEntry]` and `OutlineEntry` holds `kind` (`document`, `section`, `init`, `keyword`, `type`), `name`, `level` and `anchor`; plus `short_doc(keyword: KeywordDoc) -> str` and `find_entry(outline, kind, name) -> Optional[OutlineEntry]` (keywords matched with `normalize(name, ignore="_")`, sections and types case- and space-insensitively). Each parameter has a caller in this change: `keywords` for `-k` (D8), `import_args` for the metadata, `project_root` for the source entry (D6), `document_links` for directory output (D9). It lives in `robotcode-robot` because the CLI, the REPL and the language server (`vscode-doc-browser`) all depend on that package. It reuses the existing converters and `KeywordDoc._format_description`, but not `LibraryDoc.to_markdown`, whose heading scheme is shared with the hover; argument lines follow the form of `KeywordDoc._get_argument_list` but are written by the renderer, since that helper marks kinds with the hover's symbols and does not link types (D2). The old full mode stays for its two callers until Q4 is decided. `init` is the kind of the `Importing` heading so that the outline kinds equal the anchor kinds planned for the editor target payload (`keyword|section|type|init`).

Rejected: fixing `LibraryDoc.to_markdown(only_doc=False)` in place — it shares `header_level`, `_link_inline_links` and the `Library *Name*` title with the hover and the tree view, so a new structure there either changes those surfaces or adds a mode flag to a method with many callers; a Jinja-style template — no template engine is a dependency today.

### D2: Structure modeled on Libdoc's Markdown output, parts as labelled blocks

The skeleton follows RF 7.5's `LibdocMarkdownWriter` (same problem, same audience): title, metadata list, `## Introduction`, `## Importing`, `## Keywords` with `### <Keyword>`, and adds `## Data types` with `### <Type>` (Libdoc's HTML has that section). Inside an entry the parts are bold-labelled blocks in Libdoc's order, not `####` headings: under GitHub's anchor rules repeated headings get numbered anchors (`arguments`, `arguments-1`, …), and every such heading would be an outline entry in the browser sidebar and in site generators' page outlines. Example (library `MyLib` inside the project, RF 7.5, Q1 default):

```markdown
# MyLib

- **Type**: Library
- **Version**: 1.0
- **Scope**: TEST
- **Source**: `lib/MyLib.py`
- **Import arguments**: `mode=b`

## Introduction

My library. See [Do Thing](#do-thing).

### Section One

…

## Importing

**Arguments**:
- `mode` = `a` — The mode.

Initializer documentation.

## Keywords

### Do Thing

**Arguments**:
- `value`: [`int`](#integer) — The value.
- `*items`: `str`
- `flag`: [`bool`](#boolean) = `False` *(named-only)*

**Returns**: `str` — The result.

**Raises**:
- `ValueError` — If the value is negative.

**Tags**: `alpha`, `beta`

Does the thing …

## Data types

### boolean

**Kind**: Standard

Strings `TRUE`, `YES`, … are converted to `True`, …

**Converted types**: `string`, `integer`, `float`, `None`

**Used by**: [Do Thing](#do-thing)
```

Argument entries use the existing list form (`_get_argument_list`: name with `*`/`**`, types joined by ` | `, `=` default, `—` description with indented continuation lines); named-only and positional-only are marked with Libdoc's words in italics instead of the hover's `🏷`/`⟶` prefixes. Without a description the entry ends after the default; there is never an argument table. Resources get `Type`/`Source` only. Level-1/level-2 headings are written by the renderer only; headings inside documentation texts are shifted below their entry (D4).

### D3: Order, private keywords, initializer, reproducibility

Keywords and types are sorted with `key=lambda x: x.name.lower()` (Libdoc's `_sort_key`); `sorted` is stable, so the output no longer depends on the hash seed. Keywords with `is_private` are skipped everywhere (entries, outline, `--list`, `--search`), as in Libdoc's HTML; `is_private` is already `False` on RF < 6.0. `## Importing` appears when an initializer has arguments (RobotCode's existing condition, equal to Libdoc's) or when the document has load errors (D6). Keyword entries of resources keep no source line in the Markdown.

### D4: One conversion path for every format

Per text: Robot format → `MarkDownFormatter`; Markdown → `normalize_markdown_doc` (heading shift, admonitions, reference links); reST → `convert_from_rest`; other formats unchanged — the same calls `KeywordDoc.to_markdown` and `TypeDoc.to_markdown` make. Headings of the converted text are then moved with `shift_headings` so the introduction starts at `###` and keyword/initializer/type documentation at `####` (capped at `######`). `%TOC%` in Robot-format and Markdown documentation becomes a two-level list of the introduction's `###` sections with their `####` subsections, where a subsection before the first section is left out — RF 7.5's `_get_toc` rule for the Robot format, applied on every version and to both formats, so `BuiltIn` and `Collections` on RF ≤ 7.4 get no `Table of contents` entry — followed by the document's `Importing`/`Keywords`/`Data types` entries (RobotCode's existing TOC entries plus the data types of the `TODO`). References are resolved against the document's own targets — `LibraryDoc.get_reference_targets()` (keywords, used type names, Libdoc's fixed names, Markdown introduction headings and reference definitions) plus the introduction headings of the other formats: `[Name]`/`[Name][]`/`[text][Name]` in Markdown texts through the existing `resolve_reference_links`, and inline-code spans `` `Name` `` in Robot-format and plain-text documentation through a new `resolve_backtick_links` in `markdown_docs.py` (outside fenced code, like the other helpers; Libdoc does not link backticks in Markdown documentation, so neither does this). Precedence: a keyword, type or section of the document itself; then, in directory output, another document of the same call, which resolves to that document's file (D9) — before the introduction's reference definitions, so that `[BuiltIn]` in `Collections` on RF 7.5 links to the written `BuiltIn.md` instead of robotframework.org's latest version (Context); then the reference definitions; everything else stays as it is. Argument and return types link to their `Data types` entry through `ArgumentInfo.type_docs` / `KeywordDoc.return_type_docs` (RF ≥ 6.1; nothing to link below). In a `-k` selection, references to entries that are not part of the output are rendered as inline code, so every link keeps a target.

The two converter defects are fixed where they arise, for every surface: `TableFormatter._format_cell` escapes the `|` characters left in a cell after its inline formatting (so a `[url|text]` link inside a cell still converts), and `LinkFormatter` writes link targets with `#` instead of `\#` (link texts keep today's escaping). The `(\#slug)` targets of `LibraryDoc._link_inline_links` are not converter output and stay as they are; the canonical renderer does not use that method. A flag to limit this to the new renderer would be a parameter on a shared class for one call site; the change is visible in hover only for documentation with such tables or links and is captured by the `keyword-documentation-rendering` delta.

### D5: Anchors from the final heading sequence, outline, semantic navigation

The renderer first converts all texts and assembles the document with placeholders for links and the TOC, then walks the final ATX headings in document order (`iter_headings`) and assigns anchors with a stateful `Slugger` in `markdown_docs.py` that applies the rule of Q1 and numbers repeated slugs in document order; then it inserts the TOC and resolves the placeholders. Because the anchors come from the heading sequence alone, any consumer that walks the same headings with the same slugger — the REPL viewer's anchor map, GitHub — derives the same anchors. The headings of the canonical document are its ATX headings outside fenced code, as `iter_headings` reads them; a Setext heading or a heading inside raw HTML (HTML- and reStructuredText-format documentation) gets no anchor and no outline entry (Risks), so a consumer that pairs rendered headings with the outline in order (`vscode-doc-browser`) counts ATX headings only. `Data types` comes after `Keywords`, so keyword anchors never depend on type names. The outline is produced in the same walk; the browser, the REPL and later the VS Code browser navigate by `find_entry(kind, name)` and use the entry's anchor, never a slug they compute themselves. With the Q1 default, `markdown_docs.slugify` becomes the GitHub rule and `LibraryDoc._link_inline_links`/`_create_toc` use it instead of their inline copy, so hover TOC links, the REPL viewer and the canonical form agree. The golden strings of `test_library_doc_rendering.py` keep their anchors (plain titles slug identically under both rules); the `Library *BuiltIn*` expectations of `test_markdown_docs.py` and `test_doc_viewer.py` change from `library-*builtin*` to `library-builtin`, and the TOC and backtick links of the punctuated standard-library sections listed in Context change in library hovers and the REPL's `.doc` (for example `#today-and-now` instead of `` #`today`-and-`now` ``); link and anchor map change together, so the REPL keeps following them.

### D6: Metadata, scope value, load errors

The metadata list shows `Type` (`Library`/`Resource`), `Version` (if set), `Scope` (libraries), `Source` (relative to `project_root` if the file is inside it, else omitted — machine-specific paths of installed packages would make files differ between machines), `Import arguments` (as given, not resolved, so no variable value is written into files). The scope is stored as Libdoc names it: `get_library_doc_from_library` stores `lib.scope.name` on RF ≥ 7.0, where `lib.scope` is an enum, and `str(lib.scope)` below, chosen once at module import; this also changes the library hover's "Library Scope" from `Scope.GLOBAL` to `GLOBAL` on RF 7.x, and the release version bump rebuilds cached `LibraryDoc`s. `LibraryDoc.errors` are rendered at the start of `## Importing` as a list (message, then `source:line` relative to the project root when known), so a failed import still yields a document with its title.

Where the keywords come from: `library-loading-robustness` adds `LibraryDoc.loaded_without_arguments` (the keywords come from a load without arguments after the load with the import's arguments failed) and `library-keyword-set-declaration` adds `LibraryDoc.runtime_only_args` (the keywords come from other arguments, because these are only known at run time). The canonical document shows each marker as a `> **Note:**` block after the errors at the start of `## Importing`, which is then present, with the wording of that change's own message (the `LibraryLoadedWithoutArguments` diagnostic; the import hover note). This change does not depend on the two changes, so whichever is implemented later adds the note to the renderer and a scenario to "Load errors are part of the document": task 4.5 here for markers that exist when this change is implemented, task 4.3 of the marker's change otherwise.

### D7: Targets and resolution through the analysis setup

Targets are resolved through an `ImportsManager` built from `robot.toml`, as the analysis resolves imports; the prototypes (Context) confirm that this works unchanged on RF 5.0 and 7.5, one of them with a hand-built `Workspace` and `DocumentsCacheHelper` as below. The command builds that setup from `robotcode-robot` and does not use `robotcode-analyze`:

1. It loads the configuration as `analyze-config-in-robot` makes `analyze dump-model` do it: config files and root via `get_config_files` with the path targets; `robot_config = load_robot_config_from_path(*config_files, verbose_callback=app.verbose)` without `extra_tools`, since the loader reads `[tool.robotcode-analyze]` as a built-in section; `analyze_config = get_analyze_config(robot_config)` from `robotcode.robot.config.analyze_config`, the analysis part of the section or its defaults (the command needs only `to_workspace_analysis_config()`, not the `code` table of `analyze code`); `profile = robot_config.combine_profiles(*(app.config.profiles or []), verbose_callback=app.verbose, error_callback=app.error).evaluated_with_env()`; then `merge_variable_and_path_options(profile, variable=variable, variablefile=variablefile, pythonpath=pythonpath)` from `robotcode.robot.config.utils`. If `analyze-config-in-robot` decides its Q4 as (b), so that the loader does not add the built-in sections itself, the command passes `extra_tools=BUILTIN_TOOL_CONFIG_CLASSES` from `robotcode.robot.config.loader`.
2. It puts the profile's `python-path` on `sys.path` as `RobotFrameworkLanguageProvider._update_python_path` does (relative entries joined to the root, glob-expanded, directories inserted at the front).
3. It creates a `Workspace` with one `WorkspaceFolder` for the root, as `CodeAnalyzer` does, and registers a reader for Robot files (`robot.utils.FileReader`) on its documents manager's `on_read_document_text`.
4. It asks `DocumentsCacheHelper(workspace, workspace.documents, FileWatcherManagerDummy(), profile, analyze_config.to_workspace_analysis_config())` for the root folder's `ImportsManager` (`get_imports_manager_for_workspace_folder`) and analyses nothing.

`get_analyze_config` and `merge_variable_and_path_options` belong to `analyze-config-in-robot`, which also lets `analyze code` and `analyze dump-model` call the merging function, so the three commands merge `-v/-V/-P` the same way; this change only calls them. Steps 2 to 4 are a handful of calls into `robotcode-robot` and `robotcode-core` and stay in the command module.

Each target is split on `::` (Libdoc's syntax); the first part is a resource when its extension is in `ALLOWED_RESOURCE_FILE_EXTENSIONS` (so `.robot` suite files, `.json`/`.rsrc` from RF 6.1 and `.md` from RF 7.5 follow the installed version) and is then found like a `Resource` import (relative to the base directory, then on the python path); otherwise it is a library. Libraries go through `get_libdoc_for_library_import(name, args, base_dir)`, resources through `get_resource_doc_for_resource_import(path, base_dir)`, with `base_dir` = the current working directory. Consequences taken over from the analysis on purpose: `load-library-timeout`, `ignored-libraries` (kept out of the disk cache) and `ignore-arguments-for-library` apply, the analysis disk cache is read and written (one entry per library regardless of arguments, except for libraries that declare `args` once `library-keyword-set-declaration` is applied), and loading runs in the analysis' subprocess. An exception raised by the resolution (for example a resource or library path that does not exist, or, before `library-loading-robustness`, a load that timed out) becomes a document with the target's name and that error (`error_from_exception`), so the requirement "Load errors and exit code" holds for it too.

Rejected: calling `get_library_doc` directly with the profile's python path (the `robotcode libdoc` way) — it ignores `[tool.robotcode-analyze]`, the timeout and the cache, so the command could disagree with the diagnostics; Libdoc's `LibraryDocumentation` — its model is not RobotCode's `LibraryDoc`, so every consumer would need a second renderer; building the `ImportsManager` through `analyze code`'s `CodeAnalyzer` and its `RobotFrameworkLanguageProvider` — the hosting package would depend on `robotcode-analyze` for a setup whose parts are in `robotcode-robot` and `robotcode-core` (maintainer decision); a shared helper in `robotcode-robot` for steps 2 to 4 — this command would be its only caller unless the analysis' language provider were rewritten to use it.

### D8: Command, output modes and lookup options

`robotcode doc [OPTIONS] TARGET...` (name per Q2) with `-o/--output PATH`, `--tui/--no-tui` (default: auto), `-k/--keyword PATTERN` (multiple), `--list`, `--search TEXT`, `--search-regex PATTERN`, `-v/--variable`, `-V/--variablefile`, `-P/--pythonpath`; `list`/`search` are options, not subcommands, because the positional targets would otherwise compete with subcommand names (Libdoc's `libdoc X list` puts the command after the target, which does not work for several targets). Mode selection: `--list`/`--search*` → the keyword list; otherwise, if `-o` → files (D9); otherwise, if `-k` → the selected entries as Markdown; otherwise the browser when stdin and stdout are TTYs and either `--tui` is given or neither flag is given and the session is not an AI-agent session — an explicit `--tui` wins over the agent detection as explicit `--color`/`--pager` and the REPL's explicit `--backend` do, and `--tui` without a terminal is a usage error; otherwise `app.echo_as_markdown` with the documents joined by a blank line. `-k` uses `robot.utils.MultiMatcher(patterns)` (caseless, spaceless, `*`/`?`), as `libdoc … show` does, and passes the matched keywords to `render_documentation(keywords=…)`; no match in any document → error on stderr, exit 1. The list form is Markdown grouped per document — `## <Name>` then `- **<Keyword>** — <short doc>` (entities bold, as `discover`'s and `results`' Markdown renderers write them), `short_doc` being the first paragraph of the raw documentation joined into one line (Robot Framework's `getshortdoc` rule) and then converted like the rest. Search reuses `make_search_matcher` from `runner/cli/_search.py` (repl already imports runner CLI modules): `general` over name, raw documentation, argument names/types/defaults/descriptions, return and raises descriptions, `tag` over tags; matches in keyword names are wrapped in inline code with `make_md_highlighter` (`runner/cli/_markdown.py`) as `results`/`discover` do; the short documentation is not highlighted, since it already carries Markdown code spans. Load errors: printed on stderr with `app.error`, exit code 1 after all documents are produced. JSON follows Q6. Without a target the command is a usage error (exit 2); `library-index` later replaces this for a call without lookup options by the index listing (its MODIFIED requirement of `documentation-cli`).

### D9: Directory output and cross-document links

`-o PATH` is a directory when it exists as one or ends with `/` or `os.sep`; it is created if missing. File names are `<doc.name>.md`, with `-2`, `-3`, … for repeated names in target order; the mapping is computed before rendering and passed as `document_links` (normalised name → relative file name), so a `[BuiltIn]` reference or a `` `BuiltIn` `` backtick name in another document links to `BuiltIn.md` when it names no keyword, type or section of its own document, even where the introduction defines `[BuiltIn]` as a link to robotframework.org (D4). No index file is written (site generators build their own navigation); the written files are reported with `app.verbose`. Files are written with `encoding="utf-8", newline="\n"` so the same input gives byte-identical files on Windows, Linux and macOS; existing files are overwritten.

### D10: Browser — the existing viewer as a pane, a sidebar next to it

`DocViewer` is split into a pane (body window, search bar, footer, state, anchor map, link following, back/forward; key bindings scoped to the pane so they are active only when it has focus) and the existing full-screen wrapper; `DocViewer(link_resolver).run(title, markdown, scroll_to=…)` keeps its API and behaviour for `.kw`, `.help` and the keyword lists. The pane gets `jump_to(anchor)`, which pushes the back stack like an `#anchor` link, and builds its anchor map with the shared `Slugger` (D5). New `repl/_pt/doc_browser.py` composes a sidebar and the pane in one full-screen `Application`: per document (`LibraryDoc` + `DocumentationMarkdown`) the outline's introduction sections (nested by level), `Importing`, `Keywords (shown/total)` with a filter line, `Data types (n)` and `Tags` (collected from the documented keywords, with counts); Enter or a click jumps the pane to the entry's anchor, loading another document first when needed (a content follow in the pane's history); the filter narrows by case-insensitive substring, a tag entry narrows to keywords with that tag; a key toggles the sidebar (and it starts hidden below 80 columns); keys or clicks move the focus between sidebar and pane; the footer shows the keys. Rendering stays rich → ANSI → fragments as today.

## Risks / Trade-offs

- [The disk cache keeps one entry per library, so `Name::args` can show another argument set's keywords after an earlier load] → documented on the docs page; `library-keyword-set-declaration` removes it for libraries that declare `args`; listing the library in `ignored-libraries` keeps it out of the disk cache today.
- [Loading a library runs its code] → same subprocess and timeout as the analysis; `library-loading-robustness` makes the timeout hard.
- [reST/HTML documentation stays HTML inside Markdown; its headings are neither shifted nor in the outline] → same as the editors today; noted in the docs.
- [Setext headings (`Title` + `===`) in Markdown documentation are not shifted and get no outline entry] → rare in library documentation; `shift_headings` already leaves them; can be converted later.
- [GitHub-style anchors differ from other site generators' slug rules for punctuation] → the rule is documented; links inside the generated files are consistent; explicit HTML anchors stay possible later (Q1).
- [With Q1 (a) the anchors of punctuated section titles change in library hovers and the REPL's `.doc` (Context)] → TOC links, backtick links and the REPL viewer's anchor map all use `slugify`, so they change together; anchors in editor hovers are inert.
- [Several documents in one file (`-o FILE`) or one pipe share one anchor namespace: the second document's `Introduction`, `Keywords`, `Data types` and repeated type headings get numbered anchors on GitHub, while its own links still point to the unnumbered ones of the first document] → each document is correct on its own and the browser shows documents separately; directory output is the form for websites; noted on the docs page.
- [Converter corrections change hover text for affected Robot-format documentation] → only table cells with `|` and links with `#`; the rendered result in VS Code/LSP4IJ is unchanged for links and fixed for tables.
- [Library hover shows `GLOBAL` instead of `Scope.GLOBAL` on RF ≥ 7.0] → intended correction; cached documentation is rebuilt by the release bump.
- [The browser on small terminals] → sidebar starts hidden below 80 columns and can be toggled.

## Open Questions

Each question has a recommended default; tasks that depend on one are marked "if Qn …".

- **Q1 Anchor scheme.** (a) GitHub heading slugs — lower-case, characters other than letters, digits, `-`, `_` and spaces removed, spaces to `-`, repeated slugs numbered `-1`, `-2` in document order; links work on GitHub and in the REPL viewer without HTML. (b) Libdoc ids — raw keyword name, `type-<Name>`, `Introduction`/`Importing`/`Keywords`/`Data types` — only reachable through explicit `<a id>` HTML before each heading, and ids with spaces are not valid HTML ids. (c) Keep RobotCode's current slug (lower-case, spaces to `-`, punctuation kept) — not what any Markdown host generates. **Recommended: (a)**, with `markdown_docs.slugify` switched to it (D5; this also changes the anchors of punctuated section titles in library hovers and the REPL's `.doc`, see Risks). In-app navigation is by kind and name in every variant.
- **Q2 Command name.** **Recommended: `robotcode doc`** (short, next to `libdoc`/`testdoc`); alternatives `robotcode docs`, `robotcode keywords`. Only the command name, the docs page and the skill recipes change with it.
- **Q3 Hosting package.** In every variant the configuration model and the `ImportsManager` setup come from `robotcode-robot` (D7, `analyze-config-in-robot`), so no variant adds a dependency on `robotcode-analyze`. (a) `robotcode-repl` hosts the command without a new dependency; the browser, `DocViewer`, `_search.py` and `_markdown.py` are all reachable. (b) `robotcode-analyze` hosts it and imports the browser from `robotcode-repl` only when installed (plain Markdown otherwise); it cannot import `robotcode-runner`, so `make_search_matcher` and `make_md_highlighter` would move to a lower package or be duplicated; agents would need only `analyze`, but the command uses nothing of `robotcode-analyze`, so that package would host it only for its installation footprint. (c) `robotcode-runner` hosts it, `prompt_toolkit` and the viewer move from repl to runner (the lowest common package of both users); runner needs no other new dependency, but CI installations of runner get a terminal UI library. **Recommended: (a).** The tasks assume (a); with (b) or (c) task group 5 moves accordingly.
- **Q4 REPL `.doc` and hover.** **Recommended:** `.doc` (REPL and `robot-debug`) renders the canonical documentation of the session's library or resource and opens the browser on the prompt_toolkit backend (the plain backend pages the canonical Markdown); `.kw` and the hover keep their compact rendering. If confirmed, `documentation-cli` gets a requirement "REPL `.doc` shows the canonical documentation in the browser" and `docs/03_reference/repl.md` is updated; `LibraryDoc.to_markdown(only_doc=False)` then has only the unused HTTP Markdown branch left (neither this change nor `vscode-doc-browser`, whose Non-Goals exclude it, removes that branch). The requirement "Existing documentation surfaces keep their rendering" of `library-documentation-markdown` encodes the recommended default for the hover and `.kw`; if the hover is to switch as well, that requirement is replaced by one that names the hover as a consumer of the canonical form.
- **Q5 Libdoc spec files as targets.** **Recommended: not in this change.** RobotCode's `LibraryDoc` has no reader for them, Libdoc's reader returns its own model, `.json` is also a resource extension from RF 6.1, and RF 5.0/6.1 cannot read RF 7.5 specs.
- **Q6 JSON output.** **Recommended:** support the global `--format json|json-indent|toml` via `app.print_data` with `{"documents": [{name, type, version, scope, source, import_args, markdown, outline}]}` and, for `--list`/`--search`, `{"keywords": [{document, name, anchor, short_doc, arguments, tags}]}` — cheap given D1, not a replacement for Libdoc's JSON spec. If not confirmed, the command ignores the global `--format` as `robotcode libdoc` and `robotcode repl` do (no code). If confirmed, `documentation-cli` gets a requirement for it. The same answer decides `library-index` Q5 (the index listing as JSON) and the payload question of `vscode-doc-browser` (whose response embeds the same `OutlineEntry` objects).
- **Q7 Repeatable `--arg`.** **Recommended: not in this change.** Targets are split on `::` before variables are resolved (D7), so an argument containing `::` (an IPv6 URI) can be passed through a variable: `robotcode doc -v 'HOST:[::1]:8270' 'Remote::http://${HOST}'`; `--arg` would also be ambiguous with several targets.
- **Q8 `docs/03_reference/ai-agents.md`.** It names `libdoc` as the lookup the plugin teaches. **Recommended: leave it unchanged** (AI features are not to be surfaced further in user docs until the AI rework lands); update the sentence together with that rework.
