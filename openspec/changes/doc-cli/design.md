# Design: doc-cli

## Context

See proposal.md for the motivation and specs/ for the behaviour. Verified facts that shape the approach (probes on RF 5.0, 6.1, 7.0 and 7.5 in the hatch environments where a version is named):

- **Full page today.** `LibraryDoc.to_markdown(only_doc=False)` (`packages/robot/src/robotcode/robot/diagnostics/library_doc.py:1646-1713`, importing and keywords in `_get_doc_for_keywords` `:1741-1780`) has two callers. One is the REPL's `.doc` (`packages/repl/src/robotcode/repl/console_interpreter.py:1249`, `header_level=1`). The other is the `type=md` branch of the documentation server (`packages/language_server/src/robotcode/language_server/robotframework/parts/http_server.py:76-86`, `header_level=0`), which no client requests. Keyword entries come from `KeywordDoc.to_markdown(add_type=False)`, and only this branch uses `add_type=False`. Its keyword heading sits at the level of the library title (`_get_signature`, `:1121`).
- **Defects of the page.** The keyword order follows `KeywordStore.values()`, which returns a set (`:1375-1376`). `LibraryDoc.types` is built from a set (`:2792-2811`). Separators are appended without a blank line; on RF 7.5, whose standard libraries are documented in Markdown, dozens of paragraphs of the BuiltIn page become setext headings. `_get_toc_sections` has a TODO for data types (`:1786-1796`). With `add_signature=True`, the initializer is also rendered before the title. Private keywords are included.
- **Scope.** `get_library_doc_from_library` stores `str(lib.scope)` (`:2585`). That is `GLOBAL` or `TEST` on RF 5.0 and 6.1, but `Scope.GLOBAL` or `Scope.TEST` on RF 7.5, where Libdoc itself uses `lib.scope.name`.
- **Anchors.** `markdown_docs.slugify` (`packages/robot/src/robotcode/robot/utils/markdown_docs.py:60-62`) only lower-cases and replaces spaces. `anchor_link_resolver`, `render_toc` and the REPL viewer's anchor map (`packages/repl/src/robotcode/repl/_pt/doc_viewer.py:216-255`) use it. `LibraryDoc._create_toc` (`:1798-1802`) and `_link_inline_links` (`:1731-1739`) inline the same rule, and `_link_inline_links` writes its targets as `(\#slug)`. The RF 7.5 DateTime hover links its section `` `TODAY` and `NOW` `` to ``#`today`-and-`now` ``. VS Code's Markdown language service (`vscode-markdown-languageservice`, `src/slugify.ts`) copies github-slugger's rule and numbers repeated slugs `-1`, `-2`.
- **Type references and backtick names.** On RF 6.1 and newer, where libraries have type documentation, a Markdown reference `[Color]` reaches the link resolver as a type. `anchor_link_resolver` returns no link for it, so the page shows `` `Color` ``; on RF 7.5 this happens to the `[Secret]` references in the argument descriptions of `OperatingSystem` (verified). The heading of a type reads `Color (Enum)` (`TypeDoc.to_markdown`, `library_doc.py:417`). `MarkDownFormatter` turns Robot-format names in single backticks and code in double backticks into the same code span (`markdownformatter.py:247-248`). `KeywordDoc` writes argument names, argument types and the return type as code spans directly, not through the resolver (`:1093-1095`, `:1110-1112`, `:1158`). `_link_inline_links` runs over the whole assembled page of a library not documented in Markdown (`:1709-1713`). It links every code span whose text equals a heading of level 2 or deeper, whatever the span came from. On RF 6.1 and 7.4, it links the `XML` arguments `text`, `tail` and `tag` and the code ``` ``text`` ``` and ``` ``tail`` ``` to the introduction's sections of these names. In `BuiltIn` it links the argument `repr`, the code ``` ``str`` ``` and, on RF 7.4, the argument type `str` of 100 argument rows to the sections `repr` and `str`. With keyword headings at level 2, as in the REPL's `.doc` today, it also links ``` ``Run Keyword If`` ``` to that keyword (verified). A type's heading has no such text, so `` `Color` `` stays code. Libdoc's HTML links names in single backticks to the default sections, keywords, types and the `= … =` headings of a Robot-format introduction (RF 7.5 `robot/libdocpkg/htmlutils.py:58-91`, `:210-218`; the same targets on RF 5.0 and 6.1). It does so only after `html_format` has turned double-backtick code into `<code>` (`:135-141`), so it links neither such code nor argument names. On RF 7.4, 37 argument rows of the `XML` page name the argument `source`, whose reference target is the type `Source`, and its documentation writes ``` ``source`` ```; `String`, `Collections` and `DateTime` have arguments `string`, `dictionary`, `list` and `date` with such targets (verified).
- **Converter.** `LineFormatter` escapes every `#` before links are converted (`packages/robot/src/robotcode/robot/utils/markdownformatter.py:220-227`, `:238-239`). So the RF 6.1 BuiltIn hover contains `[eval](http://docs.python.org/library/functions.html\#eval)`, and through `_link_inline_links` also `[str](\#str)`. `TableFormatter._format_cell` (`:347-351`) leaves a `|` inside a cell, so the `Should Match Regexp` example row with `(Foo|Bar)` has more cells than its header on RF 6.1.
- **Live loading of libraries.** `get_library_doc(name, args, working_dir, base_dir, command_line_variables)` (`library_doc.py:2417-2546`) imports in-process. It calls `os.chdir(working_dir)`, uses `base_dir` for `${CURDIR}` and relative paths, and resolves variables in the name and the arguments.
- **Failed initialisation.** When initialising with the arguments fails, `get_library_doc` retries without them (`:2523-2533`) and returns those keywords together with the error; `library-loading-robustness` marks this case with `LibraryDoc.loaded_without_arguments`. When no instance exists at all (the import failed, or the initialisation failed and no retry succeeded), the document has no initializer entry, because `inits` is built only from an instance (`:2598-2682`). Checked on RF 5.0, 6.1 and 7.5 with an unknown library and with a library whose required argument is missing. A keyword that cannot be created leaves the initializer and the other keywords in place and adds "Adding keyword … failed" to `errors`.
- **Resources and suite files.** `get_library_doc` cannot load resource files. `ResourceFileBuilder(process_curdir=False).build(path)` plus `get_resource_doc_from_resource` (`:3780-3805`) documents `.resource` files on RF 5.0–7.5, and Markdown resources on RF 7.5, which Libdoc rejects. On every version it rejects suite files ("Resource file with 'Test Cases' section is invalid.", or `'Tasks'`). `TestSuiteBuilder(process_curdir=False).build(path)` builds them, and `get_resource_doc_from_resource(suite.resource, path)` documents their keywords. That document is named after the file on RF 5.0 to 6.1 (`login`) and has no name on RF 7, while `suite.name` is `Login` (verified on RF 5.0, 6.0, 6.1, 7.0 and 7.5 with a Test Cases file and a Tasks file). Libdoc documents suite files since RF 6.0, with `suite.name` and the type `SUITE` (RF 7.5 `robot/libdocpkg/robotbuilder.py:153-167`); RF 5.0's Libdoc rejects them. For a file that is not a `.resource` file, Libdoc tries the suite builder first and reports the resource builder's error when both fail (RF 7.5 `robot/libdocpkg/builder.py:80-113`). `find_file` (`:3160-3177`) resolves variables in a path and searches the base directory first, then `sys.path`.
- **Initialization files.** Libdoc treats only `__init__.robot` as one: it builds the file's directory as a suite (RF 7.5 `robot/libdocpkg/robotbuilder.py:158-162`), which gives the type `SUITE`, the keywords of the file and the directory's suite name (verified on RF 6.0 and 7.5; RF 5.0's Libdoc documents the resource `__init__`). Robot Framework recognises an initialization file by the name `__init__`, case ignored, with an extension it parses (RF 7.5 `robot/parsing/suitestructure.py:159-164`). It derives a suite's name from the directory with `format_name` below RF 6.1 and `TestSuite.name_from_source` from RF 6.1: a prefix up to `__` is removed, underscores become spaces, and an all-lower-case name is title-cased, so `Mysuite` stays `Mysuite` and `01__my_suite` becomes `My Suite`. `ResourceFileBuilder` builds an initialization file with its keywords, but reports each suite setting, such as `Suite Setup`, as not allowed in a resource file. `TestSuiteBuilder(process_curdir=False, allow_empty_suite=True)` builds it with the same keywords and without these errors, as a suite named after the file: `Init`, or `INIT` for `__INIT__.robot` (verified on RF 5.0, 6.0, 6.1, 7.0 and 7.5). A `Name` setting in the file, which exists since RF 6.1, names the suite in both Libdoc and this build (verified on RF 6.1, 7.0 and 7.5); RF 5.0 and 6.0 report "Non-existing setting 'Name'".
- **Configuration.** `run_repl` (`packages/repl/src/robotcode/repl/run.py:92-131`) builds Robot's settings from the project configuration:
  1. `handle_robot_options` (`packages/runner/src/robotcode/runner/cli/robot.py:288-332`) reads the config files and profiles, writes `env` into `os.environ` and builds the command line with `-v`, `-V` and `-P`;
  2. `RobotFrameworkEx(...).parse_arguments` and `RobotSettings` turn it into settings;
  3. `settings.pythonpath` is prepended to `sys.path`.

  A prototype outside the repository passed `GlobalVariables(settings).as_dict()` as `command_line_variables` to `get_library_doc(..., working_dir=root, base_dir=start directory)`. Profile-dependent keywords, `env` and the python path came out right, also when started from a subdirectory, on RF 5.0, 6.0, 6.1 and 7.0–7.5. `robotcode libdoc` changes into the project root first (`packages/runner/src/robotcode/runner/cli/libdoc.py:72`), so relative paths given in a subdirectory fail there.
- **Languages.** `robot` passes `settings.languages` to `TestSuiteBuilder` as `lang` (RF 7.5 `robot/run.py:476`). `RobotSettings.languages` exists since RF 6.0 and is built from `--language` (RF 7.5 `robot/conf/settings.py:552`), which the configuration chain writes for `robot.toml`'s `languages` (`packages/robot/src/robotcode/robot/config/model.py:1776-1791`). `ResourceFileBuilder` and `TestSuiteBuilder` take `lang` since RF 6.0; RF 5.0 has neither the parameter nor the setting. A resource file with `*** Einstellungen ***` and `*** Schlüsselwörter ***` and no `Language:` line gives an empty resource on RF 5.0 and 6.0 and fails on RF 6.1 to 7.5 ("Unrecognized section header '*** Einstellungen ***'"). With the languages of `RobotSettings({"language": ["de"]})` it is documented with its keywords on RF 6.0 to 7.5, and so is a suite file with `*** Testfälle ***` through `TestSuiteBuilder` (verified). Repeated `--language` options add up: `--language de --language fi` gives both, and the German file is still read on RF 6.0, 6.1 and 7.5. RF 5.0's option parser rejects `--language` with `option --language not recognized`, also when it comes from `robot.toml`'s `languages`; `robotcode robot` then exits with 252 (verified). The language server adds the setting `robotcode.robot.languages` to the languages of the profile (`packages/robot/src/robotcode/robot/diagnostics/document_cache_helper.py:160-161`), and test discovery passes it as `--language` (`vscode-client/extension/testcontrollermanager.ts:951`).
- **CLI conventions.** `app.echo_as_markdown` (`packages/plugin/src/robotcode/plugin/__init__.py:443-465`) renders with rich and a pager on a colour terminal and prints raw Markdown otherwise. In AI-agent sessions, the root CLI turns colour and pager off unless they are given explicitly (`src/robotcode/cli/__init__.py:397-405`). `app.print_data` serves the global `--format json|json-indent|toml`; plain dataclasses keep snake_case keys. For JSON, `as_json` leaves out every field that holds `None` and has a default (`packages/core/src/robotcode/core/utils/dataclasses.py:138-151`); `remove_defaults` is used only for TOML (`packages/plugin/src/robotcode/plugin/__init__.py:358-373`). The REPL falls back to its plain backend when `_is_interactive_stdin()` is false or `is_running_in_ai_agent()` is true (`packages/repl/src/robotcode/repl/cli.py:104-113`, `:131-153`).
- **Viewer and matchers.** `DocViewer(link_resolver).run(title, markdown)` (`doc_viewer.py:470-654`) runs a standalone full-screen viewer with search, `#anchor` jumps and back/forward. Libdoc's `list` matches with `MultiMatcher([f"*{p}*" …])` and its `show` with `MultiMatcher(names)` (RF 7.5 `robot/libdocpkg/consoleviewer.py`). `MultiMatcher(patterns, ignore=…)`, `RecommendationFinder(normalizer).find_and_format(…)`, `getshortdoc(doc)` and `search_variable(string)` are called the same way on RF 5.0 and 7.5.
- **Limit.** A library whose keyword names need a running execution context, for example `BuiltIn().get_variable_value` in `get_keyword_names`, fails with `RobotNotRunningError` in both `get_library_doc` and Libdoc. Only the `.doc` of the REPL and of `robot-debug`, which read the loaded instance, can show it.

## Goals / Non-Goals

**Goals:**
- One command group for people, pipes and agents. It shows what Robot Framework loads for one target with the project's configuration, generated anew on every call.
- One full page that is valid, reproducible and navigable Markdown on RF 5.0–7.5. `robotcode doc`, the REPL's `.doc` and, through the JSON output, `vscode-doc-browser` all show it.

**Non-Goals:**
- The analysis setup: `ImportsManager`, `[tool.robotcode-analyze]`, the disk cache, `load-library-timeout` (maintainer decision: live generation).
- A new renderer module, a separate terminal browser, or several targets per call.
- `robotcode doc suites/tests PATH` (like Testdoc) and `robotcode doc types TARGET`; both are possible later extensions.
- Changing `robotcode libdoc`. Its root-relative paths and the robot profile's `name` and `quiet` leaking into Libdoc are a separate fix.
- The documentation HTTP server, HTML output, and Libdoc spec files as targets.
- Changing hover, signature help, completion, the Keywords view or `.kw` beyond the converter corrections, the scope name and the anchor rule.

## Decisions

### D1: A command group in `robotcode-repl`

Maintainer decision. A new module `packages/repl/src/robotcode/repl/doc_cli.py` holds the click group `doc` with the commands `lib`, `keywords`, `keyword` and `browse`. `register_cli_commands` in `packages/repl/src/robotcode/repl/hooks.py` returns it next to `repl` and `robot-debug`. The REPL package hosts it because `browse` reuses the REPL's viewer. It already depends on `robotcode-runner` (configuration chain) and `robotcode-plugin` (output helpers), so no dependency changes.

Every command takes `TARGET`, the repeatable options `-v/--variable`, `-V/--variablefile`, `-P/--pythonpath` and `--language LANG`, and `--base-dir DIR`. `-v`, `-V` and `-P` reuse the option definitions of `SHELL_OPTIONS` in `repl/cli.py` (`:261-285`), moved into a small shared list that `SHELL_OPTIONS` and `doc_cli` both use. `--language` is defined in `doc_cli.py`, without a short form, as in `robot` (maintainer decision (2026-09-29), D2). `lib`, `keywords` and `keyword` also take `-o/--output FILE`. `keywords` takes `PATTERN…` and the repeatable `--tag TAG`; `keyword` takes one or more `NAME`s. `lib` has no alias.

### D2: Live loading with the project configuration

Maintainer decision: no `ImportsManager`, no RobotCode cache, no analysis settings. The command builds Robot's settings as `run_repl` does:

1. `-v`, `-V`, `-P` and `--language` become the robot options `--variable`, `--variablefile`, `--pythonpath` and `--language`. They follow the options of the configuration, so Robot Framework adds the languages of `--language` to those of `robot.toml` and the profiles, as the language server adds `robotcode.robot.languages` to them (maintainer decision (2026-09-29); Context). `vscode-doc-browser` passes that setting this way.
2. `handle_robot_options` loads `robot.toml` and the selected profiles, which writes `env` into `os.environ`.
3. `RobotFrameworkEx(...).parse_arguments` and `RobotSettings` give the settings, and `settings.pythonpath` is prepended to `sys.path` inside `app.save_syspath()`.
4. `GlobalVariables(settings).as_dict()` provides the variables of a run: profile and command-line variables, variable files, `${EXECDIR}`, `${OUTPUT_DIR}`.

The start directory, `--base-dir` and `-o` are made absolute before anything changes the current directory.

The target is split on `::` like Libdoc does it. If the first part has an extension from `ALLOWED_RESOURCE_FILE_EXTENSIONS`, it is a file:

- `find_file` resolves it (variables, base directory, then `sys.path`);
- `ResourceFileBuilder(process_curdir=False).build(path)` with `get_resource_doc_from_resource` documents it;
- if that raises a `DataError`, as for a suite file, `TestSuiteBuilder(process_curdir=False).build(path)` builds it, and `get_resource_doc_from_resource(suite.resource, path)` documents the suite's keywords with `suite.name` and the type `SUITE`, as Libdoc does (maintainer decision; Context). `LibraryDoc.type` is a free string (`library_doc.py:1426`); the page's title becomes `Suite *Login*`. If `TestSuiteBuilder` fails as well, the error of `ResourceFileBuilder` aborts (D3), as in Libdoc;
- a suite initialization file, named `__init__` with one of these extensions other than `.resource` and `.rsrc` (case ignored, as in Robot Framework), is documented as Libdoc documents `__init__.robot` since RF 6.0, on every RF version (maintainer decision (2026-09-29); Context): the type `SUITE`, the keywords of the file, and the suite name Robot Framework derives from its directory, `My Suite` for `01__my_suite`. It skips `ResourceFileBuilder`, which reports its suite settings as errors, and goes straight to `TestSuiteBuilder(process_curdir=False, allow_empty_suite=True).build(path)`. The build names the suite after the file (Context). Names are derived with `format_name` below RF 6.1 and `TestSuite.name_from_source` from RF 6.1, chosen once at import time, the pair that `packages/runner/src/robotcode/runner/cli/discover/discover.py:148-159` uses. When the suite's name equals the name derived from the file, the name derived from the directory replaces it. Otherwise the name comes from a `Name` setting and is kept, as in Libdoc. So `01__my_suite/__init__.robot` gives `My Suite` and `lower_dir/__INIT__.robot` gives `Lower Dir` (verified on RF 5.0, 6.1 and 7.5). If the build fails, its error aborts (D3). A directory as TARGET has no extension, so it goes through the library import like any other name (maintainer decision (2026-09-29): no special handling). With the path step below it gives Libdoc's empty library;
- on RF 6.0 and newer, both builders get `lang=settings.languages`, so the file is read in the languages of `robot.toml`, the profiles and `--language`, as `robot` reads it (maintainer decision). RF 5.0's builders have no `lang`; the call is chosen once at import time. On RF 5.0, Robot Framework's option parser already rejects a language (Context), and the command aborts (D3).

Otherwise the target is a library. A name that exists as a path, relative to the base directory, is first made absolute, with `/` turned into the platform separator, as Libdoc's `_normalize_library_path` does (RF 5.0 `robot/libdocpkg/robotbuilder.py:54-58`, RF 7.5 `:62-66`; maintainer decision (2026-09-29)). Without this step `Mysuite` and `./Mysuite` fail to import. With it a directory gives an empty library with one initializer entry and no errors, so the command prints it and exits with 0, as Libdoc does (verified on RF 5.0 and 7.5). Then `get_library_doc(name, args, working_dir=<project root>, base_dir=<base dir>, command_line_variables=<variables>)` loads it. Robot's argument resolver gives the arguments their values, so `${True}` stays a boolean. The project root is the working directory, as for `robotcode robot`, which runs there; without a project it is the start directory.

Loading happens in the command's own process, once per call. There is no cache to invalidate and no timeout: Ctrl+C stops a hanging import, and `vscode-doc-browser` cancels its child process.

Rejected: running Libdoc, the route of `robotcode libdoc`. It knows no variables and gives no RobotCode `LibraryDoc` for the page.

### D3: Failing loads abort

Maintainer decision. The command writes no documentation, reports the errors with `app.error` and exits with 1 in these cases:

- the configuration or the resolution raises: Robot Framework rejects an option, such as a language on RF 5.0, a library path or file is not found, a variable cannot be resolved, a file can be built neither as a resource file nor as a suite file, or a suite initialization file cannot be built as a suite (D2);
- the library document has no initializer entry, so no instance was created: the library could not be imported (also an unknown library name, for which `get_library_doc` returns the import error instead of raising), or the initialisation failed and no retry succeeded (Context);
- `LibraryDoc.loaded_without_arguments` is set (from `library-loading-robustness`): the keywords come from a load without the given arguments, which Libdoc would not document.

In every other case, the remaining `LibraryDoc.errors` and the errors of resource keywords are reported with `app.warning`, and the documentation is written with exit code 0. This also serves `vscode-doc-browser`, whose `executeRobotCode` accepts JSON only with exit code 0. Usage errors keep click's exit code 2.

### D4: The page is fixed in `LibraryDoc.to_markdown(only_doc=False)`

Maintainer decision: fix the existing renderer, add no new module. Only the `only_doc=False` branch changes. `KeywordDoc.to_markdown` and `TypeDoc.to_markdown` keep their output; the page calls them with other arguments. `header_level` stays the offset of all levels, and the callers pass 0; the REPL's `.doc` switches from 1.

Every caller renders the page as `to_markdown(only_doc=False, header_level=0, link_resolver=anchor_link_resolver)`. The REPL's `.doc` and the documentation server already pass the resolver (`console_interpreter.py:1249`, `http_server.py:84`), and `doc_cli.py` does the same. Without it, references in Markdown documentation such as `[Set Log Level]`, and the Robot-format names below, would become inline code instead of links to their headings (`markdown_docs.py:191-193`). References to types in documentation text link to the type's heading under `## Data types`, as in Libdoc's HTML (maintainer decision): Markdown reference links such as `[Color]` and, in Robot Framework's format, names in single backticks. Argument names, argument and return types, and Robot-format code in double backticks stay inline code, also when they equal the name of a type, a keyword or a section, as Libdoc's HTML leaves them (maintainer decision (2026-09-29); Context). That heading's anchor can carry a number (D5), so it is known only on the assembled page. `anchor_link_resolver`, which gets only a kind and a name, keeps returning no link for types; its docstring, which says types have no heading, is corrected (`markdown_docs.py:64-65`). Instead, the `only_doc=False` branch renders a page with data types twice, and the two renderings differ only in how references to types are written:

1. The first rendering gives the anchors of the level-3 headings under `## Data types` through `heading_anchors`, as for the JSON (D5).
2. The second passes a resolver that returns these anchors for types and asks the given resolver for everything else. Markdown reference links reach it through `normalize_markdown_doc`, as before, and Robot-format names as described next.

In Robot Framework's format, the page links names in single backticks itself, in place of `_link_inline_links`. The conversion of the introduction, of keyword documentation (`KeywordDoc.format_text`, D6) and of the argument, return and exception descriptions (`_format_doc_fragment`) asks the rendering's resolver for each name in single backticks that has a target in `get_reference_targets()` (`:1589-1624`): a keyword, a section or a type. This happens before `MarkDownFormatter` runs, because afterwards double-backtick code is the same code span as such a name (Context). When the resolver returns an anchor, the name is written as Robot Framework's link `[<anchor>|<name>]`, which the converter turns into `[<name>](<anchor>)`, with `#` since task 2.1. Keywords and sections get `#<slug>` from `anchor_link_resolver`, and types get the anchors of step 1. Headings (`= … =`) and preformatted text keep the name. A name that targets a type is the type's name or a name a keyword uses for it, so `` `bool` `` links to the type `boolean`, as in RF 7.5's Libdoc (`htmlutils.py:77-82`).

- `get_reference_targets()` also returns the `= … =` headings of a Robot-format introduction as sections, found with Robot Framework's `HeaderFormatter` and added last, as in Libdoc (`htmlutils.py:58-66`, `:84-91`). So far it has headings only for Markdown (`library_doc.py:1618-1622`).
- Only the page passes these targets to its keyword entries for Robot-format documentation. A `KeywordDoc` computes them itself only for Markdown (`:1023-1027`). So the hover, `doc keyword` and the REPL's `.kw`, whose prompt_toolkit resolver links keywords (`packages/repl/src/robotcode/repl/prompt_toolkit_interpreter.py:152-161`), keep inline code.
- `_link_inline_links` no longer runs on the page; the library hover and the other renderings of `LibraryDoc.to_markdown()` keep it. On the assembled page it cannot tell a name from an argument name or from double-backtick code (Context). So names in backticks in documentation in HTML, reStructuredText or plain text are not linked on the page (maintainer decision (2026-09-29): accepted, no separate link step for these formats).
- The argument types of an `Arguments:` part and the return type are not documentation text either. They stay inline code on every page, as they pass neither the resolver nor `_link_inline_links`. Linking them apart from the argument names would need extra machinery (maintainer decision: link them only if that needs none).

In the `only_doc=False` branch:

- Keyword entries use `kw.to_markdown(header_level=header_level + 2, add_type=False, …)`. That gives `### <Keyword>` with `#### Arguments:` and `#### Documentation:`, nested as in RF 7.5's Markdown writer. The initializer is rendered the same way under `## Importing` and never before the title. Data types use `TypeDoc.to_markdown(header_level=header_level + 1)` under `## Data types`.
- The introduction's headings move one level down with `shift_headings`, after its table of contents is built. Headings in keyword documentation move three levels down through the existing `modify_doc_handler`.
- Keywords and types are sorted by `name.lower()`, Libdoc's sort key. Keywords with `is_private` are skipped; it is always `False` before RF 6.0.
- Every separator is written as `\n\n---\n\n`.
- The keyword index starts `## Keywords`. It is inserted once the page is assembled, with the anchors of the keyword headings (D5). `_get_toc_sections` adds `Data types`.
- A last pass, the new `markdown_docs.code_span_variables`, writes every scalar variable in text as inline code. It runs for libraries, resource files and suite files that are not documented in HTML or reStructuredText. It finds variables with Robot's `search_variable`, so `${x}[0]` and nested names stay whole. It skips fenced and indented code blocks, HTML blocks, code spans and link targets, and leaves an escaped `\${x}` alone. Code spans are used rather than `\$` escapes: the raw Markdown goes to agents and files, and an escape would be copied along with the variable. The pass runs on the page only; the hover keeps its compact rendering (maintainer decision).

The scope is stored as `lib.scope.name` on RF ≥ 7.0 and as `str(lib.scope)` below, chosen once at import time. The library hover shows the fixed value as well.

Rejected: a separate renderer, the earlier plan, which means two full-page renderings of one model. Also rejected: RF 7.5's `LibdocMarkdownWriter`, which exists only on RF 7.5 and writes the documentation unconverted.

### D5: Anchors follow GitHub

Maintainer decision: GitHub-style heading slugs. `markdown_docs.slugify` implements github-slugger's rule: lower case, characters other than letters, marks, digits, `_`, `-` and spaces removed, spaces replaced by `-`. A new `heading_anchors(markdown)` walks the ATX headings outside fenced code (`iter_headings`) and returns `(level, title, anchor)`, with repeated slugs numbered `-1`, `-2` in document order. It has four users:

- the page fills its keyword index from it;
- the page takes the anchors of its type headings from it for the type links (D4);
- `doc_cli.py` takes the keyword and type anchors for the JSON from it: the level-3 headings after `## Keywords` and after `## Data types`, in the order of the entries;
- the REPL viewer builds its anchor map from it (`_build_anchor_to_line_map`).

`_create_toc` and `_link_inline_links` call `slugify` instead of their inline copies, as `render_toc` and `anchor_link_resolver` already do, and `_link_inline_links` writes `(#slug)`. A link to a heading whose text repeats points to the first occurrence, as a plain slug does on GitHub. Type links are the exception: they point to the type's heading, with its number (D4). The rule also changes the table-of-contents links of library hovers for titles with punctuation or code (`#today-and-now` for DateTime on RF 7.5) and the links of the REPL's `.doc`, whose anchor map changes with them.

### D6: Output formats

Maintainer decision: Markdown through `app.echo_as_markdown`, `-o`, and the JSON fields.

- **Markdown:** `app.echo_as_markdown(text)`. With `-o`, the text is written with `encoding="utf-8", newline="\n"` and nothing is echoed. `-o` together with a `--format` other than `text` raises `click.UsageError`.
- **`keywords`:** the page title, then one line per selected keyword, `` - **<Name>** `<args>` — <short doc> ``, or `_(no keyword matches)_`.
- **`keyword`:** for each selected keyword, `KeywordDoc.to_markdown()`, the rendering the hover shows, so no new keyword layout is needed. The keywords are separated by `---`. Then comes `TypeDoc.to_markdown(header_level=1)` for each type that `LibraryDoc.get_types_for_argument` finds for their arguments, sorted by name. Signature help documents an argument's types the same way. As in the hover, references stay inline code, including references to the types printed below. Linking them would need the two renderings of D4 here too (maintainer decision: only if trivially consistent).
- **JSON:** plain dataclasses `LibraryDocumentation`, `KeywordSelection` (the same fields without `markdown` and `types`), `KeywordEntry` and `TypeEntry` in `doc_cli.py`, printed with `app.print_data(data)`. Their fields have no defaults and never hold `None`, so `as_json` keeps every field (Context).
  - `type` is `LibraryDoc.type`: `LIBRARY`, `RESOURCE` or `SUITE` (D2).
  - The `anchor` of a type entry is the anchor that the type links of `markdown` point to (D4). `vscode-doc-browser` gives the type headings these ids.
  - `args` is `KeywordDoc.parameter_signature()`, the form of the Keywords view and signature help, without its zero-width joiners.
  - `doc` is the keyword's documentation and `short_doc` its first paragraph (Robot's `getshortdoc`), both converted by a new public `KeywordDoc.format_text(text)`; `short_doc` is then joined into one line. `format_text` is the conversion that `KeywordDoc.to_markdown` applies to the documentation (`library_doc.py:1006-1014`), moved into a method that `to_markdown` calls: Robot format through `MarkDownFormatter`, reStructuredText through `convert_from_rest`, Markdown through `normalize_markdown_doc` with the keyword's reference targets, HTML and plain text as written. The JSON passes no link resolver, so references become inline code, as in the hover.
  - `source` is `LibraryDoc.source`, or `""` when it is unknown; `lineno` is `LibraryDoc.line_no`, which is `-1` when unknown.

### D7: Keyword selection

- **`keywords` PATTERNs:** `MultiMatcher([f"*{p}*" for p in patterns], ignore="_")` over the names. That is Libdoc's `list` with underscores ignored as well, as the maintainer asked.
- **`--tag`:** `MultiMatcher(tags, ignore="_")` against each keyword's tags. Patterns and tags apply together.
- **`keyword` NAMEs:** a keyword is selected when `MultiMatcher([name], ignore="_")` matches its name, or when `KeywordStore.iter_all(name)` returns it, which applies RobotCode's name normalisation and embedded-argument matching. Selected keywords keep the page order and appear once.
- **A name that selects nothing:** `RecommendationFinder(normalize).find_and_format(name, <keyword names>, f"No keyword matches '{name}'.")`, with RobotCode's `normalize` from `robotcode.robot.utils.match`, is written with `app.error`, and the command exits with 1 after the output of the other names.
- Private keywords are never selected, because they are not in the page.

### D8: `browse`

Maintainer decision: the REPL's viewer, no new browser. `browse` loads the target like `lib` (D2, D3). It opens the viewer when `_is_interactive_stdin()` (`repl/cli.py:104-113`) and the same check for standard output are true and `is_running_in_ai_agent()` is false. `doc_cli.py` imports the two existing checks and adds only the one for standard output. The viewer runs as `DocViewer().run(<title>, <page>)`, imported only then. Otherwise `browse` prints what `doc lib` prints (`app.echo_as_markdown`). In the viewer, `#anchor` links jump through the anchor map of D5 and `http(s)` links open the browser, so no `link_resolver` is needed. `--format` does not apply to `browse`.

`browse` shows the `lib` page. Its keyword index is the one at the start of `## Keywords`, reached through the table of contents where there is one; there is no second index at the top.

## Risks / Trade-offs

- [Loading runs the library's code in the command's process, with no timeout] → Same as Libdoc and `robotcode libdoc`. Ctrl+C stops it, and `vscode-doc-browser` cancels its child process.
- [Libraries that need a running execution context cannot be documented live] → The command aborts with the library's error. The docs page names the `.doc` of the REPL and of `robot-debug` as the way to see them.
- [An import argument that contains `::` cannot be written in TARGET] → Same as Libdoc. The target is split before variables are resolved, so such an argument can be passed through a variable (`-v 'HOST:[::1]'` with `'Remote::http://${HOST}:8270'`). The docs page shows this.
- [A page with data types is rendered twice (D4)] → One rendering of `BuiltIn` on RF 7.5 takes about 7 ms with today's renderer (measured), little next to importing the library.
- [The converter corrections, the scope name and the anchor rule change hovers] → Only Robot-format tables with `|`, links with `#`, the scope on RF ≥ 7.0 and table-of-contents links of titles with punctuation or code are affected. The `keyword-documentation-rendering` delta captures them. Cached documentation is rebuilt, because the analysis cache drops its tables when the RobotCode version changes (`packages/robot/src/robotcode/robot/diagnostics/data_cache.py:374-381`).

## Migration Plan

The command is new. The page, the hover changes listed above and the REPL's `.doc` change with the release. There is no configuration or data migration. Apply after `library-loading-robustness`, which adds `LibraryDoc.loaded_without_arguments`. `vscode-doc-browser` is applied after this change. Rollback is a revert.
