# Design: support-rf75

## Context

See proposal.md for motivation. Facts that shape the approach (all verified against the unpacked RF 7.4.2 and 7.5 sources and a full test run of RobotCode against RF 7.5 in a scratch environment):

- **Documentation pipeline.** RF 7.5 moved the splitting of `Tags:` lines and the unescaping of resource keyword docs out of `KeywordDocBuilder.build_keyword` into `KeywordImplementation.update_docs()` (`robot/running/keywordimplementation.py`), which Libdoc calls via `TestLibrary.update_docs()` / `ResourceFile.update_docs(unescape=True)`. `update_docs()` mutates the keyword objects (doc text loses all Google-style sections, `args.docs`/`return_doc`/`raises` are filled, tags merged) and is not idempotent with `unescape=True`. The parser behind it is `robot.running.docstringparser.parse_docstring(doc, name) -> DocInfo(doc, args, returns, raises, tags)`; it exists only from 7.5 on and emits a `LOGGER.warn` for the legacy layout without an empty line before `Tags:`. RobotCode builds its `KeywordDoc`s from `KeywordDocBuilder().build_keyword(...)` at three keyword sites in `packages/robot/src/robotcode/robot/diagnostics/library_doc.py` (library init ≈2328, library keywords ≈2392, resource keywords ≈3394 in `_build_resource_doc`; the two variables-file initializer sites ≈2683/≈2737 carry no tags and stay unchanged). The same functions are fed with the *live* objects of a running session by the REPL (`get_library_doc_from_library`, `get_resource_doc_from_resource`, whose contract promises to leave the objects untouched). No logger capture covers those sites today: `_std_capture` only redirects stdout/stderr around `get_library_doc`, `get_model_doc` holds `LOGGER.cache_only` only around the AST visit, and the REPL entry points have none. Observed on 7.5: docstring tags are lost (`tags=[]` where Libdoc reports them), `robot:private` via docs is no longer detected, resource docs are not unescaped, `-tag` negation is not applied, and the `Tags:` line is rendered as text.
- **Standard libraries** now declare `doc_format="MARKDOWN"` (BuiltIn, Collections, String, OperatingSystem, Process, DateTime, XML, Dialogs, Screenshot, Telnet) with Google-style `Args:` sections and Libdoc reference links (`[Set Log Level]`). RobotCode renders `MARKDOWN` docs verbatim (only `ROBOT` and `REST` are converted). Standard type docs are obtained with `TypeDoc.for_type(type_info, converters)` — 7.5 added a `doc_format` parameter; without it the type text is ROBOT markup but stored under the library's `MARKDOWN` format and rendered raw (`[https://…|int]`).
- **Type aliases.** 7.5 gives `TypeInfo` an `alias` and an `is_recursive` flag; for a recursive alias the `nested` tuple holds the raw resolved typing object, which RobotCode's `_yield_type_info` (≈2446) walks into and crashes on `.is_union`; the error is caught and the library ends up with `types == []`. RF's own `TypeDocBuilder._yield_infos` stops at `is_recursive`.
- **Return types.** `ArgumentSpec.return_type` is now always a `TypeInfo` (`TypeInfo()` when unset, falsy, `str()` is `''`; `-> None` becomes a truthy `TypeInfo("None")`). RobotCode's `is not None and is not type(None)` guards (≈2426-2431) therefore yield `''` instead of `None` for unannotated keywords on 7.5.
- **Libdoc HTML** (`get_robot_library_html_doc_str` → `convert_docs_to_html()` → `LibdocHtmlWriter`) needs the `markdown` package for Markdown-documented libraries on 7.5; without it RF raises `DataError: Markdown format requires 'markdown' module to be installed.` Reproduced for `Collections`; it affects every Markdown-documented standard library. `markdown` is not a dependency of any RobotCode package and not in `bundled_requirements.txt` (the bundle installs RobotCode's packages with `--no-deps`, so only that file feeds the VS Code extension and the IntelliJ plugin). The documentation web view already catches every exception and renders an error page with the message, so the only fix needed is the dependency.
- **`robot.toml` model.** `packages/robot/src/robotcode/robot/config/model.py` is partially generated by `scripts/generate_rf_options.py` between `# start generated code` / `# end generated code` markers from RF's `_cli_opts` dicts and USAGE texts. The generator is stale: it no longer emits the `alias="kebab-case"` kwargs (80 fields) — regenerating the schema from its output turns property names into snake_case (1816-line schema diff) — and drops the hand-added `max-error-lines = "NONE"` example; its output is not ruff-clean. `console` is a manual type override (`type_templates["console"]`) containing the never-valid `skipped`. RF 7.5 moved `ConsoleType`/`ConsoleTypeQuiet` from `RobotSettings._extra_cli_opts` to `_BaseSettings._cli_opts`, so a naive regeneration moves `console`/`quiet` into `CommonOptions`; `RebotProfile` inherits them and `robotcode rebot` (`rebot_options.add_options(profile)`) would pass a top-level `console`/`quiet` to `rebot`, which RF ≤ 7.4 rejects (`option --console not a unique prefix`). `docs/03_reference/config.md` has no script; it is produced by `robotcode config info desc` and is currently slightly behind the model (the `max-error-lines = "NONE"` example and a re-wrapped `wrapper` paragraph). `docs/public/schemas/robot.toml.json` comes from `hatch run create-json-schema`.
- **Markdown files.** RF 7.5 parses `.robot.md` suites by default, accepts `Resource    file.md` / `.markdown` (`robot.running.importer.RESOURCE_EXTENSIONS`), but Libdoc rejects Markdown resources. RobotCode's `imports_manager.RESOURCE_EXTENSIONS` and `library_doc.ALLOWED_RESOURCE_FILE_EXTENSIONS` do not contain them → "invalid resource file extension" for a valid import. `.robot.rst` resources are today only *accepted*: the raw text is tokenized as Robot syntax, so RobotCode reports a false `ResourceEmpty` warning and keyword-not-found errors; neither `analyze code`, the language server, `discover files` nor the editors treat `.robot.rst` as a suite. RF reports line numbers inside `.robot.md`/`.robot.rst` code blocks relative to the concatenated blocks, not to the file (since RF 3.1 for reST).
- **Built-in variables.** 7.5 sets `${TEST_METADATA}` (`robot/running/context.py`) and allows `[Metadata]` in tests (`TestCaseSettings.names`). RobotCode's `BUILTIN_VARIABLES` (`packages/robot/src/robotcode/robot/utils/variables.py`) lacks it (the lookup ignores the `$`/`&` identifier, so `&{SUITE_METADATA}` also serves `${SUITE_METADATA}`); test-level `[Metadata]` already lexes and analyzes without errors on 7.5 (RobotCode takes the setting list from RF) but has no test coverage. Test-data files under `data/tests/versions/` are globbed by four regression tests on every RF version, so a new file there needs baselines in every `_regtest_outputs/rf*/` directory.
- **Translations.** 7.5 renamed Fr `test_cases_header` to `Cas de test` and Fi tag settings to `Tunnisteet`, keeping the old terms accepted through the new `Language.deprecations` mechanism (no warnings before 7.6). `scripts/generate_tmlanguage.py` builds header regexes from the per-language `*_header` attributes, so a regeneration under 7.5 drops `unités de test`. The committed `syntaxes/robotframework.tmLanguage.json` is already out of sync with the generator: it was hand-edited in commit `6fad9b16` (106 lines) and lacks the Arabic headers added in RF 7.3; `syntaxes/robotframework-repl.tmLanguage.json` is a hand-maintained fork carrying its own copy of the header regexes.
- **Tests.** The RF-version-keyed regression outputs live only under `tests/robotcode/language_server/robotframework/parts/_regtest_outputs/rf<MM>/` (selected by `pytest_regtestex.py`); the hover regtests compare only the first line of the hover, so documentation-format regressions are invisible to them. Full run against 7.5 (with the `rf74` baselines copied to `rf75` beforehand): 88 failures = 87 regtest diffs consisting solely of `line:` shifts inside RF's `BuiltIn.py`/`Collections.py` (goto definition/implementation, references) + `tests/robotcode/robot/test_robot_patching.py`, which imports the private `_decorate_candidates` that 7.5 renamed. RobotCode's `variable_not_found` patch still binds on 7.5 and still pays off (7.5 removed the recommendation cost on finder misses, not on real misses).
- **Caches.** `KeywordDoc`/`ArgumentInfo` are slots dataclasses persisted by the libdoc/namespace cache; the cache directory is keyed by Python and RF version and the SQLite store by RobotCode's `app_version`, so a release bump invalidates old entries; `__setstate__` fills missing slots from defaults.
- **REPL.** The `.doc`/`.kw` commands (`packages/repl/src/robotcode/repl/console_interpreter.py`, `_pt/doc_viewer.py`) render the same `to_markdown()` output as the hover, so the Markdown-format presentation gaps (raw `Args:` sections, `%TOC%`, Libdoc reference links) show there too and are covered by the same follow-up; this change only has to keep it from failing.
- **Analyzer.** `visit_DocumentationOrMetadata` in the semantic analyzer also fires for a `Metadata` node inside a test on 7.5 and indexes its key into the suite-level metadata references; nothing consumes that index yet, so it is harmless, but a future metadata feature must distinguish suite and test scope.
- **Debugger and CLI tools (verified end to end, no code change needed).** The debugger reaches into RF internals (`EXECUTION_CONTEXTS`, `namespace.get_runner(...)`/`_kw_store`, `variables._test/_suite/_global`, `context.steps`, `LoggerApi`); of the RF modules behind them `running/namespace.py`, `variables/scopes.py`, `variables/variables.py`, `variables/evaluation.py` and `running/statusreporter.py` are unchanged in 7.5, and the changes in `context.py`, the keyword runners, `bodyrunner.py`, `output/logger.py` (lazy `_console`, `register_console_logger(console=…)`), `loggerapi.py` (upper-case `result_file` kinds) and `model/message.py` touch nothing RobotCode uses. Exercised on the same project under RF 7.4.2 and 7.5: (1) a scripted `robotcode robot-debug --plain` session (line breakpoint, `.where`, `.vars`, `.print` of scalars/lists/expressions, `.whatis`, `.list`, `.next`, `.step` into a resource keyword, `.up`/`.down`, `.return`, `.set`, keyword evaluation at the prompt, `.until`, `.source`, `.catch all`, uncaught-failure stop) — transcripts identical apart from the new `&{TEST_METADATA}` variable; (2) a test timeout and a keyword timeout expiring while stopped at a breakpoint (`TimeoutExceeded` is a `BaseException` in 7.5) — identical transcripts; (3) a scripted DAP session against `robotcode debug --tcp` (initialize/attach/configurationDone, line and conditional breakpoints, stack trace, scopes and variables, evaluate in watch/hover/repl contexts, completions, `next`/`stepIn`/`stepOut`/`continue`) — identical apart from `&{TEST_METADATA}`; (4) 7.5-only: breakpoints in a test with `[Metadata]` (`${TEST_METADATA}[Issue]` evaluates) and a run with a custom `--console` logger both work; (5) `robot`, `rebot`, `libdoc` (HTML, JSON, resource), `testdoc`, `discover all/tests/suites/tags/files/info`, `results summary/show/log/stats/diff`, `analyze code`, `config show`, `profiles list` and a piped `repl` session (keyword execution, `Import Resource`, `.imports`, `.kw`, `.doc`, `.vars`) — identical exit codes and output apart from version strings, timings and RF 7.5's own Testdoc deprecation warning, which `robotcode testdoc` passes through. Known limitation, not new: a breakpoint inside a `.robot.md` suite never hits because RF reports block-relative line numbers (same as `.robot.rst` on every version); owned by `markdown-suites` and its debugger follow-up. Exception-filter stops of the DAP debugger were verified separately with a scripted client that acknowledges the server's synced custom events (`robotEnqueued`/`robotStarted`/`robotEnded`/`robotLog` block the run for up to 15 s each until the client sends `robot/sync`, as VS Code and IntelliJ do — a client that omits it looks like a hang): the default uncaught filter and `uncaught_failed_keyword`, `failed_keyword` and `failed_suite` sent as `filterOptions` stop with reason `exception` on RF 7.4.2 and 7.5 alike. Three defects showed up, identical on both versions and therefore not part of this change (owned by `debugger-dap-e2e-tests`): the declared `failed_test` filter is rejected (`verified: false`) and never stops, filters sent as plain `filters` are ignored, and a hit-count breakpoint stops on every hit except the requested one. Note that `robot-debug` is no proxy for the DAP debugger: it has its own DAP-free debug core in `packages/repl` (covered by `tests/robotcode/repl/test_debug_*.py`, green on 7.5), while the DAP server in `packages/debugger` has no automated end-to-end test at all.
- **Verified no-ops** (no code needed): `TimeoutExceeded` as `BaseException` (all RobotCode wrappers use `except BaseException` or sit below RF's status reporter), console-logger API (`register_console_logger(**settings.console_output_config)` is key-agnostic; `robotcode robot/rebot` pass `--console` through), `ListenerFacade` refactor, tag-pattern deprecations (patterns go straight to RF), Testdoc/Telnet deprecations, deprecated `robot.utils` helpers (unused), `language:` config lexing, `_get_model`, argument resolver, output capturer, `TestSuiteBuilder` private methods patched by `discover`, and the two other RF-internal monkeypatches — the `EmbeddedArguments.from_name` cache wrapper in `library_doc.py` and `SuiteStructureBuilder._is_included` in `runner/cli/robot.py` (signatures unchanged in 7.5).

## Goals / Non-Goals

**Goals:**
- RF 7.5 in the supported matrix with green CI, and no information loss or false diagnostics compared with RF 7.4 on the features RobotCode already has.
- One documentation code path that serves fresh and live (REPL) Robot Framework objects.
- A `robot.toml` generator that can be run again, and regenerated model/schema/reference.

**Non-Goals:**
- Rendering per-argument, return and raises documentation (`rf75-argument-docs`); resolving Libdoc reference links or `%TOC%` in Markdown docs, and resolving type aliases of enums/TypedDicts to their type documentation (same follow-up).
- Test metadata in discover/results/test explorer (`rf75-test-metadata`).
- Parsing code blocks of Markdown/reST suites and resources, `.robot.md` in the editors, test-explorer navigation for them (`markdown-suites`).
- `[rebot] console`/`quiet` in `robot.toml` (`rebot-console-options`).
- Deprecation diagnostics for translated headers/settings and tag-pattern spellings (`deprecation-diagnostics`).
- Reconciling the tmLanguage template/generator with the hand-edited grammar.

## Decisions

### D1: Post-process documentation with `parse_docstring`, never with `update_docs()`

On RF ≥ 7.5 a helper in `library_doc.py` takes the libdoc `KeywordDoc` returned by `KeywordDocBuilder.build_keyword` and derives RobotCode's `doc` and `tags` from `parse_docstring(text, name)`, where `text` is the raw doc for library keywords and `unescape(raw doc)` for resource keywords (the resource file documentation is unescaped the same way). Tags are merged with `robot.model.Tags.add(info.tags, remove_negated=is_resource)`; `is_private` then follows from the merged tags as today. The documentation text becomes `info.doc` when `info.args`, `info.returns` and `info.raises` are all empty (identical to the 7.4 result); otherwise the (unescaped) original text is kept with a trailing `Tags:` line removed — the only form RF ≤ 7.4 recognised — so no content disappears before the follow-up change renders those sections, and the text still equals the 7.4 result whenever the `Tags:` section is the trailing line. The helper runs under `LOGGER.cache_only` itself, because no existing capture covers the resource site or the REPL entry points, so `parse_docstring`'s deprecation warning for a `Tags:` line without a preceding empty line never reaches the console. It is applied at the three keyword sites; `parse_docstring` is imported once at module scope under `if RF_VERSION >= (7, 5):`; on older versions the pipeline is unchanged because `KeywordDocBuilder` still does the splitting there.

Why not `update_docs()`: it mutates the keyword objects, which the REPL shares with the running session; it double-unescapes when applied twice; and its `DocValidator` failure turns a keyword into a "Creating keyword failed" entry. Why not `all_tags`: it restores tags only, not the cleaned text or the unescaping. Why not `robot.utils.split_tags_from_doc`: deprecated in 7.5 and only handles a trailing line.

### D2: Type documentation mirrors Libdoc 7.5

- `_yield_type_info` stops descending when `RF_VERSION >= (7, 5) and info.is_recursive` (same rule as `TypeDocBuilder._yield_infos`).
- `RobotTypeDoc.for_type(type_info, converters, libdoc.doc_format)` on RF ≥ 7.5, keeping the two-argument call on older versions.
- Return type extraction at the library keyword site uses truthiness of `args.return_type` (a falsy `TypeInfo()` means "unset"; `ArgumentSpec.from_robot_argument_spec` already does this), giving `None` for unannotated keywords on every version and `None` as text for `-> None` on 7.5, as RF's Libdoc does. `ArgumentInfo.types` keeps showing the alias name (matches Libdoc); resolving aliased enums/TypedDicts to their type docs for completion and signature help is left to `rf75-argument-docs`.

### D3: `markdown` becomes a hard dependency of `robotcode-robot`

`markdown` (Python-Markdown, pure Python) is added to `packages/robot/pyproject.toml` — the lowest package that calls `convert_docs_to_html()` — and to `bundled_requirements.txt` so the VS Code extension and the IntelliJ plugin bundle it. An optional extra (as for `docutils`/REST) was rejected: with 7.5 the *standard* libraries need the converter, so "show documentation" would be broken by default. The web view needs no change: it already renders any exception message on its error page.

### D4: Repair the generator and keep `console`/`quiet` in `RobotOptions`

`scripts/generate_rf_options.py`:
- emit `alias="<kebab>"` (and `alias="extend-<kebab>"`) for every field whose name contains `_`, restoring the committed shape;
- move the `max-error-lines = "NONE"` example into `TOML_EXAMPLES`, and change the tag-pattern examples there to `foo AND bar*`;
- `console` type override becomes `Union[str, Literal["verbose", "dotted", "quiet", "none"]]` (pattern of `randomize`), dropping `skipped`; a second TOML example shows a custom console;
- the `RobotExtendOptions` block is generated with `tool="robot"` (today `tool="rebot"`, so its docstrings say "option of _rebot_");
- build the option dicts explicitly: `CommonOptions` from `RobotSettings._cli_opts` minus `ConsoleType`/`ConsoleTypeQuiet`, `RobotOptions` from `RobotSettings._extra_cli_opts` plus those two. This keeps model, schema and reference structurally identical to today (only docstrings, the `console` type and the `MARKDOWN` values of the libdoc `format`/`doc_format` Literals change), so `RebotProfile` does not inherit `console`/`quiet` and `robotcode rebot` keeps working with a top-level `console` on every RF version. Note that with `Union[str, …]` the value `skipped` is no longer *listed* but, like any string, still validates and is forwarded; RF rejects it at runtime as before.

Why not let the generator follow RF and move the two options to `CommonOptions`: `RebotProfile` would inherit them and `rebot_options.add_options(profile)` would forward a top-level `console`/`quiet` to `rebot`, which RF ≤ 7.4 rejects (`option --console not a unique prefix`). Supporting `rebot --console`/`--quiet` from `robot.toml` needs a version guard in `rebot.py` and its own decisions (types, inheritance) — that is the follow-up `rebot-console-options`.

Regeneration sequence, documented in `CONTRIBUTING.md`: run the generator from the repo root with an interpreter that has RF 7.5 (`hatch run test.rf75:python scripts/generate_rf_options.py` once the matrix entry exists) → `hatch run lint:fix` → `hatch run create-json-schema` → `hatch run robotcode config info desc > docs/03_reference/config.md`. `docs/03_reference/cli.md` only changes if RobotCode's own click help changes. The schema advertises 7.5-only values (`MARKDOWN`, custom console) on every RF version — as for other version-specific options, RF reports them at runtime on older versions.

### D5: Markdown resources — nominal parity with reST, nothing more

`imports_manager.RESOURCE_EXTENSIONS` and `library_doc.ALLOWED_RESOURCE_FILE_EXTENSIONS` gain `.md`/`.markdown` under `RF_VERSION >= (7, 5)` (module-scope constants, as the existing `RF_VERSION >= (6, 1)` case). Markdown resources are excluded from the `LibraryDocumentation` HTML path with a readable error, because RF's Libdoc rejects them. `get_document_type`, the language-server language definition, `analyze code`, `discover files`, VS Code and IntelliJ file associations stay unchanged — they do not handle `.robot.rst` today either, and claiming `.robot.md` for the `robotframework` language would take Markdown editing away from users while the language server cannot yet parse the file. The resulting false `ResourceEmpty`/keyword-not-found diagnostics for Markdown resources are the same the reST path shows today and are fixed by `markdown-suites` (code-block extraction with an explicit line-number policy).

### D6: Built-in variables and test-level Metadata

`&{TEST_METADATA}` is added to `BUILTIN_VARIABLES` under `RF_VERSION >= (7, 5)`, next to `&{SUITE_METADATA}` (one entry serves both identifiers, as for the suite variable). Test-level `[Metadata]` is covered by plain, version-branched tests over inline documents and by a semantic-analyzer snapshot skipped below 7.5 — not by a file under `data/tests/versions/`, which would require new baselines in all nine `_regtest_outputs/rf*/` directories.

### D7: Grammar edited by hand, generator taught about deprecations

The test-cases header regex in `syntaxes/robotframework.tmLanguage.json` and `syntaxes/robotframework-repl.tmLanguage.json` gains `cas de test` while keeping `unités de test`; the Arabic headers (settings, variables, test cases, tasks, keywords, comments, documentation setting) missing since RF 7.3 are added to the corresponding regexes in the same edit (values taken from `robot.conf.languages.Ar`). The generator is not run (it would revert commit `6fad9b16`), but `scripts/generate_tmlanguage.py` is extended to include `Language.deprecations` keys so a future regeneration keeps deprecated terms. Reconciling template and grammar is a separate cleanup.

### D8: Matrix, baselines and tests

- `hatch.toml`: `rf75` in the `devel` and `test` matrices with `robotframework~=7.5.0`; workflow `robot-version` list; `AGENTS.md`/`CONTRIBUTING.md`/`.github` instruction files updated (env list, "45 environments", `5.0–7.5`).
- Baselines follow the established procedure for a new RF version: copy the previous version's directory (`_regtest_outputs/rf74/` → `rf75/`) as the starting point, run `hatch run test.rf75:test` against it so that every behavioural difference shows up as a regtest failure with a diff, review those diffs — the expected ones are `line:` shifts inside RF's own sources (goto definition/implementation, references; observed: exactly 87 such diffs against 7.5 before any code change), anything else is either a real regression to fix first or an intended change to understand — and only then accept them with `hatch run test.rf75:test-reset tests/robotcode/language_server/robotframework/parts`. This runs *after* the code changes of the other tasks, so no bug gets frozen into the baselines, and `git status` must show only the new `_regtest_outputs/rf75/` tree.
- `test_robot_patching.py`: the "original RF produces recommendations" test loads `robot/variables/notfound.py` from its file into a private module (`importlib.util.spec_from_file_location`) and calls its `variable_not_found` inside `pytest.raises(VariableError)`, which bypasses both RobotCode's patch (applied at import time of `library_doc`) and RF's private names; validated on RF 5.0–7.5.
- Because the hover regtests only compare the first line, the documentation behaviour is pinned by unit tests under `tests/robotcode/robot/diagnostics/` that run on every RF version: a fixture library (docstring `Tags: alpha, beta`, `Tags: robot:private`, an `Args:` docstring with a trailing `Tags:` line, a `Tags:` line without preceding empty line, `-> None`, unannotated) and a resource (`[Tags]` + `Tags: -keep, other`, `\*escaped\*`) asserting tags, `is_private`, doc text and return type for `get_library_doc`, `get_model_doc`, `get_library_doc_from_library(create_keywords=False)` and `get_resource_doc_from_resource`, an assertion that the RF objects are unchanged, and a `capfd` assertion that nothing is printed. The type-alias test writes the `type`-statement library into `tmp_path` at runtime and is skipped below Python 3.12 / RF 7.5 (the lint matrix targets 3.10, so no `type` statement may live in checked-in test data). The 7.5 `integer` type doc is asserted to contain no `[https://` ROBOT link.

## Risks / Trade-offs

- [Standard-library hovers show the raw `Args:` block on 7.5 until `rf75-argument-docs` lands] → accepted by decision; content is complete, only presentation is pending.
- [A docstring with Google sections and a `Tags:` section that is not the trailing line keeps the `Tags:` text] → rare (RF ≤ 7.4 never recognised that form either); disappears with the follow-up that renders the sections.
- [`parse_docstring` deprecation warning on legacy `Tags:` layout] → silenced by the helper's own `LOGGER.cache_only`; a diagnostic is a candidate for `deprecation-diagnostics`.
- [New hard dependency `markdown`] → pure Python, small; needed by RF 7.5 itself for standard-library Libdoc HTML.
- [Regenerating the model rewrites docstrings of all options from RF 7.5's help text] → expected; only the generated region changes and the diff is reviewed for unintended structural changes.
- [Schema advertises values older RF rejects] → same situation as every version-specific option today.
- [REPL `.doc` output on 7.5 shows the same raw Markdown sections as the hover] → same follow-up; a smoke check guarantees it does not fail.
- [Hand-edited grammar drifts further from the template] → documented; separate cleanup.
- [Baselines frozen with a bug if reset too early] → reset is the last implementation step; only `_regtest_outputs/rf75/` may appear in `git status`.
- [RF < 7.5 cannot read a 7.5 `output.xml` with test metadata (`robotcode results`)] → RF limitation; documented in `docs/03_reference/analyzing-results.md`.
- [RF 7.5 runtime no longer honours doc-declared `robot:private` for library keywords, while Libdoc does] → RobotCode follows Libdoc (as on 7.4); worth an upstream question, no RobotCode decision needed now.

## Migration Plan

No user-facing migration. The release bump invalidates cached documentation (cache keyed by `app_version`), so previously cached 7.5 entries with lost tags are rebuilt. Rollback is a revert of the change; the `rf75` baselines are additive.

## Open Questions

- Upstream reports (do not change this design): block-relative line numbers of tests in `.robot.md`/`.robot.rst` (reproduction in scratch: file line 12 → `line="6"`), and the 7.5 runtime ignoring doc-declared `robot:private` for library keywords.
- Whether `Resource` import completion should hide non-Robot Markdown files (README.md) once `.md` is allowed — RF accepts the import, so they are offered; can be refined in `markdown-suites`.
