# Design: env-var-check-nested-names

## Context

See proposal.md for the motivation. Verified facts:

- **NamespaceAnalyzer.** [`_find_variable`](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py) (L1922) turns every `%{...}` into an `EnvironmentVariableDefinition` named `%{<text before the first '='>}`, with `default_value` set only when there is an `=`. It never returns `None` for an environment variable, so the Robot Framework ≥ 7.0 nested-name resolution in [`_iter_variables_from_token`](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py) (L2216, the `_try_resolve_nested_variable_base` block from L2238) that handles `${A_${b}}` is not reached for `%{...}`. [`_handle_find_variable_result`](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py) (L653) then checks `os.environ.get(var.name[2:-1])` when `default_value is None` and reports `EnvironmentVariableNotFound` (error) or, with hint severity in documentation and metadata, `EnvironmentVariableNotReplaced`. `_iter_variables_token` yields the variables nested in the name as separate references, so they get their own, correct diagnostics next to the wrong one for the outer name.
- The check runs only without a default. `_find_variable` splits at the first `=` even inside a nested variable (`%{%{N=x}}` gets the default `x}`), so a name that reaches the check contains no `=` at all and is the whole text between the braces.
- **SemanticAnalyzer.** `normalize_variable_lookup_name` ([variable_tokenizer.py:274](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/variable_tokenizer.py)) returns `None` for a name containing `${`, `@{`, `&{` or `%{`, so [`_resolve_variable_occurrence`](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/analyzer.py) (L4540) never checks an unresolved nested name. On Robot Framework ≥ 7.0 (branch from L4559) it resolves the name with `_try_resolve_nested_variable_base` and passes the resolved name to `_find_variable`, which splits the resolved text, so `X=fallback` becomes a default as in Robot Framework; if a nested value is not statically known it reports the hint `VariableReferenceNotStaticallyResolvable`. For a `${...}` reference to a list or dictionary variable the resolution joins the variable's values with spaces and ignores item access (checked on RF 7.5 with `@{L}` = `a b` and `&{D}` = `k=v`): `NE_${L}[0]` resolves to `%{NE_a b}` where Robot Framework looks up `NE_a`, `NE_${D}[k]` to `%{NE_k=v}`, i.e. the name `NE_k` with the default `v`, where Robot Framework looks up `NE_v`, and `NE_${L}` to `%{NE_a b}` where Robot Framework looks up `NE_['a', 'b']`. On Robot Framework < 7.0 it reports nothing for the outer name. Its [`_handle_find_variable_result`](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/analyzer.py) (L1925) is the same code as the NamespaceAnalyzer's.
- **Robot Framework** (5.0.1, 6.1.1, 7.0.1, 7.5) resolves the nested variables first and then looks up the resulting name, on all four versions: `%{NE_${S2}}` with `${S2}` = `other` fails with `Environment variable '%{NE_other}' not found.` on 5.0.1 as well.
- **Measured during planning.** With the condition of D1 monkeypatched into the NamespaceAnalyzer and `robotcode analyze code` run over probe suites (78 argument cases, `*** Variables ***`, settings, documentation, tags, `IF`, `VAR`, setup and unused-variable cases) on RF 5.0.1, 6.1.1, 7.0.1 and 7.5, exactly the 12 diagnostics for outer names with nested variables disappear on every version and none appear. Afterwards both analyzers report the same diagnostics on 5.0.1 and 6.1.1; on 7.0.1 and 7.5 the SemanticAnalyzer additionally reports the resolved `'%{NE_other}'` error and four `VariableReferenceNotStaticallyResolvable` hints for names with a default whose nested values are not statically known (`%{NE_${local}=d}`, `%{NE_${S.upper()}=d}`, `%{NE_${{expr}}=d}`).
- **References.** The NamespaceAnalyzer records a reference for the outer environment variable under its unresolved name (`%{APP_${STAGE}}`); the SemanticAnalyzer records none on RF < 7.0 and one under the resolved name (`%{APP_test}`) on RF ≥ 7.0. This change does not touch references.
- **Environment.** The language server copies the `robotcode.robot.env` setting and the `env` of `robot.toml` into `os.environ` at startup ([protocol.py:179](../../../packages/language_server/src/robotcode/language_server/robotframework/protocol.py), L239), so a plain `%{NAME}` is checked against the IDE's run environment and stays an error (maintainer decision; diagnostic modifiers can lower it).
- **Tests.** [`test_environment_variable_diagnostics.py`](../../../tests/robotcode/robot/diagnostics/test_environment_variable_diagnostics.py) runs both analyzers through its `analyze` fixture; its last three analyzer tests run only the SemanticAnalyzer, with a comment that the NamespaceAnalyzer also reports the outer environment variable. [`test_variable_pipeline_comparison.py`](../../../tests/robotcode/robot/diagnostics/test_semantic_analyzer/test_variable_pipeline_comparison.py) compares all `AnalyzerResult` fields of both analyzers, including `variable_references`, on `_PARITY_CASES` and on every `.robot` file of the LSP test data. No `.robot` or `.resource` file under `tests/` has an environment variable name with a nested variable.

## Goals / Non-Goals

**Goals:**
- No `EnvironmentVariableNotFound` / `EnvironmentVariableNotReplaced` for an environment variable name that still contains variables, on the default analysis path.
- Unchanged behavior for plain names, for the nested variables themselves and for references.
- No new static resolution.

**Non-Goals:**
- Resolving nested environment variable names in the NamespaceAnalyzer (see D1).
- Any change to the SemanticAnalyzer (see D2 and Open Questions), including its `VariableReferenceNotStaticallyResolvable` hint for environment variable names.
- The check of a name with an escaped variable: `%{APP_\${STAGE}}` is reported as `'%{APP_\${STAGE}}'` and looked up with the backslash, while Robot Framework reports and looks up `%{APP_${STAGE}}`. Both fail when neither name is set. When only `APP_${STAGE}` is set, Robot Framework passes and both analyzers (with and without D1) report `EnvironmentVariableNotFound`; when only `APP_\${STAGE}` is set, Robot Framework fails and neither analyzer reports anything (checked on RF 5.0.1 and 7.5). The spec requires only the outcome both agree on.
- The check of a name with an escaped brace: for `%{NE_\{B}` with neither `NE_\{B` nor `NE_{B` set, the NamespaceAnalyzer reports `EnvironmentVariableNotFound` for the name as written and the SemanticAnalyzer reports nothing (checked on RF 5.0.1 and 7.5), because its lookup name for such a name is `None`. `semantic-tokenizer-escapes` keeps these lookup names (its D4 and Open Questions), so the spec does not cover names with a backslash other than an escaped variable.
- Lowering the severity of `EnvironmentVariableNotFound` for plain names (maintainer decision).
- References, hover, completion and semantic tokens of environment variable names.

## Decisions

### D1: Skip the existence check for names that contain a variable

`_handle_find_variable_result` of the NamespaceAnalyzer gets one more condition on the existing check: it runs only if `not contains_variable(var.name[2:-1], "$@&%")`. `contains_variable` is Robot Framework's check (wrapped in `robotcode.robot.utils.variables` and already imported in `namespace_analyzer.py`): it ignores escaped variables and recognises `${{...}}`, on RF 5.0 as on 7.5 (checked during planning). Because the check runs only without a default, `var.name[2:-1]` is the whole name, so no scan for a top-level `=` is needed. Everything after the check — cutting the default off the token, recording the reference — stays as it is.

Alternatives considered:
- Returning `None` from `_find_variable` for such names: the reference would run into the RF ≥ 7.0 nested-name resolution of `_iter_variables_from_token`, i.e. static resolution extended to environment variables on the default path, and where that fails into the `VariableNotFound` branch, which Robot Framework does not raise either.
- Resolving the name statically, as the SemanticAnalyzer does on RF ≥ 7.0: would give the correct message for `%{NE_${S2}}`, but extends static resolution, which the maintainer does not want to pursue; and it reports an error Robot Framework does not raise when the nested value changes at run time or the name uses item access (verified, see Risks).
- Skipping the reference in `_iter_variables_from_token`: also drops the recorded reference and so changes more than the diagnostic.
- Adding the same condition to the SemanticAnalyzer's `_handle_find_variable_result`: that method never receives an unresolved nested name, so the condition would have no effect there.

### D2: SemanticAnalyzer unchanged

The SemanticAnalyzer already never reports the unresolved name, so it needs no change for the goals. Its Robot Framework ≥ 7.0 check of the statically resolved name stays; whether to keep it is an Open Question. Consequence: with the semantic model enabled on RF ≥ 7.0, a nested name whose variables all resolve statically is checked under the resolved name — for `%{NE_${S2}}` the name Robot Framework looks up, for item access a different one (see Context and Risks); on the default path it is not reported. The spec requires only what both paths share (the name as written is never reported) and the default path; the semantic path's resolved check is not a requirement. A characterization test (D3) pins it per analyzer, so deciding the Open Question changes a test, not a requirement.

### D3: Tests in the existing environment variable test module

All tests go into `test_environment_variable_diagnostics.py`, which already builds both analyzers without imports or keyword resolution:
- The three SemanticAnalyzer-only tests switch to the `analyze` fixture and so run both analyzers; the comment above them goes. Without the fix they fail for the NamespaceAnalyzer.
- New cases through `analyze`: a name that resolves to a set variable, a resolved value that contains `=`, an undefined variable in the name inside `[Documentation]` (only the `VariableNotReplaced` hint), and `@{...}`, `&{...}` and `${{...}}` in the name. For the last group the test asserts for both analyzers that no environment variable diagnostic names the reference as written and for the NamespaceAnalyzer that none is reported at all; on RF ≥ 7.0 the SemanticAnalyzer reports the resolved names `%{..._['A', 'B']}` and `%{..._{'K': 'V'}}` (the names Robot Framework reports for these) and the hint for `${{...}}`, which the test does not pin.
- One characterization test pins D2 for a name that resolves to an unset variable: no diagnostic for the NamespaceAnalyzer on every version (a spec scenario); for the SemanticAnalyzer the error with the resolved name on RF ≥ 7.0 and nothing below (current behavior, not a requirement).

No `_PARITY_CASES` entry: the references recorded for the outer environment variable differ between the analyzers (see Context) and this change leaves them alone, so a parity case with a nested environment variable name would fail on `variable_references`. Nothing is added to the LSP test data, so no `_regtest_outputs` baseline changes. Environment variables are set and removed with `monkeypatch`; names and the values that become part of a name are upper case, as environment variable names are case-insensitive on Windows (`os.environ` upper-cases its keys there) and case-sensitive on Linux and macOS.

## Risks / Trade-offs

- [A nested name whose resolved variable is not set is no longer reported on the default path (`%{APP_${STAGE}}` with `APP_prod` unset); Robot Framework fails at run time] → accepted: the current error names the wrong variable and has the same text when the resolved variable is set, and detecting the case needs static resolution. The semantic-model path on RF ≥ 7.0 still reports it.
- [The analysis paths differ for such names on RF ≥ 7.0] → pinned by a per-analyzer characterization test (D3), not by the spec; resolved by the Open Question.
- [The SemanticAnalyzer's resolved check can be wrong] → verified: with `${S2}` = `other` in `*** Variables ***`, `Set Suite Variable    ${S2}    suffix` in the suite setup and `NE_suffix` set, `Log    %{NE_${S2}}` passes on RF 7.5 while the SemanticAnalyzer reports `Environment variable '%{NE_other}' not found.`; the NamespaceAnalyzer with D1 reports nothing. Unchanged by this change; input for the Open Question.
- [The SemanticAnalyzer's resolved check is wrong for item access, also with purely static values] → verified on RF 7.5 with `@{L}` = `a b` and `&{D}` = `k=v` in `*** Variables ***`: with `NE_a` and `NE_v` set, `Log    %{NE_${L}[0]}` and `Log    %{NE_${D}[k]}` pass in Robot Framework, while the SemanticAnalyzer reports `Environment variable '%{NE_a b}' not found.` for the first; with `NE_v` unset, Robot Framework fails the second with `Environment variable '%{NE_v}' not found.`, while the SemanticAnalyzer checks `NE_k` with the default `v` and reports nothing. The NamespaceAnalyzer with D1 reports nothing for either. Unchanged by this change; input for the Open Question.

## Migration Plan

None. Cached analysis results of an earlier RobotCode version are dropped when the version changes (`SqliteDataCache`, [data_cache.py:276](../../../packages/robot/src/robotcode/robot/diagnostics/data_cache.py)); with a development build, analyze with `--no-cache-namespaces`. Rollback is reverting the condition.

## Open Questions

- **Keep or align the SemanticAnalyzer's resolved check?** This change keeps it (smallest scope). Keeping it reports the lookup Robot Framework fails with its resolved name for a scalar nested in the name (`%{NE_${S2}}` → `'%{NE_other}'`, as Robot Framework reports) and for `@{...}` and `&{...}` in the name; reports nothing on RF < 7.0 although Robot Framework 5 and 6 resolve the same way; gets item access and a list or dictionary referenced as `${...}` wrong even when all values are static — a false error for `%{NE_${L}[0]}` on a test that passes in Robot Framework, and for `%{NE_${D}[k]}` a check of `NE_k` with the default `v` instead of `NE_v` (see Context and Risks); reports an error Robot Framework does not raise when a nested value changes at run time (see Risks); and keeps the `VariableReferenceNotStaticallyResolvable` hint for environment variable names, also for names with a default. Aligning it would drop `%{`-references from the RF ≥ 7.0 resolution branch of `_resolve_variable_occurrence` (from L4559), so both paths report nothing for the outer name on every version and no diagnostic depends on statically guessed values; it would also drop the reference the SemanticAnalyzer records under the resolved name (which model-based LSP features read it was not checked). The spec would then extend its default-path sentence ("no existence diagnostic") to both paths, with a task for `analyzer.py` and the characterization test of D3 changed accordingly. Aligning would also remove the `VariableReferenceNotStaticallyResolvable` hint that the open change `variable-name-resolution-errors` specifies for `%{...}` references on the semantic-model path only (its scenario for `%{%{NE_N_${S}}=x}`); that scenario would then change to "no hint on either path". For the decision: `semantic-model-switchover` makes the SemanticAnalyzer the default analysis path and `semantic-model-cleanup` removes the NamespaceAnalyzer and the flag, so with the check kept, the resolved-name check described above becomes the only behavior, and the requirement for the disabled semantic-model path ends with the flag.
