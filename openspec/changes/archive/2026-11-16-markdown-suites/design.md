# Design: markdown-suites

## Context

See proposal.md for the motivation. Verified facts (Robot Framework 7.5.1, Robocop 9.3.0 and 9.4.0, RobotCode main of 2026-11-10):

- **Robot Framework.** `MarkdownParser` serves `md`, `markdown` and `robot.md`. Its private `_read_markdown_data(reader)` (identical on master) returns the file's lines with every line outside a robot block and both fence lines blanked, block lines dedented by `min(indent, fence indent)`, and the column offsets of the dedented lines; blocks and empty lines in blocks cannot be recovered from it. Block rule: open `(\s*)(`{3,}|~{3,})\s*(\S+)` with `robot`/`robotframework` (case-insensitive), close at a line of only the same character, at least as many; unclosed runs to the end; other fences are not tracked. `ResourceFileBuilder` picks `MarkdownParser` by suffix, whatever `--extension` says. `__init__.robot.md` is not an init file (robotframework/robotframework#5853, open).
- **Files Robot Framework parses** (User Guide, "Selecting files to parse" and "Suite file extensions"; `robot/parsing/suitestructure.py` of 7.5.1). Files with the extensions `.robot`, `.robot.rst`, `.robot.md` and `.rbt` are parsed automatically; `.md` and `.markdown` need `--extension` or `--parseinclude`. `--extension` replaces the default list. `ValidExtensions` adds the last suffix of each `--parseinclude` pattern (`os.path.splitext`) to the list and matches a file by each of its trailing suffix chains, so `md` matches `shop.robot.md`. A file in a directory is parsed when its extension is valid and, when patterns are given, it matches one of them (`IncludedFiles`: by name or by path, relative patterns against the working directory, a directory pattern recursively, case-insensitive); an `__init__` file of a valid extension needs no pattern. `robotcode robot` runs Robot Framework in the project root. The User Guide calls `--extension` likely to be deprecated in favour of `--parseinclude`. Each extension of the list goes to the standard parser of that extension, any other to the Robot Framework parser (`standard_parsers.get(ext, robot_parser)`): `rst`, `rest`, `robot.rst` to the reStructuredText parser, `rbt` and `json` to the JSON parser (from 6.1), `md`, `markdown` and `robot.md` to the Markdown parser (from 7.5). The default list is `robot` up to 6.0, `robot`, `rbt`, `robot.rst` from 6.1 and also `robot.md` from 7.5. Custom parsers from `--parser` add their own extensions, known only from the imported parser.
- **RobotCode.** `DocumentsCacheHelper` types documents by single suffix (`.robot`, `.resource`, `__init__.robot`) and tokenises `document.text()` with `robot.api.get_*_tokens`; imported resources always go through `get_resource_tokens` on the raw text. 39 handlers in 21 language-server modules are gated on the language id `robotframework`, which the client sends (VS Code sends `markdown` for `.robot.md`). The language server, `analyze code` and `discover` already load the robot.toml profile; the language server gets it at start and VS Code restarts it when the robot.toml changes. `discover info` reads no configuration. `analyze code` scans `.robot`/`.resource`; `CodeAnalyzer` registers only the Robot Framework provider's language definition, through the classmethod `get_language_definitions`. The edits of code actions are computed in `resolve`, which gets no document and so no language gate. Robocop gets RobotCode's model (`SourceFile(path, config, _model=model)`), formatting uses `format_until_stable`.
- **Robocop ≥ 9.2** supports Markdown itself: `EmbeddedSourceFile` builds one model per block, translates positions and leaves prose untouched; `reload_model()` builds the models from the given `_source_lines`, so unsaved editor text works; `RobocopFormatter.format_embedded` formats each block alone (its own `format_file` calls it for embedded files, and then saves). Given RobotCode's model instead, Robocop treats the file as plain Robot data: findings in the prose and formatting that drops the prose. Robocop reads each block on its own, Robot Framework reads them as one text: a block that continues a test gets `*** Comments ***` inserted when formatting, and the linter reports `can-be-resource-file` and `not-allowed-char-in-filename` for such files (measured, left to Robocop).
- **VS Code.** The client's document selector is language-based; `PythonManager.executeRobotCode(folder, args, profiles, format)` runs CLI commands with the folder's interpreter.
- **Semantic model.** Both analyzers work on the model built from the tokens, so Markdown tokens reach both without analyzer changes.

## Goals / Non-Goals

**Goals:**
- The same blocks and positions as Robot Framework.
- RobotCode serves exactly the Markdown files Robot Framework parses with the selected profiles.
- One function decides the formats Robot Framework parses, for `discover info`, the language server and `analyze code`.
- RobotCode's own edits never touch prose or fence lines.
- Markdown is a language of its own: its behaviour lives in parts gated on it, and the Robot Framework parts hold no Markdown checks.

**Non-Goals:**
- Format classes or hooks for other packages (the format interface is only as large as Markdown needs).
- Changing how Robocop reads blocks.
- The test explorer, run and debug commands for Markdown files in VS Code (breakpoints are part of D7).

## Decisions

### D1: Document formats from the profile, in `robotcode-robot`

`packages/robot/src/robotcode/robot/document_formats.py` holds a `DocumentFormat` dataclass (name, extensions), `MARKDOWN_SUPPORTED = RF_VERSION >= (7, 5, 1)` at module scope, and `document_formats(profile)`, the formats Robot Framework parses with the profile. It builds Robot Framework's extension list: the evaluated `extensions` option split at colons, or Robot Framework's default extensions when the option is not set, plus the last suffix of each `parse-include` pattern; each entry normalised like Robot Framework (lower case, no leading dot). It groups the list by Robot Framework's parser for each extension, in the order of their first extension, with any other extension in `robot`. The default list and the parser of each extension come from Robot Framework itself, once at module scope: `TestSuiteBuilder().included_extensions` and, from 6.1 on, `TestSuiteBuilder().standard_parsers`; a format is named after its parser class without `Parser`, in lower case (`robot`, `rest`, `json`, `markdown`). Below 6.1, where `standard_parsers` does not exist, `rst` and `rest` go to `rest`. The Markdown files RobotCode serves are those of the `markdown` format, from Robot Framework 7.5.1 on, so `robot.md` without any configuration. A second function of the module gives the file condition of the `parse-include` patterns: with patterns, a Markdown file is served only when it matches one of them, unless it is the `__init__` file of its extension; the matching is Robot Framework's own `IncludedFiles`, with relative patterns first resolved against the project root the way Robot Framework resolves them against its working directory, since `robotcode robot` runs Robot Framework in the root. The language server, `analyze code` and `discover info` call these functions with the profile they already load. An explicitly listed file in `paths`, which Robot Framework parses whatever its extension, is not followed: it is rare, and paths given on the command line are not visible to the language server. Rejected: each consumer reading the robot.toml itself (three rules that can drift); an opt-in through `extensions` only, with Robot Framework's default list not counting (decided on 2026-11-08, revised by the user on 2026-11-15: the `.robot.md` files Robot Framework runs got no editor support and no `analyze code` check); an own glob matcher for `parse-include`, which can drift from Robot Framework's; a table of the default list and the parsers per Robot Framework version (an earlier version of this change, replaced on the user's decision of 2026-11-15), which a new format of Robot Framework would not reach.

### D2: Robot Framework's data for the analysis, an own scanner for the block boundaries

`packages/robot/src/robotcode/robot/utils/markdown_blocks.py` provides `read_markdown_data(text)`, the only caller of `MarkdownParser._read_markdown_data`, and `find_robot_blocks(text)`, which returns `RobotBlock` dataclasses (opening and closing fence line, content lines) with Robot Framework's two expressions. Tokens come from `get_tokens`/`get_init_tokens`/`get_resource_tokens` on Robot Framework's data, with the column offset added per line like Robot Framework's `ColumnOffsetUpdater`. A parity test in the Robot Framework matrix keeps the scanner on Robot Framework's rule. Rejected: a CommonMark library such as markdown-it-py, which sees other blocks than Robot Framework (fences in quotes, fences indented by four or more spaces) and adds a dependency; an own extraction of the data, since Robot Framework's method gives its dedent exactly.

### D3: An own language `robotframework-markdown`

`document_formats.py` also provides `markdown_language_definition(profile, root)`, which returns `LanguageDefinition(id="robotframework-markdown", extensions=[".<extension>", …], extensions_ignore_case=True)` for the extensions of the `markdown` format of D1, with the file condition of D1 when `parse-include` sets patterns, or `None` when no Markdown extension is active, so that the language exists only on Robot Framework ≥ 7.5.1. `LanguageDefinition` gets an optional file condition, a function of the path; `detect_language_id` takes a definition only when one of its extensions matches and its condition, if any, holds, so that the language server's preload, delete watcher and `didOpen` and the scan of `analyze code` follow the same rule. The language-server protocol adds it to its language definitions as an entry of its own and its extensions to its file extensions (watchers, workspace file operations); both stay per instance, since the active extensions come from the profile, and the `robotframework` definition stays as it is. No editor sends this id: VS Code sends `markdown` for these files. `didOpen` therefore keeps the client's language id only when it is one of the server's languages and otherwise takes the id the server detects from the file name; so only the Markdown files Robot Framework parses get the Markdown language, and any other Markdown file the client sends gets none. `detect_language_id` matches extensions of more than one part, such as `.robot.md`, and takes the definition with the longest matching extension. These rules are not Markdown's own: a later format in Markdown files, such as Gherkin's `.spec.md`, gets a language id of its own the same way, from its definition.

Handlers that work on Markdown documents as they are accept both ids, `@language_id("robotframework", "robotframework-markdown")`: hover, goto, references, rename, document highlight, semantic tokens, inlay hints, inline values, signature help, code lens, diagnostics, the collection of code actions (documentation, quick fixes, refactor), reading the document text, completion resolve and the `ImportsManager`'s invalidation of modified resources. Completion, folding, document symbols, selection range, Robocop diagnostics and formatting keep `robotframework` only; their Markdown behaviour is in the Markdown parts of D4 and D5. The workspace preload and the delete watcher take the extensions of both definitions.

`DocumentsCacheHelper` reads a document's Robot Framework data with the reader of its language, from a mapping of language ids to readers: Robot Framework's tokenizers on the text for `robotframework`, Robot Framework's Markdown data of D2 for `robotframework-markdown`. An imported resource ending with `.md` or `.markdown` is always read with the Markdown reader, on Robot Framework ≥ 7.5.1 and also without an active format, since Robot Framework picks the resource parser by suffix. A Markdown document is typed INIT when it is `__init__.<extension>` and the extension is not `robot.md`, otherwise GENERAL; `__init__.robot.md` stays GENERAL until robotframework/robotframework#5853 changes Robot Framework. The blocks of D2 are available for Markdown documents.

Rejected: serving Markdown documents under the language id `robotframework`, with Markdown checks in the Robot Framework parts (the first implementation of this change), which mixes both languages in one code path; one definition with every Markdown extension and checks for the active ones in the handlers; the editor's id `markdown`, whose gate would match every document a client sends as Markdown, also without an active format or below Robot Framework 7.5.1; `.robot.md` as a language of its own in VS Code, which takes Markdown's features from the file (measured in VS Code 1.146: no outline, no folding of headings, no links, the preview only by command, since its menus are bound to the language `markdown`).

### D4: Markdown parts for completion, ranges and placed code

The Markdown behaviour of the language server lives in parts of its own in `robotframework/parts/markdown/`, registered in the Robot Framework protocol and gated on `robotframework-markdown`. Where a Markdown part needs a different result from Robot Framework logic, the Robot Framework part gets one overridable step with today's behaviour as its default, and no Markdown check.

- **Completion** returns nothing when the position is not on a content line of a block (D2's scanner), and the Robot Framework completion otherwise.
- **Ranges.** The folding and symbol visitors and the selection-range computation take each node's range from one method, which the Markdown parts replace. In a Markdown document a range runs from the element's first token on a block line to its last line with data and the empty lines after it in the same block, since the empty lines after an element in Robot Framework's data stand for prose and fence lines and for the empty lines of later blocks without data. Selection ranges skip an element whose range does not hold the position, so that each range holds the next, and a position outside the blocks gets none.
- **Placed code.** The edits of "Create Keyword", "Extract keyword" and "Create suite variable" are computed in `resolve`, where no language gate applies. `create_insert_keyword_workspace_edit` and the variable-section insertion therefore ask an event for the place of the new code, called with `language_id_filter(document)`; without a handler the Robot Framework position stays. The Markdown handler keeps a position inside a block, moves a position after a block to the end of that block (before its closing fence, or the end of the file for an unclosed block) and a position before the first block to the start of its content, and indents the placed lines like the block's opening fence, which Robot Framework removes again. Rejected (by the user): not offering these code actions for Markdown files.

### D5: Robocop's own Markdown support

A Markdown part checks and formats Markdown documents with Robocop ≥ 9.2, with the Robocop configuration of the existing helper: it builds `EmbeddedSourceFile(path=…, config=…, _source_lines=<document lines>)` and calls `reload_model()`; the linter runs `run_check` on it, formatting calls `format_embedded` and returns one edit for the whole document when the text changed. With an older Robocop the part reports no findings and formatting shows a message, like the existing one for a missing Robocop. The part has no range formatting, so a range formatting request for a Markdown document returns no edit, since Robocop counts the lines of each block on its own. The Robot Framework Robocop and formatting parts stay as they are. How Robocop reads blocks is Robocop's matter (user decision, 2026-11-10). Rejected: RobotCode formatting each block itself with the section of the block before as context (own code on Robocop's internals).

### D6: `discover info`

`info` loads the configuration through `handle_robot_options`, as `discover files` does, and adds `document_formats: Optional[List[DocumentFormat]]` to `Info` with every format of D1; the Markdown text output gets a section for them. It lists what Robot Framework parses, also where RobotCode serves nothing: `json` and `rest`, and `markdown` on Robot Framework 7.5.0. It lists the extensions only; the `parse-include` patterns are applied by the language server and `analyze code`. Resource files (`.resource`), which Robot Framework reads by their suffix whatever the settings, and the extensions of custom parsers, which are known only after importing the parser, are not listed. A configuration that cannot be read fails the command like the other `discover` commands. Rejected (by the user): listing only the formats RobotCode serves besides `.robot` files.

### D7: VS Code

Before it creates a folder's language client, `languageclientsmanger.ts` runs `discover info` with the folder's profiles and JSON output. A pure function turns the `markdown` format into selectors `{ scheme: "file", pattern: "<folder path>/**/*.<extension>" }`, added to the existing ones; the other formats add nothing, since `.robot` files reach the server by their language and it serves no `json` or `rest` files; a failing call is logged and adds nothing. When `md` comes from a `parse-include` pattern, the client sends every `.md` file of the folder, and the language server gives those outside the patterns no language (D3). The restart after a robot.toml change runs the query again. Rejected (by the user): reporting the formats in the `initialize` result, which needs a running server and is of no use to other editors.

Breakpoints: VS Code lets breakpoints be set only in the languages that a `contributes.breakpoints` entry names (`canSetBreakpointsIn`), or everywhere with the user setting `debug.allowBreakpointsEverywhere`; an entry's `when` clause is evaluated in the window's context at each toggle, not per file (VS Code 1.131 and 1.142). The manifest adds `{ "language": "markdown", "when": "robotcode.markdownSuites" }`, and the extension sets the context key `robotcode.markdownSuites` to whether the document of the active editor matches the Markdown selectors of its folder's language client (`vscode.languages.match`), again when the active editor changes and when a client starts or stops. A breakpoint that is set stays, and debugging stops at it also while another file is active (measured). When `md` comes from `extensions` or a `parse-include` pattern, the selectors match every `.md` file of the folder, so breakpoints can be set in all of them, which the user wants: those files are suites then. In a split editor, the active side counts, not the one under the mouse. The debugger needs no change: it matches breakpoints by path, and Robot Framework 7.5.1 reports the lines of the file (measured: a breakpoint at line 6 of `tests/first.robot.md` stops there, with the frames at the file's lines). Rejected (by the user, 2026-11-15): documenting `debug.allowBreakpointsEverywhere`, which allows breakpoints in every file of every language; a change of its own for breakpoints; a key that is set while any client serves Markdown (an earlier version of this change), with which breakpoints could be set in every Markdown file of the window.

### D8: `analyze code`

A `MarkdownLanguageProvider` in `robotcode-analyze` contributes the language definition of D3 and the workspace scan for the Markdown files of that definition. The analysis of these documents is the Robot Framework provider's, on the tokens of D2: its analysers run for every document, and its text reader accepts both languages. `CodeAnalyzer` registers the language definitions of all its providers, and `get_language_definitions` gets the profile, since the Markdown definition depends on it. Rejected: scanning the Markdown files in the Robot Framework provider, which mixes both languages again; a Markdown provider with an analysis of its own, which would duplicate the Robot Framework analysis although only the tokens differ.

### D9: Tests

Unit tests for D1 (default list, `extensions`, `parse-include` patterns by name, by path and of a directory, `__init__` files) and D2 (fence variants, unclosed and empty blocks, other-language fences, CRLF fixtures written with `write_bytes`) plus the parity test, skipped below Robot Framework 7.5.1; `test_document_cache_helper.py` for typing and positions; a namespace test for Markdown resources; language-server tests for the language id, preload, completion, ranges, code actions and Robocop, with a test data folder of their own whose robot.toml sets `extensions`, served by its own server like the existing topic groups, with baselines only under `rf75/`; `discover info` and `analyze code` acceptance tests in `tmp_path` projects; a unit test of D7's selector function in `vscode-client/test/` and a check in the isolated VS Code harness. The Markdown tests check the parts of D3 to D5 through the language server, so they hold for the restructured code; the existing tests and baselines of the Robot Framework parts check that their behaviour is unchanged.

## Risks / Trade-offs

- [Robot Framework changes `_read_markdown_data` or its block rule] → one helper and the parity test in the Robot Framework matrix show it; the fix goes there.
- [Robocop reads blocks on their own] → Robocop's findings and formatting of continuing blocks differ from Robot Framework; documented as a known limit.
- [`discover info` adds a process start before each language-server start] → one short CLI call per folder; no call when the folder is not taken up.
- [With `md` active, every `.md` file goes to the language server, README files included] → Robot Framework parses them too when `md` is in `extensions`; files without blocks yield empty models. When `md` comes from a `parse-include` pattern, the files outside the patterns get no language.
- [Every project on Robot Framework ≥ 7.5.1 now has its `.robot.md` files served and checked by `analyze code`, without configuration] → Robot Framework runs them as well; `extensions` or `parse-include` exclude them for both.
- [With `md` from a `parse-include` pattern, breakpoints can be set in every `.md` file of the folder, also outside the patterns] → the selectors match by extension; a breakpoint on a line that is not executed never stops.
- [`__init__.robot.md` is no init file] → follows Robot Framework until robotframework/robotframework#5853 changes it.
- [A format of another package, such as Gherkin later, cannot add its language id to the decorators of the shared handlers] → it needs a registration then; not part of this change.

## Migration Plan

Additive: on Robot Framework ≥ 7.5.1, RobotCode serves and checks the Markdown files Robot Framework parses, `.robot.md` files without any configuration, and reads imported Markdown resources like Robot Framework. Nothing changes below 7.5.1. Rollback: revert.
