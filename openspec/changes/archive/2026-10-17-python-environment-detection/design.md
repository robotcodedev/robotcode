# Design

## Context

See proposal.md for the motivation. Verified on 2026-10-16, in the isolated harness with ms-python.python 2026.10.0 and ms-python.vscode-python-envs 1.40.0 copied from the user's profile, and in the sources of both extensions (vscode-python @6278ebae, vscode-python-environments @86c5747c):

- `vscode-client/extension/pythonmanger.ts` uses `@vscode/python-extension`: `getActiveEnvironmentPath(folder)`, `resolveEnvironment`, the event `onDidChangeActiveEnvironmentPath`; `robotcode.python` overrides. Under the Python Environments extension, `getActiveEnvironmentPath` keeps returning the setting or the old auto-selection, which that extension never writes, and the event fires only on setting changes or when the Python extension itself asks for the interpreter. In the harness, a `.venv` created with `uv venv` never reached RobotCode this way; its quick pick stayed open and **Retry** failed again.
- The Python Environments API (the extension's exports; types in `@vscode/python-environments` 1.4.0): `getEnvironment(folder.uri)` returns `{ envId, version, sysPrefix, execInfo.run.executable, error? }`, races one second and may return the last known value, the real one following through `onDidChangeEnvironment`; `onDidChangeEnvironment` fires for explicit selections, `onDidChangeEnvironments` for found and removed environments, `onDidChangePackages` only for environments made active with `setEnvironment`; `refreshEnvironments(folder.uri)`, `getPackages`, `managePackages(env, { install })`. With `python.useEnvironmentsExtension` explicitly `false` the extension exports nothing. Measured: a new venv was not found on its own within 70 s; after `refreshEnvironments(folder.uri)` it was found and auto-selected, `onDidChangeEnvironments` fired on both APIs, `getEnvironment` returned it, `getPackages` listed `robotframework`.
- Old API only: a new venv is in `known` after `refreshEnvironments({ forceRefresh: true })` but never auto-selected in the session; `updateActiveEnvironmentPath(venvPython, folder)` fires `onDidChangeActiveEnvironmentPath`, and RobotCode's existing handler then closed the dialog and started the language server with the venv.
- Both extensions get existence, version and prefix from PET: `NativeEnvInfo { executable, version, prefix, error }`, the venv version from `pyvenv.cfg`, otherwise one interpreter run, cached. The old API's `ResolvedEnvironment` carries `version { major, minor, micro }` with `-1` when unknown, `executable.uri` and `executable.sysPrefix`; `getActiveEnvironmentPath()` is `{ id: "DEFAULT_PYTHON", path: "python" }` when nothing is selected, and `resolveEnvironment` of that default resolved to the `python3.15` on the PATH in the harness (2026-10-16), so it is a usable interpreter, not nothing. The Python Environments extension marks broken environments with `error` and `version` `'no-python'` or `'Unknown'`.
- File watchers: `RelativePattern(folder, "**/pyvenv.cfg")` fired for `uv venv`; nothing fired for files three or more levels below a directory created during the session (`.venv/lib/python3.15/site-packages/…`), in any watcher form, with VS Code's default `files.watcherExclude`.
- `languageclientsmanger.ts`: `isValidRobotEnvironmentInFolder` runs a `while (!valid)` loop under `_pythonValidPythonAndRobotEnvMutex`, with `selectPythonEnvironment`'s quick pick (`ignoreFocusOut`); `discoverTests` and the language client start wait on that lock; `_pythonValidPythonAndRobotEnv` and `_pythonCanceledPythonAndRobotEnv` are the caches, `isRobotEnvironmentKnownInvalid` reads the first. `languageToolsManager.ts` shows the Python and Robot Framework items of the language status with `getPythonInfo` and offers "Select Environment" and the Tool Menu entry, both calling `selectPythonEnvironment`.
- uv-made environments have no pip; their `pyvenv.cfg` has a line `uv = <version>`. The legacy commands `python.setInterpreter` and `python.createEnvironment` work with the Python Environments extension too (they also call its `setEnvironment` and `python-envs.createAny`); the Python Environments command `python-envs.set` takes the folder's `Uri`.

## Goals / Non-Goals

**Goals:**

- One place that knows a folder's environment and its problem, read by the language client start, discovery, the language status, the Test Explorer hint and the notification; nothing waits on a dialog.
- Recovery without the user: when the Python side changes its selection, when a venv appears, when Robot Framework is installed.
- The same behaviour with and without the Python Environments extension, as far as the old API allows.

**Non-Goals:**

- Selecting an environment on the user's behalf in the old API world without being asked; **Use .venv** is an offer.
- Watching `site-packages`; polling replaces it.
- Changing how the language server, discovery or runs use the interpreter once it is known.

## Decisions

### An environment provider with two backends

`pythonmanger.ts` gets a provider that resolves `{ executable, version, sysPrefix, problem }` for a folder. The Python Environments backend uses the extension's exports when `vscode.extensions.getExtension("ms-python.vscode-python-envs")?.exports` is an object with `getEnvironment`, typed with `@vscode/python-environments`; it calls `getEnvironment(folder.uri)`, takes `execInfo.run.executable`, `version` and `sysPrefix`, and treats `error`, `'no-python'` and a missing executable as problems. The old backend keeps `getActiveEnvironmentPath` and `resolveEnvironment` and reads `version` from the resolved environment; `DEFAULT_PYTHON` (nothing selected, path `python`) is resolved like any other path and used when the Python extension resolves it to an interpreter, otherwise it is "no interpreter selected"; any other path without an executable is "interpreter missing". `robotcode.python` short-circuits both, as today. The provider merges the events of both APIs into one `onDidChangeEnvironment(folder)`.

Alternative, the old API only with `refreshEnvironments`: rejected, because its selection never follows the Python Environments extension's auto-selection, which is what VS Code's Python view shows the user.

### Usability from API data, Robot Framework by one check

The Python version check spawns no process: `version` from the provider decides `>= 3.10`; only a provider result without a usable version (`-1` parts, `'Unknown'`) falls back to the existing `checkPythonVersion` once. The Robot Framework check is `check_robot_version.py` alone: it imports `robot` with the interpreter, so it finds the package wherever Python does (site-packages, user site, `PYTHONPATH`, `.pth` files), checks the 5.0 minimum and reports the version. A first version looked for `robotframework-*.dist-info` under `sys.prefix` as a cheap signal before running the script; the user dropped it on 2026-10-16, because the look misses every install outside the prefix (user site, `PYTHONPATH`) while the message promises to notice the install.

### A state per folder replaces the loop and the lock

A reset (restart, Retry, a changed setting) bumps a generation counter per folder and drops the running check, so a check that started with the old environment does not publish its result; a failing check (an API that rejects) ends as `interpreterMissing` with a log line instead of a state stuck at `checking`. The Robot Framework check tells `missing` (the script says so), `tooOld`, and `failed` (timeout, script not started) apart; the last becomes `interpreterMissing`.


`languageclientsmanger.ts` keeps `{ state: "unknown" | "checking" | "usable" | "unusable", problem?, executable?, version?, sysPrefix?, checkedAt }` per folder. `getServerOptions` and `discoverTests` read it and return at once when the folder is unusable; a check runs at most once at a time per folder and never shows UI. `isValidRobotEnvironmentInFolder` becomes the accessor of that state (plus a run of the check when the state is unknown), `isRobotEnvironmentKnownInvalid` reads `state === "unusable"`, and `_pythonCanceledPythonAndRobotEnv` disappears: there is no dialog to cancel. "Restart Language Servers" sets the state to unknown and checks again, as today.

### Triggers

- Provider events (both APIs, merged): re-resolve and re-check the folder.
- `createFileSystemWatcher("**/pyvenv.cfg")` on create: call `refreshEnvironments(folder.uri)` on the Python Environments API or `refreshEnvironments({ forceRefresh: true })` on the old one, then re-resolve; in the old API world also remember the venv as a candidate for **Use .venv** (its interpreter is `<venv>/bin/python` or `<venv>\Scripts\python.exe` next to the `pyvenv.cfg`). The candidates in the old API world are, besides the remembered ones, the environments in `known` whose folder lies in the workspace folder and `.venv` or `venv` in the folder itself with a `pyvenv.cfg`: the Python extension does not re-select an interpreter for a folder it already chose one for, so a `.venv` created in a later session stays unselected until the user acts.
- Polling: while a folder is unusable because Robot Framework is missing or too old, the check script runs every five seconds, after five minutes every ten seconds (the user's numbers), until it says `ok`; then the folder is checked again in full. It stops when the folder is usable, switched off or reset, and a new check (Retry, an environment event, a restart) starts it again at five seconds. A Python start every few seconds is the price for finding the package as Python does; the slower pace keeps a folder that was left alone cheap. When the problem is a missing interpreter or an old Python, polling is not needed: a different interpreter arrives through the events.
- `onDidChangePackages` of the Python Environments API, when it fires, triggers the confirmation directly.

### The message

One progress notification per folder (`vscode.window.withProgress` with `ProgressLocation.Notification`, title "RobotCode", `cancellable`), kept open by a promise the extension resolves. It is the only notification code can update and close: `progress.report({ message })` replaces the text when the problem changes, resolving the promise closes it when the folder becomes usable, is switched off or removed. VS Code keeps a progress notification on screen (no toast timeout), gives it a **Cancel** button and no close cross. Its actions are links in the text, `[label](command:robotcode.environmentAction?<args>)`, which VS Code renders and runs in notification messages (verified in the harness): **Use .venv** (old API world with a candidate), **Select Environment**, **Create Environment**, **Retry**. A `showWarningMessage` with buttons was the first version; it could not be closed, so a solved problem left a stale toast, its toast disappeared after VS Code's timeout, and the Python side's own selection shortly after the first check produced two of them.

The message is requested by the callers that know the folder is a Robot Framework project, the language client start and the test discovery, not by the Test Explorer's profile loading, which runs for every folder. It is shown 2.5 s after the first unusable result: the Python side's own selection arrives shortly after RobotCode's first check at startup, so by then the state is final and the text right, and a folder that becomes usable in that time shows nothing. **Cancel** closes it for the current problem; a new problem, **Retry** and **RobotCode: Restart Language Servers** open it again.

Texts (VS Code prefixes the title): "Found a Robot Framework project in '<folder>', but the selected Python environment '<name>' has no Robot Framework. Install it into that environment." / "… but the Robot Framework <version> in the selected Python environment '<name>' is older than 5.0, which RobotCode needs. Update it." (No hint how to install: `uv sync` fits only a project with a `pyproject.toml` that declares Robot Framework, and the other ways are as many as the tools.) / "… but no Python interpreter is selected for it." / "… but its Python interpreter '<path>' no longer exists or cannot be started." / "… but its Python <version> is older than 3.10, which RobotCode needs." ("project" rather than "files": a folder with only a `robot.toml` starts the language client too.) With the setting `robotcode.python` the texts name the setting instead of "the selected Python environment". After **Retry**, "Checked again at <time>." is appended while the problem remains. A sentence that the message closes when RobotCode finds the package was dropped as clumsy; instead, when a folder whose message was shown becomes usable, a short information message confirms it: "Environment for '<folder>' found: <name> with Python <version> and Robot Framework <version>. RobotCode is ready." Folders that are usable from the start get no such message.

### Switching a folder off

After **Cancel**, a plain warning notification asks whether to switch RobotCode off for the folder. **For this session** puts the folder into an in-memory set that `isDisabledForFolder` reads next to `robotcode.disableExtension`: the language client start, the discovery and the Test Explorer (whose switched-off hint names the session case), the environment events and the polling skip such a folder; the restart commands take it out again, a window reload forgets it; the Test Explorer drops the folder's run profiles on the `Refreshed` event the switch-off fires. **For this project** writes `robotcode.disableExtension: true` into the folder settings, which restarts the folder's client as any setting change does and so stops it. Closing the question changes nothing: the problem stays visible in the language status and the Testing view, and the checks keep running.

### The actions

- **Select Environment** (also `robotcode.selectPythonEnvironment` and the Python item of the language status): `python-envs.set` with the folder's `Uri` when the Python Environments API exists, else `python.setInterpreter`; the selection comes back through the provider events.
- **Create Environment**: `python.createEnvironment` with `{ workspaceFolder }`, which works in both worlds and installs the project's declared dependencies when its dialog offers that.
- **Retry**: forgets a cancel, shows "Checking the Python environment again…", asks the Python side to look for environments (`refreshEnvironments(folder.uri)`, or the forced refresh of the old API, which its documentation reserves for refreshes the user triggers), resets the folder's state and restarts its client, which checks again; the message is then replaced at once with the result and the time of the check.
- No **Install Robot Framework**: the first implementation had one (`managePackages` with the Python Environments API, otherwise a terminal running `uv pip install` or `pip install`), verified in both modes and then removed on 2026-10-16 at the user's decision. It installed the newest `robotframework`, whatever the project pins in `pyproject.toml`, `requirements.txt` or a lock file; in a uv project a `uv pip install` into `.venv` is outside the lock and the next `uv sync`, which is exact by default, removes it again; poetry, pipenv, pixi and conda have their own commands; `pip install` into a system Python fails as externally managed. Which tool and which version a project wants is not ours to guess, and the Python Environments view already offers a package install. The message says that Robot Framework has to be installed, not how, and the polling picks up whatever the user installs.
- **Use .venv** (old API only): `updateActiveEnvironmentPath(candidate, folder)`; the resulting `onDidChangeActiveEnvironmentPath` drives the rest, as the harness showed.
- **Open Settings** instead of Select, Create and Use .venv when the setting `robotcode.python` names the interpreter: the setting wins over the Python side, so a selection there would change nothing; the message names the setting and opens the settings at `robotcode.python`.

### Types and dependencies

`@vscode/python-environments` is added as a dependency for its types; the API object itself is taken from the extension's exports, so a missing or switched-off extension costs nothing. `@vscode/python-extension` stays for the old backend.

## Risks / Trade-offs

- [`getEnvironment` answers with the last known value after one second] → every answer is provisional until the next `onDidChangeEnvironment`, which re-resolves; the state machine tolerates repeated checks.
- [The Python Environments API 2.0 is pending (capabilities work)] → the consumer methods used here are the stable 1.x ones; the types package pins a 1.x version.
- [Users with `python.useEnvironmentsExtension` unset and experiments off: the Python extension itself does not bridge, the Python Environments extension still exports its API] → RobotCode follows the Python Environments extension, the same source as its view; the configuration guide says which environment RobotCode uses.
- [The progress bar of the message suggests work in progress] → it is: RobotCode listens and polls, and the text says what closes the message.
- [Escape or "hide notifications" moves the message into the notification center] → it stays there with its links until it closes; a later **Retry** or restart replaces its text but does not bring it back as a toast.
- [Polling with a Python start every few seconds] → only for folders whose Robot Framework is missing or too old, five seconds for five minutes, then ten; nothing for usable or switched-off folders.
- [`python-envs.set` argument shape changes] → the command is called with a `Uri`, as its source takes it today; a failure falls back to `python.setInterpreter`.

## Verification

Harness matrix of 2026-10-16 (isolated VS Code 1.142 with ms-python.python 2026.10.0, ms-python.vscode-python-envs 1.40.0, ms-python.debugpy 2026.6.0 from the user's profile; folders with one Robot Framework file each, environments made with uv):

With the Python Environments extension:

- No venv, the extension's global Python 3.15 without Robot Framework: notification with **Install Robot Framework**, **Select Environment**, **Create Environment**; the Testing view shows the environment hint, the language status "not installed - not installed in the Python environment". `uv venv` in a shell: the `pyvenv.cfg` watcher fired, `refreshEnvironments(folder.uri)` made the extension find and select `.venv`, the folder was checked again with `.venv`. `uv pip install robotframework`: the polling saw the dist-info, the check passed, the language server started and the tests were discovered, all within about ten seconds and without the user.
- Venv without Robot Framework selected: notification without an install action; `uv pip install robotframework` from a shell was picked up by the polling, the folder was usable and the language server running a few seconds later. (Before the action was removed, **Install Robot Framework** through `managePackages` had worked the same way.)
- Venv with Python 3.9: "older than 3.10" decided from the API's data, no Python process in the log; only **Select Environment** and **Create Environment**. **Select Environment** opened the Python Environments picker, **Create Environment** the Python extension's create flow (Venv, Conda).
- Usable folder, selection switched through the API to the 3.9 venv: language server stopped, notification, hint, tests removed; switched back: language server started, tests back.
- Usable folder whose `.venv` was deleted: the extension fell back to its global Python, RobotCode restarted on it and reported the missing Robot Framework.
- Folder with only a `robot.toml`: the language client start checks it and the notification appears; hence "project" in the text.

With the Python extension's API only (`python.useEnvironmentsExtension: false`):

- No venv, global Python 3.15: notification as above. `uv venv`: forced refresh, check again, a second notification now with **Use .venv** (the first stays in the notification center). **Use .venv**: `updateActiveEnvironmentPath`, the folder re-checked on `.venv`; `uv pip install robotframework`: polling, usable, language server, tests.
- Venv without Robot Framework (auto-selected): notification without an install action; an install from a shell made the folder usable a few seconds later. (Before the action was removed, **Install Robot Framework** in a terminal running `uv pip install --python … robotframework` had worked the same way.)
- Python 3.9: as above, no Python process.
- Usable folder, `updateActiveEnvironmentPath` to the 3.9 venv and back: as above.
- Global interpreter selected while `.venv` with Robot Framework exists in the folder: **Use .venv** offered at once; choosing it made the folder usable.

Second round, 2026-10-16, after the message became a progress notification with **Retry** and **Cancel** (old API mode, venv without Robot Framework, where the first check still saw the global interpreter): one message at startup with the links **Select Environment**, **Create Environment**, **Retry** and the button **Cancel**, no second one; **Retry** appended "Checked again at <time>."; **Select Environment** opened the interpreter picker; **Cancel** asked with **For this session** and **For this project**; **For this session** closed the message, the Testing view showed the switched-off hint, the log said so, and **RobotCode: Restart Language Servers** brought the message back; **For this project** wrote `robotcode.disableExtension: true` into `.vscode/settings.json` and the hint appeared; a `uv pip install robotframework` from a shell closed the message by itself and started the language server within two seconds. With the Python Environments extension (venv without Robot Framework): one message at startup, **Create Environment** opened the Python extension's create flow, an install from a shell closed the message and started the language server within three seconds. Old API with the global interpreter selected while `.venv` exists: the message offered **Use .venv** as its first link, and choosing it selected `.venv`, made the folder usable, started the language server and closed the message. Multi-root workspace (Python Environments mode, four folders: usable, venv without Robot Framework, Python 3.9, second venv without Robot Framework): one message per unusable folder, each naming its folder, the usable folder's tests in the tree; **Cancel** on the Python 3.9 folder asked for that folder and **For this session** switched only it off while the other messages stayed; an install into one folder closed only its message and started its language server; removing a folder from the workspace closed its message. VS Code shows at most three toasts at a time, further messages wait in the notification center.

Findings kept as they are:

- At startup the Python side's first selection event arrives right after RobotCode's first check, so an unusable folder is checked twice, two short Python starts; the message waits 2.5 s and shows the final text once.
- The Python extension shows its own "An Invalid Python interpreter is selected" toast for a uv venv in the Python Environments mode; not RobotCode's.
- Escape in the workbench hides all toasts; the message then lives in the notification center until it closes.

Review round, 2026-10-16: a cancelled message comes back when a virtual environment appeared that it can offer (the cancel is remembered per problem and offered venv); **Cancel** during a running check still asks the switch-off question (`isRobotEnvironmentKnownInvalid`); the question reads "Switch RobotCode off for the folder '<folder>'? For this session: until the window is reloaded or the language servers are restarted. For this project: with the folder setting robotcode.disableExtension, until you remove it."; the Test Explorer refreshes its hint when a folder is switched off; the error toast of a failed action names the action as the user saw it. Verified in the harness: the question text and its two buttons. Independent review afterwards, fixes verified in the harness: an interpreter from the setting `robotcode.python` without Robot Framework gets the message that names the setting, with **Open Settings** (opens the Settings editor) and **Retry** (appended the time of the check); a `uv pip install robotframework` into that venv closed the message and started the language server. The generation guard of the checks first compared an unset counter with zero and marked every first check as superseded, which the same harness run exposed before the fix. Third round: the polling with the check script noticed a `uv pip install robotframework` within three seconds and closed the message; measured over twelve minutes with a temporary log line, the script ran 60 times at 5 s intervals and from then on every 10 s (40 attempts observed), and **Retry** started the 5 s pace again; after the texts lost their closing sentence, an install closed the message and the information message "Python environment for 'env-venv-no-rf16' found: .venv (venv) with Python 3.13.12 and Robot Framework 7.5. RobotCode is ready." appeared (since reworded to "Environment for … found"); `resolveEnvironment` of the old API's `DEFAULT_PYTHON` returned the PATH's `python3.15` with prefix and version, which the provider now uses instead of reporting "no interpreter selected".

## Open Questions
