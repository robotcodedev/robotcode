# Design: library-loading-robustness

## Context

See proposal.md. The change has three parts: a hard timeout, a remembered timeout and a visible fallback without arguments (maintainer decision 2026-09-29). Verified facts that shape the design:

- **Worker and timeout.** `ImportsManager._run_in_subprocess` (`imports_manager.py:1641-1666`) starts a fresh `ProcessPoolExecutor(max_workers=1, mp_context=spawn)` per library or variable-file load, waits with `.result(self.load_library_timeout)`, turns `TimeoutError` into a `RuntimeError` ("… timed out after N seconds …") and then runs `executor.shutdown(wait=True)` in `finally`, which waits for the worker to finish. Reproduced during planning: a library sleeping 4 s with a 1 s timeout raised at 1.0 s and returned at 4.1 s. `ProcessPoolExecutor.terminate_workers()`/`kill_workers()` exist only from Python 3.14; RobotCode supports 3.10+. A planning prototype with a spawned `multiprocessing.Process`, a one-way `Pipe`, `poll(timeout)` and `terminate()`/`kill()` returned at 1.0 s, the library's code after its blocking call never ran, and `Collections` loaded normally through the same helper.
- **Failure lifetime.** The timeout error propagates out of `_LibrariesEntry._update` (`imports_manager.py:218-225`) / `_VariablesEntry._update`, so `_lib_doc` stays `None` and the next `get_libdoc_with_meta` (`:284-297`) loads again; two suites importing one hanging library loaded it twice in one `analyze code` run. A load that fails with an error returns a `LibraryDoc` with `errors`, which the entry keeps: two suites importing a refused `Remote` connected only for the first. An entry lives while a namespace references it (`__remove_library_entry` via `weakref.finalize`) and is invalidated by `check_file_changed` (library source, package directory or Python path, depending on what the `LibraryDoc` carries). Library results with errors are written to disk with `meta.has_errors` and not served from it; variable-file results never set `has_errors`. `build_namespace_meta` (`imports_manager.py:841-874`) refuses to persist a namespace when a dependency meta is `None`. `_import_default_libraries` (`import_resolver.py:192-224`) reports only exceptions ("Can't import default library …"), not `LibraryDoc.errors`. The language server is restarted by the VS Code client when `robot.toml`/`pyproject.toml` change and by Clear Cache and Restart (`languageclientsmanger.ts`); `robot/cache/clear` alone clears only the disk cache.
- **Fallback without arguments.** `get_library_doc` records the error of `_get_test_library(..., args)` / instantiation and, `if args:`, builds the library again with `()` and documents that instance (`library_doc.py:2513-2533`). Observed with `analyze code` on RF 7.5: `Library StrictLib.py bogus`, `… a b c AS Two` and `… ${NOT_KNOWN} AS Three` report `ImportContainsErrors` / `DataError` / `VariableError`, and all three provide `Strict Keyword` (reported as `MultipleKeywords`); nothing says where the keywords come from. `ignore-arguments-for-library` passes `()` to `get_library_doc` (`imports_manager.py:1731`). `LibraryDoc.__setstate__` (`library_doc.py:1528`) sets missing slots to `None`; the disk cache is keyed by `app_version`.

## Goals / Non-Goals

**Goals:**
- The load in the worker process never blocks longer than `load-library-timeout` (plus process termination), and a timed-out load is not repeated for every namespace build.
- The fallback without arguments is visible on the import and to every caller of `get_library_doc`.

**Non-Goals:**
- Remembering other failures than timeouts and imports that end early beyond today's behaviour: errors are already kept in the entry, failed variable-file loads stay in the disk cache unlike failed library loads, and exceptions such as a library path that does not exist stay fast and are not cached.
- Finding a module by name in the analysing process. `get_library_meta` and `get_variables_meta` call `get_module_spec` (`library_doc.py:1891-1920`) before the worker starts (`imports_manager.py:1706`, `:1882`), and for a dotted name it imports the parent packages. The timeout does not cover this; unchanged.
- Changing import-name completion. It runs in the shared pool of `ImportsManager.executor` with its own limit of 5 seconds (`COMPLETE_LIBRARY_IMPORT_TIMEOUT`, `imports_manager.py:2063-2106`) and does not wait for its worker beyond that limit.
- Removing the reloads with `()` of signature help, inlay hints and the semantic analyzer (`signature_help.py:646`, `inlay_hint.py:550`, `semantic_analyzer/analyzer.py:3958`). They go through the same import entries, so the hard and the remembered timeout bound them.

## Decisions

### D1: Hard timeout with a plain spawned process

`_run_in_subprocess` keeps its contract (one fresh process per load, `spawn` context, same callers) but uses a `multiprocessing` `Process` whose module-level target sends `(ok, value)` over a one-way `Pipe`. The parent waits with `multiprocessing.connection.wait` on the pipe and the process sentinel for `load_library_timeout`, capped at 2,000,000 seconds because waiting on a pipe takes the timeout in milliseconds as a C int on POSIX (a larger value raised `OverflowError`, found in review). On expiry it raises a dedicated timeout exception (a `RuntimeError` subclass with today's message, so callers can tell a timeout apart). A `finally` block ends a worker that is still alive in every case (timeout, `KeyboardInterrupt`, errors): `terminate()`, `join` for one second, `kill()` if needed, `join()`. It does not call `Process.close()`: on Python 3.10 that races with `Process.start()` in other threads, and it fails when another thread has already reaped the child (found in review). An `Exception` raised in the worker is re-raised in the parent with its type. A `SystemExit` ends only the worker (maintainer decision 2026-09-30): the worker catches `Exception` only, so multiprocessing turns `SystemExit(n)` into the exit code `n`. If the worker ends without sending a result, the parent raises a dedicated `LoadExitError` naming the exit code (today `BrokenProcessPool`): "… failed: the import ended with exit code n before it finished, for example through sys.exit() or a crash in the imported code." The message does not mention the worker process, which users do not know about (maintainer decision 2026-09-30). The parent closes its copy of the sending end after `start()`, so the pipe reports EOF when the worker ends. On Windows the worker takes over the sending end only when it unpickles its arguments; if it ends before that, only the sentinel is ready and the pipe has no data. Both cases give the error naming the exit code, not a timeout.

Rejected: `terminate_workers()`/`kill_workers()` (Python 3.14 only); killing the pool's processes through `ProcessPoolExecutor._processes` (private attribute); a thread with a timeout (cannot stop the worker); a version split between 3.14 and older.

### D2: A timeout becomes a kept error result

`_get_library_libdoc` and `_get_variables_libdoc` catch the timeout exception, and the exception of an import that ended early (D1), and return an error document instead of raising, as for any other import error: a `LibraryDoc`/`VariablesDoc` with the import name, `source` set to the file RobotCode already resolved without importing (`LibraryMetaData.origin`, or the found path of an import by path), and one `Error` without a source with the timeout message, which no longer names `working_dir` and `base_dir`, and the type name `LibraryTimeoutError` or `VariablesTimeoutError` for a timeout and `LibraryExitError` or `VariablesExitError` for an import that ended early (new constants in `errors.py`; today the code is `RuntimeError`, maintainer decision 2026-09-30), so `_report_entry_errors` reports it on the import with that code; the `LibraryDoc` also gets `python_path`. The existing entry code then keeps it (`_lib_doc` is set) and attaches its file watchers, and `check_file_changed` invalidates it when a file changes. Libraries are watched through `source`, else `python_path` (without a meta, as for `ignored-libraries`, a library imported by module name has no `source`, like a library that cannot be found). Variable files are watched through `source` only (`imports_manager.py:478-486`, `:505-511`), so a variable file without a resolved path, such as a module name that matches `ignored-variables`, stays failed until a restart. The error document is not written to the disk cache, and the methods return `None` as meta, so namespaces that depend on it are not persisted. `ImportResolver` records dependency metas per import name (`lib:{imp.name}`, `var:{imp.name}`, `import_resolver.py:332`, `:560`), and a later import of the same name overwrites the entry; `_import_library` and `_import_variables` therefore keep an existing `None` for the key instead of replacing it, so that a later import of the same name that loads (for example with other arguments and an alias) does not make the namespace persistable. `_import_default_libraries` reports the errors of a returned default-library document with its existing "Can't import default library '…': …" message, so a timed-out `BuiltIn` stays visible. The command-line variable files already report `VariablesDoc.errors`.

Alternatives: caching the exception object in the entry (a second failure path next to `LibraryDoc.errors`, and no file watchers); remembering timeouts on disk (would survive a restart, which the proposal names as the retry point).

### D3: The fallback without arguments carries a marker

`get_library_doc` keeps the retry with `()` (maintainer decision) and sets a new `LibraryDoc` field `loaded_without_arguments: bool = False` when the documented instance comes from that retry. Old pickles get `None` (falsy) through `__setstate__`. `ImportResolver._report_entry_errors` (imports of the analysed file only) appends, after the import's errors, an INFORMATION diagnostic `LibraryLoadedWithoutArguments` (new `Error` constant): "Keywords of library '<name>' come from loading it without arguments, because loading it with the import's arguments failed." INFORMATION, because the original error is already reported as ERROR on the same import and this message only explains the keywords. The marker is set by `get_library_doc` itself, so callers outside the analysis see it too: `doc-cli` calls `get_library_doc` directly and aborts when the marker is set.

Alternatives: appending the note to the error's related information (not suppressible on its own, and invisible to other callers); a WARNING (a second warning-or-worse diagnostic on an import that already has an ERROR).

### D4: The disk cache key includes the import arguments

The disk cache keeps a library's or variable file's documentation under `LibraryMetaData.cache_key` (module name or path), and `_get_library_libdoc` serves a stored entry whenever its meta matches, whatever the import arguments (`imports_manager.py:592-600`, `:1775`). The in-memory import entries are already keyed per argument set (`_LibrariesEntryKey(source, resolved_args)`), but their load reaches the disk cache first. Found while testing this change: an argument added to a library without arguments, or a mistyped `Remote` URL, showed the stored documentation of an earlier load and no error until Clear Cache and Restart.

`LibraryMetaData.cache_key_for_args(args)` appends the arguments to the key, separated by a newline as the namespace entries do (so `robotcode analyze cache list` shows `key · args` and its patterns match the key part), and returns the plain key for an import without arguments, so stored entries of such imports stay valid. `_get_library_libdoc` resolves the arguments with `resolve_args`, as the in-memory entry key does; with `ignore-arguments-for-library` the library is loaded with `()`, so its key has no arguments and it keeps one entry. `_get_variables_libdoc` gets arguments that its entry has already resolved. `_save_import_cache` writes under the same key. The meta itself and the namespace dependency metas are unchanged (maintainer decision 2026-09-30).

Rejected: loading live whenever the arguments differ from a stored entry (argument variants would never be cached); a declaration per library, as the parked `library-keyword-set-declaration` plans it (the key per argument set makes its `args` value unnecessary).

## Risks / Trade-offs

- [Processes started by the library survive the worker (Java of SikuliLibrary's default mode, node of Browser with `jsextension=`)] → unchanged from today (the executor never ended them either). Ending a process tree portably needs platform-specific code or a dependency such as `psutil`, which RobotCode does not have.
- [A library installs a `SIGTERM` handler] → `kill()` after one second.
- [A library that is slow only once stays failed until a file change or restart] → the timeout message says how to raise the limit; Restart Language Servers or Clear Cache and Restart loads it again.
- [Any change in the directory of a timed-out library's source loads it again, the rule every library entry uses today; so saving a suite next to `SlowLib.py` waits for the timeout again] → accepted, the spec and the docs describe the directory rule (maintainer decision 2026-09-30). Libraries such as `Remote` live outside the workspace and are not affected by saves.
- [A timed-out library inside a resource file no longer marks the suite's `Resource` import with "Import definition contains errors."] → it now behaves like every other load error of a nested import, which is reported in the resource file itself; accepted.
- [More diagnostics on imports with failing arguments] → information severity; suppressible.
- [One disk entry per argument set] → bounded by the argument sets the project imports; entries of imports without arguments keep their key.
- [A `Remote` server that changes its keywords under the same URL is still served from the disk cache] → unchanged; `ignored-libraries` remains the remedy (the `volatile` value of the parked `library-keyword-set-declaration`).

## Migration Plan

Additive; no user migration. A release drops the whole disk cache through its version (`app_version`), so entries written under the old key, where an entry under the plain key may come from an import with arguments, are not reused. A development build with an unchanged version needs Clear Cache and Restart once. The new diagnostic code can be suppressed with the existing modifiers. Timeout diagnostics get the codes `LibraryTimeoutError` and `VariablesTimeoutError`, and imports that end early `LibraryExitError` and `VariablesExitError`, instead of `RuntimeError`; modifiers that match `RuntimeError` for these need the new codes.
