# Design: variable-name-resolution-errors

## Context

See proposal.md for the motivation. Verified facts:

- **Robot Framework (5.0.1, 7.0.1, 7.5).** Before a finder looks a variable up, `VariableReplacer._get_variable_value` (`robot/variables/replacer.py`) calls `VariableMatch.resolve_base` (`robot/variables/search.py`), which replaces the variables in the whole text between the braces. `EnvironmentFinder.find` (`robot/variables/finders.py`) then splits that resolved text at the first `=` into name and default. So in `%{NE_X=${S}}` the default is resolved even when `NE_X` is set, and an undefined variable in it fails. A declared name that cannot be resolved fails as follows on 7.0.1 and 7.5: in `*** Variables ***` as a file-level error ("Setting variable '${R_${UNDEF2}}' failed: Variable '${UNDEF2}' not found.", the variable is not created and the tests still run); in `VAR` and in an assignment the test fails with the same message; an unset environment variable fails with "Environment variable '%{NE_UNSET_suffix}' not found.", naming the resolved name. On 5.0.1 and 6.1.1 a nested declared name is invalid ("Invalid variable name '${X_%{NE_A_${S}}}'", and `${Q_%{NE_A_${S}}}=` is not an assignment but a keyword name), while a nested reference such as `${NAME_%{NE_A_${S}}}` is resolved and passes.
- **Where `VariableNameNotResolvable` is reported** ([errors.py:51](../../../packages/robot/src/robotcode/robot/diagnostics/errors.py)). Only on Robot Framework 7.0 and newer, at three declaration sites in each analyzer:
  - `NamespaceAnalyzer`: `_visit_Variable` for `*** Variables ***` ([namespace_analyzer.py:280](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py), [:305](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py)), `visit_Var`, which exists only on 7.0 and newer ([:472](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py), [:495](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py)), and `_analyze_assign_statement` for keyword-call and inline-`IF` assignments ([:1489](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py)).
  - `SemanticAnalyzer`: the same three methods ([semantic_analyzer/analyzer.py:513](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/analyzer.py), [:537](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/analyzer.py), [:702](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/analyzer.py), [:724](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/analyzer.py), [:3213](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/analyzer.py)).
  - Two causes: an empty nested variable (`${}`, `@{}`, `&{}`, `%{}`) in the name, checked before any resolution (in assignments this returns without a diagnostic), and a `(None, ref)` result of `_try_resolve_nested_variable_base`. Only the second is affected by this change.
- **The resolution contract.** `_try_resolve_nested_variable_base` ([namespace_analyzer.py:1955](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py), [semantic_analyzer/analyzer.py:4338](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/analyzer.py)) replaces every nested variable of a name with `_resolve_variable_to_string` and returns the resolved name (`str`), `False` when a part is not statically resolvable, or `(None, ref)` when a part is not found. The declaration sites turn `False` into the hint `VariableNameNotStaticallyResolvable` and `(None, ref)` into the error `VariableNameNotResolvable`, and define no variable in both cases. The reference sites (`_iter_variables_from_token` in the `NamespaceAnalyzer`, [namespace_analyzer.py:2261](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py); `_resolve_variable_occurrence` in the `SemanticAnalyzer`, [semantic_analyzer/analyzer.py:4618](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/analyzer.py)) record a reference for a resolved name that exists, report the hint `VariableReferenceNotStaticallyResolvable` for `False`, and report nothing otherwise (the `NamespaceAnalyzer` falls through to its extended-syntax branch, which skips names with nested variables). `dev-docs/semantic-model.md` ("Nested Variable Diagnostics") documents the split: the error because Robot Framework fails too, the hint because the analyzer lacks the static information.
- **The `%{...}` branch** of `_resolve_variable_to_string` ([namespace_analyzer.py:2011](../../../packages/robot/src/robotcode/robot/diagnostics/namespace_analyzer.py), [semantic_analyzer/analyzer.py:4394](../../../packages/robot/src/robotcode/robot/diagnostics/semantic_analyzer/analyzer.py)) splits the unresolved text at the first `=`, returns `os.environ[name]` if set, else the unresolved default, else `None`. It is reached for an environment variable directly in a name, through `_resolve_string_expression` for one in the value of a variable used in a name, and for one nested in the name of another environment variable. The environment is the IDE's: the language server applies the `env` of the initialization options and of the workspace configuration at startup ([protocol.py:180](../../../packages/language_server/src/robotcode/language_server/robotframework/protocol.py), [:240](../../../packages/language_server/src/robotcode/language_server/robotframework/protocol.py)). Both analyzers already import `split_from_equals` ([utils/variables.py:230](../../../packages/robot/src/robotcode/robot/utils/variables.py)), a wrapper of Robot Framework's `robot.utils.escaping.split_from_equals`, which splits a text at the first `=` that is not part of a variable and not escaped, and returns `None` as the value when there is no such `=`.
- **`%{...}` references with nested variables.** For a reference whose outer variable is `%{...}` and whose text contains a nested value that cannot be resolved statically, the `SemanticAnalyzer` already reports `VariableReferenceNotStaticallyResolvable` (`_resolve_variable_occurrence` handles `%{` like `${`, `@{` and `&{`), and the `NamespaceAnalyzer` reports nothing. Checked with `robotcode analyze code` on Robot Framework 7.5 for `Log    %{NE_${{1}}=x}` and for `Log    %{NE_${r}=x}` with `${r}` assigned from a keyword call.
- **Other checks on the same tokens.** Before resolving a declared name, both analyzers analyze its nested variables as references. The `SemanticAnalyzer` checks a nested `%{NE_UNSET_${S}}` under its resolved name (`EnvironmentVariableNotFound` for `%{NE_UNSET_suffix}`); the `NamespaceAnalyzer` checks the unresolved name in `_handle_find_variable_result` and reports `EnvironmentVariableNotFound` for `%{NE_A_${S}}` even when `NE_A_suffix` is set. That check is not part of this change; the open change `env-var-check-nested-names` removes the `NamespaceAnalyzer`'s check of such unresolved names and leaves the `SemanticAnalyzer`'s check of the resolved name as an Open Question.
- **Tests.** `tests/robotcode/robot/diagnostics/test_semantic_analyzer/test_nested_variable_resolution.py` tests this resolution for both analyzers (`run_both` fixture), including `%{UNLIKELY_ROBOTCODE_TEST_VAR=fallback}`. Its classes are skipped on Robot Framework older than 7.0; none checks that nothing is reported there. No variable name in the LSP test data has an environment variable with a nested variable. Names with `%{...}` exist in `hover.robot` (`${VALID VAR %{ENV_VAR=env_value}}`, `${INVALID VAR %{UNKNOWN_ENV_VAR}}`, `${VALID VAR %{UNKNOWN_ENV_VAR=env_value}}`) and `variables.robot` (`${%{TESTENV}.server.ip}`), but none has a variable inside the braces, so D1 leaves them unchanged.

## Goals / Non-Goals

**Goals:**
- No error and no variable under a name with unresolved text where the analyzer would have to guess the result of a nested environment variable.
- No new error or warning where today's result is the name Robot Framework defines when the resolved environment variable is not set (a default without variables behind a name with a variable, D1).
- Keep every result that is certain today, including the error for an unset environment variable without default.

**Non-Goals:**
- Resolving nested variables inside `%{...}` before the lookup (see D1, rejected alternative).
- Uses of the name Robot Framework defines at run time (`${X_1}` still gets `VariableNotFound`) and variables used only through such names (still `VariableNotUsed`); see Open Questions.
- The `NamespaceAnalyzer`'s `EnvironmentVariableNotFound` for an unresolved nested name (change `env-var-check-nested-names`), and the diagnostics of variables nested in `%{...}`.
- Nested references on Robot Framework older than 7.0, which Robot Framework resolves but the analyzers do not try to.
- Aligning the two analyzers for references whose outer variable is `%{...}` (see Context and D3).
- The wording of the error that stays for an unset environment variable without default (see Open Questions).

## Decisions

### D1: Return "not statically resolvable" where the `%{...}` branch would use unresolved text

In the `%{...}` branch of `_resolve_variable_to_string`, in both analyzers:

1. Split the text between the braces with `split_from_equals` into name and default. If the name contains a variable (`contains_variable(name, "$@&%")`), the analyzer does not know which environment variable Robot Framework looks up: return the default if there is one and it contains no variable, as today; otherwise return `False`.
2. Otherwise the name contains no variable. Split and look up as today (at the first `=`, in `os.environ`); a set variable returns its value.
3. If it is not set and has a default, return `False` if the default contains a variable (`contains_variable(default, "$@&%")`), else the default.
4. Without a default, return `None` as today, so the error stays.

An escaped `\${S}` is no match for `contains_variable`, so it keeps today's behavior. The result changes only where today's branch returns a default with an unresolved variable (steps 1 and 3), `None` for a name with a variable (`%{NE_A_${S}}`, step 1), or a fragment of a nested variable that contains `=` (`%{NE_${{'a=b'}}}` returns `b'}}` today, step 1). A default without variables behind a name with a variable (`%{NE_${S}=fb}`) is returned as today. It is what Robot Framework uses when the resolved environment variable (`NE_suffix`) is not set; see Risks and Open Questions.

Alternatives considered:
- Resolving the text between the braces with `_resolve_string_expression` before splitting it, as the earlier review suggested. A prototype defined `${X_1}` and removed the follow-on `VariableNotFound`, but it extends static resolution, which is not pursued (maintainer decision).
- Returning `False` in step 1 also for a default without variables (the first version of this design). `${N_%{NE_${S}=fb}}` gets the hint instead of defining `${N_fb}`. With `NE_suffix` not set, Robot Framework 7.5 defines `${N_fb}` and passes, while a prototype of this variant reported a new `VariableNotFound` error on `Log    ${N_fb}` and a new `VariableNotUsed` warning on `${USED_fb}` used only as `${USED_%{NE_${S}=fb}}`; today neither is reported. That adds errors where the analyzer cannot know the result. See Open Questions.
- Returning `False` whenever the text contains any variable. A set environment variable with a variable in its default (`${Y_%{NE_SET=${S}}}`) is resolved correctly today; a prototype of this variant turned it into a hint and a new `VariableNotFound` on `${Y_setval}`.
- Splitting with today's split at the first `=` and checking only the name part for variables. A nested variable that contains `=` (`%{NE_${{'a=b'}}}`) is cut in two; the name part `NE_${{'a` contains no complete variable, so the fragment `b'}}` would be returned as the default. `split_from_equals` does not split inside a nested variable.

### D2: The existing hint, not silence

`False` is the existing result for "not statically resolvable", and all declaration and reference sites already turn it into `VariableNameNotStaticallyResolvable` or `VariableReferenceNotStaticallyResolvable`, as for `${X_${{1}}}` or `${NAME_${local}}`. Silence would need another result besides `str`, `False` and `(None, ref)` for this one case. References such as `${NAME_%{NE_X=${S}}}`, which got nothing before, get the hint.

### D3: Same edit in both analyzers, no caller changes

The resolution code is duplicated in both analyzers, which implement the same nested variable resolution "for output parity" (`dev-docs/semantic-model.md`), so both get the same edit. The callers stay as they are. The `NamespaceAnalyzer` never resolves a reference whose outer variable is `%{...}` (its `_find_variable` returns an environment variable definition for every `%{...}`), while the `SemanticAnalyzer` does and reports the hint for such a reference when a nested value cannot be resolved (see Context). So `%{%{NE_N_${S}}=x}` gets the new hint only from the `SemanticAnalyzer`, as `%{NE_${{1}}=x}` does today. The reference requirement in the spec therefore requires identical results for `${...}`, `@{...}` and `&{...}` references and pins the semantic-only hint for `%{...}` references in a scenario of its own. If `env-var-check-nested-names` decides its Open Question for aligning the `SemanticAnalyzer` (no RF ≥ 7.0 resolution for `%{...}` references), that hint goes away and the scenario changes to no hint on either path.

### D4: Tests

New test class in `test_nested_variable_resolution.py`, skipped on Robot Framework older than 7.0, running both analyzers through `run_both` with environment variables set and removed through `monkeypatch` (unique upper-case `ROBOTCODE_TEST_…` names, upper-case values for `${S}`). The assertions filter the codes of this change (`VariableNameNotResolvable`, `VariableNameNotStaticallyResolvable`, `VariableReferenceNotStaticallyResolvable`, `VariableNotFound`) and check the defined names and the recorded references per analyzer, instead of `_assert_nested_var_parity`, because the `NamespaceAnalyzer` additionally reports `EnvironmentVariableNotFound` for the unresolved nested name (see Context; until `env-var-check-nested-names` lands), and only the `SemanticAnalyzer` reports the hint for a `%{...}` reference (D3). A second test, skipped on Robot Framework 7.0 and newer, runs both analyzers on `${X_%{NE_A_${S}}}` and checks that neither `VariableNameNotStaticallyResolvable` nor `VariableNameNotResolvable` is reported, so the spec scenario for older versions is covered. No LSP test data and no regression baselines change.

## Risks / Trade-offs

- [A name that fails in Robot Framework gets only the hint, for example `${W_%{NE_UNSET_${S}}}`] → Intended: no error where the analyzer cannot know the result. The `SemanticAnalyzer` still reports `EnvironmentVariableNotFound` for `%{NE_UNSET_suffix}` on the nested token; whether it keeps that check of a statically resolved name is an Open Question of `env-var-check-nested-names`, which removes the `NamespaceAnalyzer`'s check of the unresolved name.
- [`${Z_%{NE_A_${UNDEF}}}` fails in Robot Framework for certain ("Setting variable '${Z_%{NE_A_${UNDEF}}}' failed: Variable '${UNDEF}' not found." on 7.5), and the analyzer knows that `${UNDEF}` is not defined, yet the name gets the hint instead of today's `VariableNameNotResolvable`] → Step 1 returns before the nested variables of the environment variable are looked at. The error is carried by `VariableNotFound` on `${UNDEF}`, which both analyzers keep. This departs from the split in `dev-docs/semantic-model.md`, where a nested inner variable that is not found makes `VariableNameNotResolvable`.
- [A default without variables behind a name with a variable is kept: `${N_%{NE_${S}=fb}}` defines `${N_fb}`, which is not the name Robot Framework defines when `NE_suffix` is set (on 7.5, `Log    ${N_val}` passes with `NE_suffix` = `val`) or when a nested variable of the name resolves to text with `=` (for `${L_%{NE_${{'a=b'}}=fb}}` Robot Framework defines `${L_b=fb}`, the analyzer `${L_fb}`, today `${L_b'}}=fb}`)] → Today's result in the first case; uses of the name Robot Framework defines keep `VariableNotFound`, as today. Returning `False` instead adds errors where Robot Framework passes (D1, alternatives); see Open Questions.
- [`${X_1}` keeps `VariableNotFound` and `${NAME_suffix}` keeps `VariableNotUsed`] → Same as for every name that cannot be resolved statically; see Open Questions.
- [New hints on references that were silent, including `%{...}` references such as `%{%{NE_N_${S}}=x}`, which only the `SemanticAnalyzer` reports (D3)] → Hint severity; can be suppressed with the existing modifiers like any diagnostic.
- [`${Y2_%{NE_SET=${UNDEF}}}` defines `${Y2_setval}`, while Robot Framework fails because it resolves the default before the lookup] → Unchanged by this change; `${UNDEF}` gets its own `VariableNotFound`.

## Migration Plan

No migration: the change lowers an error to an existing hint, reports that hint instead of some definitions under names with unresolved text, and adds the existing hint to some references. Rollback is reverting the two branches.

## Open Questions

- Uses of a name that Robot Framework defines at run time from a declaration the analyzer cannot resolve (`${X_1}`) keep the error `VariableNotFound`, for this case as for `${X_${{1}}}`. Should such uses be reported differently when a declaration in scope could not be resolved? That would need both analyzers to track unresolved declarations per scope, which neither does today, and is a separate change.
- Step 1 keeps a default without variables behind a name with a variable (`%{NE_${S}=fb}`): no new diagnostics, but a wrong name when the resolved environment variable is set. Should it return `False` instead, giving the hint on the declaration but new `VariableNotFound` errors on uses of the default name and new `VariableNotUsed` warnings, also where Robot Framework passes with the environment variable not set?
- The error that stays for `${U_%{NE_UNSET}}` says "Variable '%{NE_UNSET}' not found.", while Robot Framework says "Environment variable '%{NE_UNSET}' not found.". Align the wording in a follow-up?
